## Подтверждённые ошибки интерфейса

### F1 · P1 · Ответ на предыдущий вопрос меняет новый экран

**Воспроизведение:** выбрать ответ в теме 01, задержать ответ `POST /api/answers`, вернуться к категориям и открыть тему 02, затем разрешить старому запросу завершиться.

**Результат:** новый, ещё не отвеченный вопрос получает статус «Верно», подсветку и пояснения предыдущего вопроса. Кнопка ответа блокируется. В проверке ни один вариант нового вопроса не был выбран. Например, к вопросу про `ON_ERROR_ROLLBACK` появились пояснения про `pg_ctl`.

**Причина:** `submitAnswer()` после `await` изменяет текущий DOM и обращается к изменяемым `questions[index]`, не проверяя, относится ли ответ API к открытому вопросу. См. [public/js/app.js](../public/js/app.js), функция `submitAnswer`, строки 469–509 на дату аудита.

**Предлагаемая правка:** привязать отправку к конкретному вопросу и экземпляру экрана; применять результат только при совпадении. Повторное открытие того же вопроса также должно отличаться от старого запроса.

**Проверка будущего исправления:** задержанный ответ после перехода не меняет варианты, результат и доступность кнопок нового экрана; обычный ответ по-прежнему отображается.

[Скриншот F1](audit-2026-10-14/late-response.png).

### F2 · P1 · После ошибки завершения экзамена таймер остаётся остановленным

**Воспроизведение:** начать экзамен, установить близкий срок завершения в сохранённом состоянии тестовой сессии и восстановить экзамен. Однократно вернуть HTTP 503 для `POST /api/exam/check`, нажать завершение, восстановить доступность API и дождаться истечения срока.

**Результат:** значение таймера осталось `00:06` до и после ожидания семи секунд. Срок уже истёк, но экран экзамена остался активным и позволил изменить ответ. Повторного автоматического запроса завершения не было.

**Причина:** `finishExam()` вызывает `stopTimer()` до запроса, а при ошибке только сбрасывает `exam.finishing` и показывает сообщение. См. [public/js/app.js](../public/js/app.js), строки 754–781.

**Предлагаемая правка:** сохранять первоначальный срок экзамена; после ошибки возобновлять отсчёт, если время ещё есть. После истечения времени блокировать изменение ответов и оставлять возможность повторной отправки результата без продления срока. Автоматические повторы не должны создавать бесконечный поток запросов.

**Проверка будущего исправления:** отказ API до и после истечения срока; восстановление сети; повторная отправка результата; сохранение ответов при ошибке.

[Скриншот F2](audit-2026-10-14/exam-network-failure.png).

### F3 · P2 · Двойной щелчок дважды сохраняет ответ

**Воспроизведение:** выбрать вариант, задержать ответ API на 500 мс и дважды нажать «Ответить» с интервалом 50 мс.

**Результат:** два запроса, две новые строки `answer_log`, восемь примечаний вместо четырёх. Повторная запись влияет на статистику попыток.

**Причина:** в `submitAnswer()` кнопка блокируется только после завершения запроса; защиты от повторного запуска нет. См. [public/js/app.js](../public/js/app.js), та же функция, что в F1.

**Предлагаемая правка:** синхронно устанавливать признак отправки и блокировать повторную отправку до первого `await`; после ошибки давать повторить попытку. Согласовать эту защиту с проверкой актуальности экрана из F1.

**Проверка будущего исправления:** быстрый двойной щелчок создаёт один запрос и один набор пояснений; после отказа API возможна новая попытка.

[Скриншот F3](audit-2026-10-14/double-submit.png).

### F4 · P3 · Список тем выходит за экран шириной 320 px

**Воспроизведение:** открыть список категорий при ширине окна 320 CSS px.

**Результат:** ширина документа — 337 px, карточки выступают за правую границу. На ширинах 360, 390 и 1280 px этот дефект не воспроизвёлся.

**Область правки:** размеры элементов сетки и размещение названия/счётчика в `.cards`, `.card`, `.card-name`, `.card-count` в [public/css/style.css](../public/css/style.css). Непереносимый счётчик и минимальная ширина содержимого требуют адаптации к узкому экрану.

**Проверка будущего исправления:** документ помещается в 320 px, длинные названия и счётчики читаются; остальные проверенные ширины сохраняют корректную раскладку.

[Скриншот F4](audit-2026-10-14/categories-320.png). Полный скриншот имеет ширину документа 337 px; исходный viewport — 320 px.

## Замечания к вопросам темы 01

### C1 · P2 · ID 265: не определён источник и способ сборки

Вопрос «Что обязательно нужно для сборки PostgreSQL из исходных кодов традиционным способом?» предполагает ответ `BC`: компилятор C и GNU make. Однако условие не уточняет, что речь о релизном архиве на Unix/Linux. Для сборки из Git нужен также Perl, поэтому текущая формулировка допускает ответ, который тренажёр сочтёт ошибочным. Объяснение «Perl нужен только для PL/Perl и сборки из git» также слишком категорично: есть другие случаи, например некоторые тесты. Это описано в [требованиях PostgreSQL 16 к сборке](https://www.postgresql.org/docs/16/install-requirements.html).

**Предлагаемое условие:** «Что обязательно нужно для обычной сборки PostgreSQL 16 из релизного архива на Unix/Linux с помощью configure и GNU make, без дополнительных процедурных языков и тестов?»

Ключ `BC` можно сохранить; объяснение следует привести к явно указанным условиям. Источники проекта: [006_seed_multi_and_code.sql](../migrations/006_seed_multi_and_code.sql), [022_option_notes_01_04.sql](../migrations/022_option_notes_01_04.sql).

### C2 · P3 · ID 4: неточное объяснение контрольных сумм

Правильный вариант `-k (--data-checksums)` верен. Неточность находится в объяснении: «Контрольная сумма проверяется при каждом обращении к странице». Проверка относится к чтению страницы с диска, а не к каждому обращению к уже находящейся в буфере странице. См. [документацию о контрольных суммах](https://www.postgresql.org/docs/16/checksums.html) и комментарий к `PageIsVerifiedExtended` в [исходном коде PostgreSQL 16](https://raw.githubusercontent.com/postgres/postgres/REL_16_STABLE/src/backend/storage/page/bufpage.c).

**Предлагаемое объяснение:** «Контрольная сумма записывается при сохранении страницы и проверяется при чтении страницы с диска. Это создаёт дополнительные затраты, но помогает обнаруживать повреждения данных».

Источник проекта: [002_seed_questions.sql](../migrations/002_seed_questions.sql).

### C3 · P3 · ID 554 и 555: пакетные утилиты ошибочно ограничены Ubuntu

В ID 554 объяснение называет `pg_lsclusters`, `pg_createcluster`, `pg_dropcluster` и `pg_ctlcluster` специфичными для Ubuntu. Эти утилиты входят также в Debian `postgresql-common`: [pg_lsclusters](https://manpages.debian.org/bookworm/postgresql-common/pg_lsclusters.1.en.html), [pg_createcluster](https://manpages.debian.org/bookworm/postgresql-common/pg_createcluster.1.en.html), [pg_ctlcluster](https://manpages.debian.org/bookworm/postgresql-common/pg_ctlcluster.1.en.html).

В ID 555 фраза «В других системах кластер создают initdb и удаляют средствами ОС» чрезмерно обобщает различия установок. В Debian доступен [pg_dropcluster](https://manpages.debian.org/bookworm/postgresql-common/pg_dropcluster.1.en.html).

**Предлагаемая правка:** назвать семейство Debian/Ubuntu и пакет `postgresql-common`; отдельно описать установку из исходников без таких обёрток. Правильные ответы `pg_lsclusters` и `pg_dropcluster` сохраняются.

Источники проекта: [013_topics_01_04.js](../scripts/questions/013_topics_01_04.js) и [013_more_questions_01_04.sql](../migrations/013_more_questions_01_04.sql).
