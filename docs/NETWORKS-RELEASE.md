## Серверный порядок после разрешения

1. Проверить чистый git status в /var/www/pg16-cert-prep; при любых изменениях
   остановиться. Сохранить состояние/PID соседних служб и проверить их сайты.
2. Сделать закрытую резервную копию базы pg16_cert и проверить её читаемость.
   Не читать .env и не использовать runtime-реквизиты для миграции.
3. Коммит/push в main; на сервере fetch, показать log HEAD..origin/main и
   pull --ff-only. Файлы доставляются только через git.
4. Административным соединением применить **148**, повторить и проверить тему/поле.
   Новая версия API зависит от этого поля: запускать её раньше 148 нельзя.
5. Перезапустить только pg16-cert-prep, проверить API и запрет новой темы в экзамене.
6. Применить **149**, повторить и проверить 48 вопросов. Этот порядок не даёт
   старому серверу выдать сетевые вопросы при ручном выборе до установки запрета.
7. Проверить вход, материал, порцию 16, ошибку и восстановление ответа, историю,
   статистику и экзамен. Для проверки использовать отдельного тестового пользователя,
   не добавлять ответы в историю владельца. Сверить соседние PID/HTTP и мониторинг.

На appuse команды миграции из каталога git-копии (выполняются на указанных этапах):

```bash
sudo -u postgres psql -X -p 5432 -d pg16_cert -v ON_ERROR_STOP=1 \
  -c 'SET ROLE pg16_owner' -f migrations/148_networks_category.sql
```

После restart и проверки новой версии API:

```bash
sudo -u postgres psql -X -p 5432 -d pg16_cert -v ON_ERROR_STOP=1 \
  -c 'SET ROLE pg16_owner' -f migrations/149_networks_questions.sql
```

Каждую команду выполнить повторно для проверки идемпотентности. Не запускать
все прежние миграции заново. Не применять схему от runtime-роли.
