# Первый этап ограничений безопасности

Учёт: задача 234; основание — согласование параметров после аудита 12 ноября.
Состояние: локальная реализация, миграция 145 применена локально дважды.
Серверные изменения, коммит и выпуск не выполнялись.

## Поведение

- Приложение ограничивает весь `/api` до 10 запросов/с на IP, token bucket на
  20 запросов; проверка до JSON-парсера и БД, превышение возвращает JSON/429.
  Память общего ограничителя ограничена 10 000 IP; новые IP при заполнении получают
  429, пока не освободятся неактивные записи. Лимиты в памяти рассчитаны на один
  процесс, сбрасываются при перезапуске. Nginx дополнительно ограничивает вход в API.
- Проверка ссылки `/auth/verify`: 10 попыток за скользящую минуту с IP до БД.
- Подготовленный systemd drop-in: MemoryMax=384M, CPUQuota=100%, TasksMax=64.
  MemoryMax — жёсткая граница: при её превышении процесс может завершить OOM;
  действующая политика Restart службы должна быть проверена перед выпуском.
- Снимки training_batches и option_check_batches считаются совместно:
  1000 строк и 50 МиБ JSON на пользователя, 500 МиБ JSON на проект.
  Размер — `octet_length(jsonb::text)`, включая пробелы канонической сериализации
  PostgreSQL. Это не размер файлов БД, TOAST, индексов, WAL или резервных копий.
- Триггеры INSERT/UPDATE/DELETE и счётчики в `snapshot_storage_usage` обеспечивают
  атомарную проверку обеих таблиц. Глобальная строка сериализует изменения всех
  пользователей; нет сканирования всех снимков при каждой записи. Изменения
  счётчиков и снимка откатываются вместе. Каскадное удаление аккаунта уменьшает
  счётчики. Ручной TRUNCATE снимков обходит row-триггеры и требует пересчёта
  миграцией 145 в одной обслуживающей операции; приложение TRUNCATE не вызывает.
- Переполнение возвращает 429 с объяснением и доступностью прежней истории.
  Автоматического удаления нет. Если существующие данные превышают квоту,
  миграция сохраняет их; рост блокируется, уменьшение/удаление разрешены.
- Новые отказы ИИ сохраняют только метаданные: первые 100 за UTC-сутки на
  пользователя. После этого обновляется одна строка суточного счётчика.
  Принятые генерации, ошибки после начала генерации и их сообщения сохраняются
  по прежним правилам. Старые тексты отказов не удаляются.
- `ai_rejection_daily` каскадно удаляется с пользователем. Новый раздел отчёта
  `rejections_daily` отделяет полное число отказов от ограниченного подробного
  журнала; он не суммируется с подробными строками как дополнительные события.

Клиенты за одним NAT делят лимит IP. При расширении аудитории лимиты нужно
пересмотреть по измерениям. Лимиты снимков не ограничивают весь диск; продолжаются
контроль свободного места и резервное копирование.

## Подготовленные конфигурации

- `deploy/nginx/pg16-api-zone.conf`: подключение внутри `http {}`.
- `deploy/nginx/pg16-api-location.conf`: подключение в существующий location API
  только этого сайта. Существующие proxy_pass, заголовки, access/error logs и
  параметры соседних сайтов сохраняются. Nginx может вернуть собственное тело
  429; страница уже обрабатывает не-JSON ошибки запросов.
- `deploy/systemd/30-resource-limits.conf`: drop-in службы pg16-cert-prep.

Фрагмент nginx сам по себе не активирует защиту. При nginx burst=20 допускаются
20 избыточных запросов; общий bucket приложения строже и пропускает максимум
20 в одном мгновенном всплеске. Включать один и тот же zone дважды нельзя.

## Порядок будущего выпуска

1. Отдельное разрешение на коммит, затем на push/деплой и серверную миграцию.
2. До правок проверить чистоту git appuse, состояние приложения и соседних сайтов,
   параметры перезапуска службы. При грязном git остановиться.
3. Сделать закрытые резервные копии БД, текущих nginx/systemd-конфигураций и
   git-состояния; проверить архивы. Зафиксировать способ возврата к прежнему коду.
4. Доставить файлы исключительно git: fetch, посмотреть log/diff HEAD..origin/main,
   затем pull --ff-only. ИИ-шлюз не меняется.
5. До перезапуска выполнить `migrations/145_security_limits.sql` с окружением
   рабочей службы через штатный `src/config/db.js`; проверить и повторить.
   Проверить совпадение snapshot_storage_usage с count/sum обеих таблиц.
   Миграция ограничивает ожидание блокировки 3 с, выполнение команд 5 с: при
   превышении безопасно откатывается, увеличение сроков требует отдельной оценки.
6. Установить доставленные git файлы nginx и drop-in в системные каталоги;
   подключить nginx-фрагменты только к этому сайту. Проверить nginx -t и конфигурацию
   systemd до применения. Конфиги и соседние сайты менять только после backup.
7. После успешных проверок daemon-reload, перезапуск только pg16-cert-prep
   (меняется серверный код), reload nginx. Проверить effective лимиты, вход,
   создание/чтение тренировок и ИИ, соседние сайты. Нагрузочные тесты production
   не выполнять как часть обычного выпуска.

Для отката вернуть прежний git-коммит и конфигурации после отдельного согласования.
Старый код совместим с дополнительными таблицами; триггеры квот продолжают действовать,
пока не выполнен отдельно согласованный откат ограничения. Суточные метаданные и
старые снимки не удалять для отката. Полная замена БД из backup потеряет новые данные,
поэтому не является обычным первым шагом отката.
