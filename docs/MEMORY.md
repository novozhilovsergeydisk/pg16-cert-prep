# Память процесса: материал для изучения

Этот материал к разделу «18. Память процесса». Он для тех, кто не работает системным администратором: все понятия объясняются с нуля, команды можно выполнять на своём сервере и сразу видеть результат. Вопросы раздела проверяют то, что здесь разобрано.

Ориентир везде один: Linux x86-64 (Debian, Ubuntu) и PostgreSQL 16. В macOS многое устроено иначе: там нет каталога `/proc`, нет systemd и cgroup, а размер страницы на процессорах Apple Silicon равен 16 КБ.

## Как пользоваться материалом

- Читайте по порядку: каждая тема опирается на предыдущую.
- Команды наблюдения только читают и не меняют ни настроек, ни данных. Выполнять их можно на рабочем сервере под своим пользователем или под root для просмотра. Исключение — пример на C в шаге 10 практикума: это лабораторный опыт для учебной среды.
- Фраза «PID» в командах обозначает номер процесса. Это не настоящий каталог: вместо `PID` подставляется число, например `1234`. Как узнать номер, описано в разделе про `/proc`.
- Файлы `/proc/PID/environ` и `/proc/PID/cmdline` чужих процессов не показывайте и не вставляйте в чат или письма: в них бывают пароли, токены и пути.
- В конце есть практикум по шагам и словарь терминов.

## 1. Что такое процесс

Программа на диске — это просто файл. Когда её запускают, операционная система создаёт процесс: работающий экземпляр программы со своими данными. У каждого процесса есть номер (PID, process identifier), по которому его можно найти.

Процесс не видит чужую память. Представьте многоквартирный дом: у каждого процесса своя квартира, и попасть в соседнюю нельзя. Если процессов запущено много, у каждого своя изолированная «квартира» памяти. Это защищает их друг от друга: сбой одного не портит приватную память другого. Исключение — общая память, которую процессы подключают намеренно; о ней речь пойдёт ниже.

PostgreSQL построен именно так: главный процесс `postmaster` создаёт отдельный процесс на каждое клиентское подключение и несколько фоновых процессов. Поэтому в списке процессов сервера вы видите десятки строк `postgres`.

Один процесс может состоять из нескольких потоков, которые работают внутри общей «квартиры». PostgreSQL потоки не использует: у его процессов поле `Threads` в `/proc/PID/status` равно 1.

## 2. Виртуальная память и страницы

Процесс не работает с настоящими адресами оперативной памяти. Каждому процессу операционная система показывает виртуальное адресное пространство: длинную ленту адресов, которая начинается как будто с нуля. На x86-64 в обычной конфигурации оно огромно, до 128 терабайт. Реальной оперативной памяти столько нет, и она не нужна: не каждому виртуальному адресу соответствует физическая страница, она появляется только там, где процесс действительно пользуется памятью.

Перевод виртуального адреса в настоящий делает процессор по таблицам страниц, которые ведёт ядро операционной системы. Для каждого процесса таблица своя. Поэтому одинаковые числовые адреса в двух процессах обычно указывают на разные физические страницы. Одну и ту же страницу процессы делят, только когда память общая: общая память, код библиотек, страницы после `fork` до первой записи. Само совпадение адресов доступа к чужой приватной памяти не даёт.

Память делится на кусочки одинакового размера — страницы. В Linux на x86-64 страница обычно равна 4 КБ. Не путайте со страницей данных PostgreSQL: она другая, 8 КБ, и это блок в файлах таблиц.

Из страниц складываются все решения ядра:

- страница может быть выдана процессу не сразу, а при первом обращении к ней;
- страница может быть отображена из файла (например, код программы);
- страницу, которой давно не пользовались, ядро может выгрузить в своп (область на диске) и вернуть при следующем обращении.

Последний пункт важен. Если страницу приходится возвращать с дискового устройства свопа, это в тысячи раз медленнее обращения к оперативной памяти. Если таких обращений много, процессы почти всё время ждут диска, и тормозит весь сервер. Бывает и своп в сжатом виде в самой оперативной памяти (zswap): возврат оттуда быстрее, но тоже не бесплатен.

## 3. Из чего состоит память процесса

Виртуальное адресное пространство процесса состоит из областей. Если нарисовать его вертикально, с малыми адресами внизу:

```
верх (большие адреса)
  начальный стек: сверху лежат строки окружения и аргументы
  стек                    растёт вниз
  ... свободное место, отображения файлов и библиотек ...
  куча                    растёт вверх
  данные программы (глобальные переменные)
  код программы
низ (малые адреса)
```

- Код — машинные инструкции. Его можно читать и выполнять, но нельзя записывать.
- Данные — глобальные и статические переменные. Живут всё время работы программы.
- Куча — память, которую программа запрашивает сама, когда нужно.
- Стек — временная память для вызовов функций.
- Окружение и аргументы — строки, которые операционная система кладёт в самый верх начального стека при запуске: переменные окружения (`PATH=...`, `PGDATA=...`) и аргументы командной строки.
- Отображения файлов и библиотек — например, стандартная библиотека C `libc.so.6`, которая нужна почти всем программам.

Это типичная упрощённая схема: конкретная карта зависит от программы и способа её загрузки. Адреса многих областей при каждом запуске перемешиваются: это защита от атак, она называется ASLR.

## 4. Стек

Стек — это стопка тарелок. Когда программа вызывает функцию, в стек кладётся «тарелка» (кадр): место под локальные переменные этой функции и адрес, куда вернуться после её завершения. Функция закончилась — кадр снимается, место освобождено. Всё происходит автоматически и очень быстро: это просто сдвиг одного указателя.

Особенности стека:

- он растёт в сторону меньших адресов;
- размер ограничен, обычно 8 МБ (команда `ulimit -s` покажет лимит в килобайтах);
- данные в нём живут только пока работает функция;
- если функции вызывают друг друга слишком глубоко (например, рекурсия без конца), стек кончается, и процесс аварийно завершается.

Не операционная система решает, когда создавать кадры: правила встроил компилятор, а исполняет их процессор. Ядро создаёт начальную область стека при запуске и может расширять её по мере обращений, проверяя лимит. Физические страницы стека, как и остальной памяти, выдаются по требованию.

PostgreSQL проверяет глубину стека сам: параметр `max_stack_depth` (по умолчанию 2 МБ) позволяет серверу в проверяемых местах прервать запрос с ошибкой «stack depth limit exceeded» раньше, чем процесс упадёт. Защиты от любой рекурсии он не гарантирует, например внутри стороннего расширения. Значение параметра должно быть меньше лимита стека самого серверного процесса с запасом около мегабайта. Этот лимит смотрят в `/proc/PID/limits` главного процесса: `ulimit -s` в вашем терминале показывает лимит оболочки, а у службы он может быть другим.

## 5. Куча

Куча — это склад. Когда программе нужна память, размер которой заранее неизвестен или которая должна жить дольше одной функции, она просит её у склада. В языке C это вызов `malloc`, а возвращает память вызов `free`. PostgreSQL написан на C, но обычно выделяет память не напрямую, а своей функцией `palloc` в контекстах памяти (о них ниже).

```
char *buf = malloc(1024);   /* получили блок в куче */
/* ... работаем с buf ... */
free(buf);                  /* вернули блок */
```

Особенности кучи:

- память остаётся занятой, пока программа сама не вызовет `free`;
- куча намного больше стека, она может расти до пределов доступной памяти;
- работать с кучей медленнее, чем со стеком;
- ошибки: если ненужный блок не освободить и потерять его адрес, получится утечка; когда такие выделения повторяются, расход памяти растёт; если вызвать `free` дважды, поведение не определено, обычно процесс аварийно завершается;
- кучу выдаёт библиотека, а не ядро: она запрашивает у ядра крупные куски и сама нарезает их на блоки. Небольшие блоки обычно лежат в области `[heap]`, а большие библиотека может запросить отдельным отображением.

Время создания кучи отличается от стека: куча растёт по мере запросов программы и библиотек, причём часть выделений случается ещё до начала функции `main`. Для новых областей физические страницы обычно выдаются по требованию, а `malloc` может вернуть и ранее освобождённый блок, который уже лежит в памяти.

В PostgreSQL память под сортировку, хеширование и разобранные запросы обычно выделяется в куче обслуживающего процесса через `palloc`, в контекстах памяти. Когда контекст сбрасывают или удаляют, освобождаются сразу все выделения в нём. Это упрощает очистку, но не исключает утечек: есть долгоживущие контексты, которые существуют всё время сеанса. Некоторые параллельные операции, например Parallel Hash, используют не локальную, а общую память.

## 6. Чем стек отличается от кучи

- Кто управляет. Стеком управляет сама программа автоматически при входе в функцию и выходе из неё. Кучей управляет программа явно: просит блок и сама возвращает.
- Сколько живут данные. В стеке — пока работает функция. В куче — пока их не освободят.
- Размер. Стек маленький (обычно 8 МБ), куча большая.
- Скорость. Стек быстрее.
- Типичная ошибка. Для стека — переполнение (слишком глубокая рекурсия). Для кучи — утечка памяти.
- Что где лежит. В стеке: локальные переменные, адреса возврата. В куче: данные, размер или срок жизни которых неизвестен заранее.

Пример на C показывает оба вида в одном коде. Это фрагмент программы, в которой подключён заголовок `stdlib.h`. Размещение переменных в стеке описано для обычной сборки без оптимизации (`-O0`): с оптимизацией компилятор может держать переменные в регистрах или вовсе убрать неиспользуемые.

```
#include <stdlib.h>

int counter = 0;                   /* глобальная переменная: область данных */

void work(void)
{
    int n = 5;                     /* локальная переменная: стек */
    char *buf = malloc(100);       /* блок в куче; сам указатель buf лежит в стеке */
}
```

При выходе из `work` кадр снимается, и переменная `n` и указатель `buf` исчезают. А блок в 100 байт, если `malloc` его выделил, а `free` не вызван, остаётся в куче: это утечка. Поэтому из функции нельзя возвращать адрес локальной переменной: её кадр уже снят.

Готовая программа со всеми этими наблюдениями лежит в проекте: `examples/stack-heap.c`. Она печатает адреса областей, показывает рост стека и переполнение. Как её запускать, описано в шаге 10 практикума.

## 7. Каталог /proc

### 7.1. Что это такое

`/proc` — это не настоящий каталог на диске. Ядро показывает через него своё внутреннее состояние в виде файлов и каталогов: какие процессы запущены, сколько у них памяти, какие настройки у ядра. Содержимое файлов формируется в момент чтения. Поэтому у многих из них команда `ls` показывает размер 0, хотя при чтении данные есть. Размер и дата в выводе `ls` не говорят ни об объёме, ни о свежести этих данных.

Читать их можно обычными командами: `cat`, `grep`, `less`, `awk`. Большинство файлов только для чтения. Но в `/proc` есть и интерфейсы управления: запись в некоторые файлы меняет настройки ядра (`/proc/sys`) или состояние процесса (например, `/proc/PID/oom_score_adj`). В этом материале используются только команды чтения.

### 7.2. Два вида содержимого

- Каталоги с числовыми именами (`/proc/1`, `/proc/877`, `/proc/1234`): по одному на каждый работающий процесс. Число — это номер процесса (PID). Когда процесс завершается, каталог исчезает.
- Общие файлы и каталоги о системе в целом: `/proc/meminfo` (память системы), `/proc/cpuinfo` (процессоры), `/proc/loadavg` (нагрузка), `/proc/uptime` (время работы), `/proc/sys` (настройки ядра).

### 7.3. Специальные имена

- `/proc/self` — ссылка на процесс, который сейчас читает каталог. Если вы запустите `ls -la /proc/self`, то увидите номер самого `ls`; при повторном запуске он будет другим.
- `/proc/$$` — каталог вашей оболочки. `$$` — это специальная переменная оболочки: её номер процесса.
- `/proc/thread-self` — то же для текущего потока.

Как узнать номер чужого процесса:

```
pgrep -u postgres -n postgres          # номер самого нового процесса postgres
head -1 /var/lib/postgresql/16/main/postmaster.pid   # номер главного процесса PostgreSQL 16
P=$(head -1 /var/lib/postgresql/16/main/postmaster.pid)
ps -o pid,comm -p $P              # главный процесс: только имя, без аргументов
ps -o pid,ppid,cmd --ppid $P      # непосредственные дочерние процессы: их заголовки
```

Первая строка файла `postmaster.pid` — это номер главного процесса кластера. Остальные строки этого файла выводить не нужно. Читать файл может пользователь `postgres` или root.

Команды `ps` здесь выбирают только главный процесс и его непосредственные дочерние процессы. Так в вывод не попадут другие программы пользователя `postgres`: в их аргументах могут оказаться секреты.

У главного процесса выводится только имя (`comm`), без аргументов запуска: в них тоже может оказаться секрет, например строка подключения `primary_conninfo` с паролем. Дочерние процессы при запуске записывают поверх исходных аргументов свой заголовок, поэтому их `cmd` показывает «checkpointer» или «пользователь база адрес idle», а не аргументы главного процесса. Такие заголовки обычно не содержат секретов, но в них есть имена пользователей, баз и адреса клиентов. Перед тем как показывать вывод другим, просмотрите его сами.

### 7.4. Что внутри каталога процесса

- `status` — основные сведения в читаемом виде: состояние, память (`VmSize`, `VmRSS`, `VmSwap`), число потоков (`Threads`). Начинать лучше с него.
- `maps` — карта виртуальной памяти: какие области есть, какие у них права, из какого файла.
- `smaps` и `smaps_rollup` — подробные размеры для каждой области и итог. В них есть показатель PSS, который честно делит общие страницы между процессами.
- `cmdline` — как был запущен процесс: аргументы командной строки (разделены нулевыми байтами). Могут содержать секреты.
- `environ` — исходная область окружения процесса, обычно то, с чем он был запущен; программа может перезаписать её содержимое. Доступ ограничен проверками прав: как правило, читать файл может только владелец процесса и root. Могут быть пароли и токены.
- `limits` — лимиты процесса: размер стека, число открытых файлов и другие. У каждого лимита два значения: мягкий (Soft Limit) — действующее ограничение, и жёсткий (Hard Limit) — потолок, до которого процесс может поднять мягкий без особых прав. Это не то же самое, что пороги `MemoryHigh` и `MemoryMax` служб systemd (раздел 10).
- `fd` — каталог открытых процессом файлов. Имя каждой записи — номер файлового дескриптора (0 — стандартный ввод, 1 — вывод, 2 — вывод ошибок), а сама запись — символьная ссылка на файл, сокет или канал. `ls -l /proc/PID/fd` покажет, куда ведут ссылки, а `ls /proc/PID/fd | wc -l` — сколько их. Число записей помогает оценить, сколько дескрипторов занято. Мягкий лимит `Max open files` в `limits` ограничивает номер нового дескриптора: он должен быть меньше лимита. Если свободного номера в этом диапазоне нет, открыть файл или создать подключение не удаётся (ошибка «Too many open files»).
- `stat` — те же сведения в компактном виде (для программ).
- `cgroup` — к какой группе управления ресурсами относится процесс (например, к какой службе systemd).
- `oom_score` и `oom_score_adj` — насколько процесс подходит для завершения при нехватке памяти и поправка к этой оценке.
- `io` — сколько данных процесс прочитал и записал (нужны права).

### 7.5. Права доступа

Часть файлов может читать только владелец процесса или root. Особенно ограничены `environ` и `io`. При монтировании `/proc` можно включить параметр `hidepid`, и тогда пользователь видит только свои процессы. Если команда отвечает «Permission denied» или «No such file», это обычно значит одно из двух: нет прав, или процесс уже завершился.

### 7.6. Файл всегда «снимок»

Содержимое `/proc` отражает состояние в момент чтения. Через секунду значения изменятся. Поэтому для наблюдения за памятью читают файл несколько раз или используют команды вроде `watch`. `/proc` не заменяет `ps`, `top` и `free`: эти программы берут сведения у ядра, в том числе из `/proc`, и показывают их удобнее. Но по `/proc` видно, откуда берутся их числа. Представление `pg_stat_activity` устроено иначе: оно показывает внутреннее состояние сеансов PostgreSQL и дополняет наблюдения средствами Linux.

### 7.7. Настройки ядра в /proc/sys

Каталог `/proc/sys` содержит настройки ядра. Читать их можно любому, менять — только root, и изменения действуют до перезагрузки (чтобы они остались, их записывают в `/etc/sysctl.d/`). Удобнее работать командой `sysctl`:

```
sysctl vm.swappiness                  # насколько охотно ядро использует своп
sysctl vm.overcommit_memory           # режим выдачи памяти (0, 1 или 2)
cat /proc/sys/kernel/randomize_va_space   # включена ли рандомизация адресов (ASLR)
```

### 7.8. Общие файлы о системе

- `/proc/meminfo` — память системы. Главные поля: `MemTotal` (всего), `MemFree` (совсем свободно), `MemAvailable` (сколько можно выделить без вытеснения в своп; на это значение и смотрят), `SwapTotal` и `SwapFree` (своп). Команда `free -m` показывает те же числа.
- `/proc/loadavg` — три числа средней нагрузки за 1, 5 и 15 минут. Команда `uptime` показывает их же.
- `/proc/uptime` — время работы системы.

## 8. Как читать /proc/PID/status

Три поля о памяти нужно уметь различать:

- `VmSize` — размер виртуального адресного пространства: все отображённые области, независимо от того, лежат их страницы в оперативной памяти или нет. Поэтому большой `VmSize` не означает такого же расхода оперативной памяти.
- `VmRSS` (resident set size) — страницы процесса, которые сейчас находятся в оперативной памяти. Сюда входят и общие страницы, к которым процесс обращался. Это приблизительный счётчик.
- `VmSwap` — приватная анонимная память процесса, которая сейчас выгружена в своп. Своп общей памяти сюда не входит.

Пример у вас на экране:

```
VmSize:   439220 kB    зарезервировано около 429 МБ адресов
VmRSS:     14864 kB    в оперативной памяти около 14,5 МБ
VmSwap:     1072 kB    около 1 МБ выгружено в своп
Threads:       1       один поток
```

Что из этого следует:

- Большой `VmSize` сам по себе не признак проблемы и не признак утечки: адреса резервируются заранее, файлы отображаются целиком.
- Реальный расход оперативной памяти смотрят по `VmRSS`. Но и он неточен для общей памяти: одни и те же общие страницы учитываются в RSS каждого процесса, который к ним обращался. Поэтому простая сумма RSS процессов PostgreSQL обычно завышает расход. Точнее считает PSS в `/proc/PID/smaps_rollup`: он делит учитываемые общие страницы между процессами. Отдельно учитывается память HugeTLB (большие страницы, выделенные заранее), которую PostgreSQL может использовать для общей области: она не входит ни в RSS, ни в PSS, её показывает поле `HugetlbPages` в `status`. Это относится именно к HugeTLB, а не ко всем видам больших страниц.
- Ненулевой `VmSwap` не значит, что процесс сейчас обращается к свопу, а его рост не доказывает нехватку памяти всей системы: причиной может быть, например, лимит службы. Для диагностики смотрят ещё обмен со свопом и давление на память. В выводе `vmstat 1` столбец `si` показывает, сколько данных в секунду возвращается из свопа, а `so` — сколько уходит в своп. Первая строка `vmstat` — средние значения с запуска системы, смотреть нужно следующие. Давление на память (`cat /proc/pressure/memory`) показывает, какую долю времени задачи задерживались из-за нехватки памяти.
- Ни большой `VmSize`, ни рост `VmRSS` сами по себе утечку не доказывают: память растёт и от кеширования, и от нагрузки, а библиотека может удерживать освобождённые блоки. Подозрение вызывает устойчивый рост удерживаемой памяти при сопоставимой нагрузке; причину ищут по выделениям памяти, в PostgreSQL — по контекстам памяти.

Поле `State` в `status` показывает, что делает процесс: `R` выполняется или готов к выполнению, `S` ждёт события (прерываемое ожидание), `D` непрерываемое ожидание, чаще всего ввода-вывода, `Z` завершился, но его ещё не «подобрал» родитель. Процесс долго в состоянии `D` — повод проверить диск и своп, но по одному состоянию нельзя определить, чего именно он ждёт.

## 9. Как читать /proc/PID/maps

Каждая строка файла `maps` описывает одну область виртуальной памяти процесса:

```
563be3386000-563be338b000  r-xp  00002000  fe:01  1761  /usr/bin/cat
 диапазон адресов         права  смещение  устр-во inode  файл
```

- Диапазон адресов — начало и конец области в шестнадцатеричной системе. Это виртуальные адреса. Начальный адрес входит в область, конечный — уже нет, поэтому размер области в байтах равен разности конца и начала. Например, `echo $((0x563be338b000 - 0x563be3386000))` даст 20480 байт, то есть 5 страниц по 4 КБ. Чтобы получить мегабайты, разделите результат на 1048576.
- Права: четыре символа. `r` чтение, `w` запись, `x` выполнение, и последний — `p` (приватная область: при записи страница копируется) или `s` (общая область: изменения видят все, кто её отобразил).
- Смещение (тоже в шестнадцатеричной системе), устройство и inode (номер файла внутри файловой системы) — какой участок какого файла отображён. Для областей без файла стоят нули (`00:00`, inode `0`).
- Последняя колонка — имя файла или служебная подпись: `[heap]` (куча), `[stack]` (стек), `[vdso]` и другие. Пустая колонка означает анонимную область без файла.

Как это читать на практике:

- `r-xp` с именем программы или библиотеки — машинный код: читается и выполняется, не записывается.
- `rw-p` с `[heap]` — куча, `rw-p` с `[stack]` — стек.
- `rw-p` без имени — анонимная память, например большие блоки `malloc`.
- `rw-s` — разделяемая область с чтением и записью. У PostgreSQL основная общая область содержит `shared_buffers` и другие общие структуры, но одного признака `rw-s` мало, чтобы определить назначение области: таких областей у сервера может быть несколько.
- Файл может быть отображён в адреса целиком, хотя процесс читает из него немного. Например, файл `locale-archive` занимает в карте около 232 МБ адресов, а процессу из них нужны единицы мегабайт: страницы попадают в оперативную память не все сразу, а по мере обращения. Ядро может прочитать часть страниц заранее (упреждающее чтение), а часть может уже лежать в кеше, потому что к файлу обращались другие процессы.
- Код библиотеки `libc.so.6` разные процессы отображают из одного файла: неизменённые страницы лежат в оперативной памяти один раз и разделяются между процессами.

## 10. Linux и память: что полезно знать

### Выдача памяти по требованию

Когда программа запрашивает новую память, ядро обычно сначала выдаёт только адреса. Настоящие страницы оперативной памяти появляются при первой записи в них. Поэтому `malloc` на гигабайт может завершиться успешно, даже если свободной оперативной памяти меньше, а `VmRSS` процесса вырастет только по мере записи. Эту схему называют выделением по требованию.

Отдельный вопрос: разрешать ли ядру выдавать обещания сверх реальных ресурсов. Это настраивается параметром `vm.overcommit_memory`. Документация PostgreSQL советует на выделенном сервере БД значение 2 (строгий учёт). Оно снижает вероятность попасть под OOM killer из-за чрезмерных обещаний памяти, но не исключает его, в частности при лимите памяти службы.

### Своп

Своп — область на диске для страниц, которые не помещаются в оперативную память. Он позволяет пережить временную нехватку, но если страницы постоянно ходят между памятью и диском, система почти встаёт. Параметр `vm.swappiness` определяет, насколько охотно ядро выгружает страницы (на серверах баз данных обычно небольшое значение).

### OOM killer

Если памяти совсем не хватает, ядро запускает OOM killer. Он выбирает процесс-жертву, учитывая занятую память и поправку `oom_score_adj`, и завершает его сигналом `SIGKILL`. Если памяти не хватило внутри группы управления ресурсами (например, службы с лимитом), жертва выбирается только среди процессов этой группы. Документация PostgreSQL советует защищать главный процесс `postmaster` поправкой `oom_score_adj`, но так, чтобы дочерние процессы оставались возможными жертвами. По умолчанию они наследуют поправку родителя, поэтому для них её сбрасывают переменными окружения `PG_OOM_ADJUST_FILE` и `PG_OOM_ADJUST_VALUE`.

Аварийно завершённый обслуживающий процесс мог повредить общую память. Поэтому `postmaster` завершает остальные процессы, подключённые к ней, и, если включён параметр `restart_after_crash` (по умолчанию включён), запускает восстановление после сбоя.

### Лимиты служб systemd

Служба, запущенная под systemd, может иметь ограничения на память (в современных системах они работают через cgroup v2):

- `MemoryHigh` — мягкий порог: выше него ядро притормаживает процессы службы и пытается освободить их память: освобождает страницы файлового кеша, а если своп есть и разрешён, может вытеснять туда анонимные страницы;
- `MemoryMax` — жёсткий предел оперативной памяти;
- `MemorySwapMax` — предел свопа; `0` запрещает своп службе.

Живой пример. На сервере, где работала эта подготовка, служба расшифровки речи долго держала процесс, которому нужно было около 3,6 ГБ при лимите `MemoryMax=2G` и неограниченном свопе. Почти вся память и своп оказались заняты, процесс почти всё время ждал диска (состояние `D`), а остальные службы, в том числе база данных, начали тормозить. Решение для этой конкретной нагрузки: запретить службе своп (`MemorySwapMax=0`) и убрать мягкий порог `MemoryHigh`. Теперь анонимные страницы службы больше не уходят в своп, и при нехватке памяти внутри лимита срабатывает OOM killer этой службы вместо долгого торможения всего сервера. Мгновенного завершения это не гарантирует: у предела `MemoryMax` ядро тоже сначала пытается освободить память, например файловый кеш.

Универсальным рецептом это не является. Обычно `MemoryHigh` — основной механизм ограничения, а `MemoryMax` — последняя защита; значения подбирают по нагрузке. Ограничения действуют на всю службу, а не на отдельный процесс.

### fork и копирование при записи

Новый процесс в Linux создаётся вызовом `fork`: дочерний процесс получает копию адресного пространства родителя. Копируется не сразу: страницы остаются общими, пока один из процессов не запишет в страницу. Тогда ядро делает ей отдельную копию. Это называется копированием при записи. Поэтому `fork` быстрый, даже если у родителя много памяти. Общие (разделяемые) отображения остаются общими.

## 11. Память PostgreSQL

### Процессы

Главный процесс `postmaster` принимает подключения и порождает остальные. Для каждого клиентского подключения создаётся отдельный обслуживающий процесс. Кроме них работают постоянные фоновые процессы: `checkpointer`, `background writer`, `walwriter`, `autovacuum launcher`, а на реплике — `startup`, который применяет журнал. Посмотреть главный процесс и его непосредственные дочерние процессы можно так (почему именно так, объяснено в разделе 7.3):

```
P=$(head -1 /var/lib/postgresql/16/main/postmaster.pid)
ps -o pid,comm -p $P              # главный процесс: только имя, без аргументов
ps -o pid,ppid,cmd --ppid $P      # непосредственные дочерние процессы: их заголовки
```

Заголовок процесса в `ps` PostgreSQL обновляет сам (параметр `update_process_title`): по нему видно пользователя, базу, адрес клиента и состояние. Чтобы освободить место под этот заголовок, сервер при старте копирует свои переменные окружения в кучу. Сам перенос исходную область не стирает, но процессы, которые меняют свой заголовок, записывают его поверх неё. Поэтому `/proc/PID/environ` у таких процессов PostgreSQL не показывает настоящего окружения.

### Общая память

Часть памяти выделяется при запуске сервера как разделяемая и подключается ко всем процессам:

- буферный кеш (`shared_buffers`) — кеш страниц таблиц и индексов;
- буферы журнала предзаписи и статусов транзакций;
- таблица блокировок и другие общие структуры.

Размер этой области больше `shared_buffers`, потому что в неё входят и остальные структуры; разница зависит от других настроек, например `max_connections` и `wal_buffers`. Дополнительно во время работы могут выделяться сегменты динамической общей памяти, например для параллельных запросов.

В `/proc/PID/maps` общие области выглядят как строки с правами `rw-s`; основная из них обычно самая большая:

```
grep rw-s /proc/PID/maps
```

### Локальная память

У каждого обслуживающего процесса есть собственная, приватная память:

- кеш системного каталога;
- разобранные запросы и состояние курсоров;
- память для сортировок и хеширования, ограниченная параметром `work_mem`.

`work_mem` — это лимит не на запрос, а на каждую операцию сортировки или хеширования в плане, причём для хеш-операций он умножается на `hash_mem_multiplier` (по умолчанию 2). В плане несколько таких операций, а запросов выполняется много, поэтому слишком большое значение при многих подключениях может увести сервер в своп или под OOM killer.

### Что полезно проверить

- Посмотреть `shared_buffers` и размер общей области: `SHOW shared_buffers;` и `grep rw-s /proc/PID/maps`.
- Посмотреть память обслуживающего процесса: `SELECT pg_backend_pid();` и затем `grep -E 'VmRSS|VmSwap' /proc/PID/status`.
- Не складывать `VmRSS` процессов PostgreSQL: общая память посчитана в каждом из них.

Переменная окружения `PGPASSWORD` небезопасна именно потому, что окружение процесса можно прочитать через `/proc`. Лучше хранить пароль в файле `.pgpass` в домашнем каталоге того пользователя ОС, который запускает клиент (`psql`, `pg_dump`). Права `0600` у этого файла означают: читать и менять его может только владелец, у группы и остальных пользователей доступа нет.

echo $$                       # номер вашей оболочки
ls -la /proc/$$ | head        # у многих файлов размер 0, хотя данные в них есть

Шаг 4. Карта памяти:

```
cat /proc/$$/maps
grep -E '\[heap\]|\[stack\]' /proc/$$/maps
```

Обе команды показывают карту вашей оболочки. Найдите код программы (`r-xp` с `/usr/bin/bash`), кучу (`[heap]`), библиотеки и стек. Стек ищите по подписи `[stack]`, а не по наибольшему адресу: выше него бывает служебная область `[vsyscall]`.

Шаг 5. Память и нагрузка системы:

```
grep -E 'MemTotal|MemAvailable|SwapTotal|SwapFree' /proc/meminfo
free -m
cat /proc/loadavg
```

Шаг 6. Лимиты и открытые файлы процесса:

```
grep -E 'stack|open files' /proc/$$/limits
ls -l /proc/$$/fd
ls /proc/$$/fd | wc -l
```

В `limits` два столбца значений: мягкий и жёсткий лимит. Число записей в `fd` показывает, сколько дескрипторов занято; сравните его с мягким лимитом `Max open files`.

Шаг 7. Главный процесс PostgreSQL и его непосредственные дочерние процессы:

```
P=$(head -1 /var/lib/postgresql/16/main/postmaster.pid)
echo $P
ps -o pid,comm -p $P              # главный процесс: только имя, без аргументов
ps -o pid,ppid,cmd --ppid $P      # непосредственные дочерние процессы: их заголовки
```

Шаг 8. Общая память PostgreSQL (подставьте номер из шага 7 вместо PID):

```
grep -E 'VmSize|VmRSS|VmSwap|Threads' /proc/PID/status
grep rw-s /proc/PID/maps
```

В `maps` найдите строки `rw-s`: это разделяемые области. Посчитайте размер самой большой по способу из раздела 9 и сравните с результатом `SHOW shared_buffers;` в `psql`: область больше, а разница зависит от остальных настроек.

Шаг 9. Память серверного процесса, который обслуживает ваше подключение (не самого `psql`). Опыт рассчитан на `psql`, запущенный на том же сервере Linux, что и PostgreSQL, с правом читать `status` этого процесса:

sudo -u postgres psql -p 5432
SELECT pg_backend_pid() AS pid \gset
\setenv MYPID :pid
\! grep -E 'VmRSS|VmSwap' /proc/$MYPID/status

```
cc -O0 -Wall -o /tmp/stack-heap examples/stack-heap.c && /tmp/stack-heap
```

Программа напечатает адреса областей и покажет переполнение стека в отдельном процессе.

## 13. Словарь терминов

- Процесс — работающий экземпляр программы со своей изолированной памятью.
- PID — номер процесса.
- Поток — часть процесса, работающая в его общей памяти.
- Виртуальный адрес — адрес, с которым работает программа; ядро и процессор переводят его в физический.
- Страница — кусок памяти фиксированного размера (в Linux на x86-64 обычно 4 КБ), единица, которой ведёт учёт ядро.
- Таблица страниц — таблица перевода виртуальных адресов в физические, у каждого процесса своя.
- Своп — область на диске, куда ядро выгружает страницы из оперативной памяти.
- Стек — автоматическая память для вызовов функций, обычно до 8 МБ.
- Кадр стека — часть стека одной вызванной функции.
- Куча — память, которую программа запрашивает и возвращает сама (`malloc` и `free`).
- Утечка памяти — блок в куче, который больше не нужен, но не возвращён.
- ASLR — перемешивание адресов областей памяти при каждом запуске ради защиты.
- `/proc` — псевдо-каталог ядра с состоянием системы и процессов.
- `self` — ссылка на процесс, который читает каталог `/proc`.
- Файловый дескриптор — номер открытого процессом файла; их список — в `/proc/PID/fd`.
- RSS — страницы процесса, находящиеся в оперативной памяти.
- PSS — RSS, в котором общие страницы поделены поровну между пользующимися ими процессами.
- Общая память — память, подключённая сразу к нескольким процессам.
- Копирование при записи (COW) — страницы остаются общими, пока в них не запишет один из процессов.
- `fork` — вызов, создающий дочерний процесс с копией памяти родителя.
- `postmaster` — главный процесс PostgreSQL, порождающий остальные.
- `shared_buffers` — размер общего буферного кеша PostgreSQL.
- `work_mem` — лимит памяти на одну операцию сортировки или хеширования.
- OOM killer — механизм ядра, завершающий процесс при нехватке памяти.
- cgroup — механизм ядра для ограничения ресурсов групп процессов; через него работают лимиты служб systemd.
- `MemoryHigh`, `MemoryMax`, `MemorySwapMax` — мягкий порог, жёсткий предел памяти и предел свопа службы systemd.
