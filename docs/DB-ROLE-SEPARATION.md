# Разделение ролей БД — план второго этапа

Я подготовил матрицу прав, проверил её с реальным кодом приложения на изолированном
PostgreSQL и проверил возврат владения. Учёт: задача 235, замечание SEC-08.
Матрица согласована пользователем. Административный runner и миграция 146
реализованы и проверены на изолированной PostgreSQL 16.14, затем выпущены на appuse
12 ноября 2026: код `78e8468`. Применение, повтор и READ ONLY verify прошли;
runtime больше не владеет БД и её объектами. Приложение не перезапускалось.
Отчёт: [выпуск разделения ролей](reviews/2026-11-12-security-audit/role-separation-release.md).
Основная локальная БД не подвергалась разделению ролей.

## Исходное состояние

12 ноября 2026 на appuse, код `f9ca989`, PostgreSQL 16.14:

- Текущая роль приложения владеет этой базой, 16 таблицами и 11 последовательностями.
  Она не superuser, не имеет CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS и членств
  в других ролях. Других принадлежащих ей БД и табличных пространств не обнаружено:
  всего одна принадлежащая БД и ноль ТП.
- `public` не принадлежит runtime непосредственно, но роль может создавать в ней
  объекты благодаря владению БД. У PUBLIC права CREATE в public нет.
- `enforce_snapshot_storage_quota()` принадлежит runtime и работает как SECURITY
  INVOKER. Простое лишение приложения прав на таблицу счётчиков сломает вставки.
- Автоматический `/usr/local/bin/pg16-cert-backup.sh` выполняет pg_dump от ОС-пользователя
  postgres, не загружает .env приложения и не зависит от runtime-роли. Его менять
  этим этапом не предлагаю; успешность копии после перехода всё равно проверяется.
- Проверка production выполнялась только чтением метаданных в READ ONLY.
  Секреты, имена пользователей/баз подключения и персональные записи не выводились.

## Предлагаемая схема

1. Сохранить текущую LOGIN-роль и её реквизиты как runtime. Приложение продолжает
   подключаться тем же способом; смена пароля и .env не нужна.
2. Создать отдельную `pg16_owner` с NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE,
   NOREPLICATION, NOBYPASSRLS. Она владеет только БД/объектами этого проекта.
   До создания проверить отсутствие совпадения с существующей чужой ролью.
3. Миграции выполнять через доверенный административный доступ ОС postgres,
   отдельное соединение и явный `SET ROLE pg16_owner`; соединение закрывать
   после миграции. Новый пароль и отдельный сетевой LOGIN мигратора не нужны.
   Runtime не получает членства в pg16_owner и права SET ROLE к ней.
4. Передать владельцу саму БД, public и согласованный перечень таблиц,
   связанных последовательностей и функции квот. Использовать адресные ALTER
   OWNER, а не REASSIGN OWNED/DROP OWNED. Объекты расширения pgcrypto,
   принадлежащие администратору, не передавать и не менять.
5. Убрать CREATE и TEMPORARY у PUBLIC только в целевой БД; оставить CONNECT/USAGE
   там, где они нужны приложению. Перед этим сохранить ACL и проверить, нет ли
   других законных пользователей этой БД, которым потребуется отдельный TEMP.
   В соседних БД/схемах и в общих атрибутах существующих ролей ничего не менять.
6. Выдать только указанную ниже матрицу. Новым таблицам/функциям владельца не
   выдавать runtime права автоматически: последующая миграция должна содержать
   адресный GRANT и проверки соответствующей функции приложения.

## Матрица runtime

SELECT означает чтение таблицы. INSERT/UPDATE выдаются на перечисленные столбцы,
а не на всю таблицу. DELETE допускает удаление любых строк указанной таблицы:
условие «только просроченные» остаётся в серверном SQL и не является отдельной
гарантией GRANT. Прав TRUNCATE/REFERENCES/TRIGGER и GRANT OPTION у runtime нет.

запрещён. У создания пользователя остаётся серверный DEFAULT роли user.
Назначение администратора и удаление аккаунта — административные операции.

## Защита триггера квот

Функция квот становится SECURITY DEFINER владельца pg16_owner, с фиксированным
search_path `pg_catalog, public, pg_temp`. Таблица public доверенная: runtime не
имеет CREATE. В реализации перехода дополнительно квалифицировать обращения
к public.snapshot_storage_usage и тип строки этой таблицы.
У PUBLIC/runtime убрать EXECUTE функции; существующие триггеры продолжают работать
без этого права. Это поведение проверено настоящим соединением runtime.
Функцию, её владельца и триггеры приложение менять не сможет.

Нельзя заменять этот шаг прямым GRANT UPDATE счётчиков: тогда компрометация
приложения позволит сбрасывать квоты. Нельзя оставлять изменяемый search_path
у SECURITY DEFINER. Будущая миграция CREATE OR REPLACE функции должна сохранять
SECURITY DEFINER/search_path: исходная миграция 145 задаёт SECURITY INVOKER по
умолчанию и не должна повторно выполняться после разделения без восстановления
защитных свойств. Процесс миграций и документацию запуска нужно обновить вместе
с новым этапом, а не продолжать запускать все SQL от runtime по старой README.

## Переход после согласования

1. Подготовить адресную миграцию/административный сценарий с проверками исходной
   роли, целевой БД, состава объектов, членств и ACL. Существующая чужая pg16_owner,
   неожиданные объекты/права или неподходящая версия — остановка до изменений.
2. Перед серверной правкой проверить чистоту git, соседние сайты/службы и действующий
   способ резервного копирования. Сохранить закрытую копию БД, схему с владельцами
   и ACL, manifest собственников/членств/default ACL, функцию и её свойства.
   Проверить архивы и команды доступа для администратора/отката.
3. Согласованные файлы доставить только коммитом/push/fetch/log/pull --ff-only.
   Резервировать короткое окно на блокировки и применение прав. Ограничения
   lock_timeout/statement_timeout задаются до DDL.
4. Одной транзакцией: роль владельца, адресная передача объектов/БД/схемы,
   отзыв прежних лишних ACL, выдача матрицы, защита функции и default privileges.
   Проверять также права столбцов: одного REVOKE на уровне таблицы недостаточно,
   если раньше существовали отдельные column grants.
5. Проверить повторяемость сценария. При повторном запуске подходящая роль и
   ожидаемое состояние распознаются; неожиданное владение не «чинится» вслепую.
6. Новым соединением именно runtime проверить positive/negative матрицу и
   разрешённые HTTP-сценарии; административные fixtures создавать отдельным
   соединением. Не запускать старый полный тестовый набор от runtime: его fixtures
   меняют вопросы, категории и роли пользователей и намеренно требуют владельца.
7. Проверить резервную копию от postgres, отчёт ИИ, целостность счётчиков квот,
   сохранность данных и соседние сайты. SEC-08 закрывать только после серверной
   проверки, а не после подготовки SQL.

Изменение только прав БД и свойств функции само по себе не требует рестарта
приложения: реквизиты сохраняются. Активные транзакции/подготовленные запросы
проверяются при переходе; перезапуск допустим только при обоснованной необходимости.

## Откат

- До COMMIT ошибки откатывают весь переход; дополнительных данных удалять не нужно.
- После COMMIT администратор одной транзакцией возвращает владельцев целевой
  БД/объектов и прежние ACL/default ACL по сохранённому manifest. Возвращаются
  также SECURITY INVOKER, владелец и search_path функции, если это их исходное
  состояние. Нельзя вернуть только INVOKER, оставив runtime без прав счётчиков.
- Новую NOLOGIN-роль не удалять, пока есть зависимости. Не применять DROP OWNED
  или массовый REASSIGN OWNED для «уборки». Если после выпуска созданы новые
  объекты владельца, их согласованно включить в manifest отката.
- Данные продолжают жить в той же БД; полное восстановление backup не является
  обычным откатом ACL, поскольку потеряет новые ответы/сессии/диалоги.
- После отката повторить вход, сохранение снимка, проверку квот и backup.
  Возврат владения восстанавливает прежний риск SEC-08; это временный выход,
  а не альтернативное исправление.

## Локальные доказательства и ограничения

На отдельном PostgreSQL 17.11, socket-only в закрытом /private/tmp каталоге,
создана копия схемы без пользовательских данных. Реальные контроллеры приложения
подключались отдельным LOGIN runtime, не через SET ROLE из superuser-сессии.
Письма были только в тестовом outbox, вызовов модели не было.

Прошли 33 проверки матрицы и четыре проверки отката. В частности, работали
вход по коду, профиль, оба режима тренировки, экзамен и повтор результата,
статистика/администраторский просмотр, ИИ accept/start/finish/poll, отказы,
SQL-отчёт. Запреты проверены по SQLSTATE 42501: роль администратора, вопросы,
архив, счётчики, DDL/DROP/TRUNCATE, отключение триггера, изменение функции,
CREATE/TEMP/SET ROLE, сброс последовательностей. При конкуренции за последнее
место один снимок сохранился, второй отклонён; HTTP вернул 429, старая история
осталась доступна. Новые таблица и функция владельца закрыты runtime по умолчанию.

Для отката проверены восстановление владения БД, DDL, создание снимка с INVOKER
и согласованность счётчиков при удалении аккаунта. Стенд остановлен.
Обезличенный перечень проверок: [evidence](reviews/2026-11-12-security-audit/role-separation-evidence.json).
Этот первоначальный этап был проверкой идеи на PG17. Затем реализованный runner
проверен на PostgreSQL 16.14, включая полный restore собственной тестовой копии
и откат ACL; подробности ниже. Изменения прав и схемы на production не выполнялись.

Разделение ролей не изолирует строки пользователей от скомпрометированного
приложения: у runtime остаются необходимые SELECT/DML. Оно ограничивает DDL,
изменение учебного контента/ролей и вмешательство в квоты. RLS и отдельные
служебные функции для всех записей — другой объём работ, здесь не предлагаются.

Основания: [права и владение PostgreSQL 16](https://www.postgresql.org/docs/16/ddl-priv.html),
[SECURITY DEFINER и безопасный search_path](https://www.postgresql.org/docs/16/sql-createfunction.html),
[область действия REASSIGN OWNED](https://www.postgresql.org/docs/16/sql-reassign-owned.html).

## Реализованный административный сценарий

`scripts/db-role-separation.js` имеет четыре отдельных режима:

- `prepare`: проверка исходного состояния, полная custom-копия от администратора,
  проверка pg_restore --list и сохранение исходного manifest владельцев/ACL,
  столбцовых прав, default ACL runtime и полного определения функции.
- `apply`: применение одной транзакцией, с тайм-аутами и проверкой итоговой
  матрицы перед COMMIT. Повтор возвращает already_applied, не перезаписывая
  исходный manifest. Возврат владения и новое применение тоже поддерживаются.
- `verify`: только REPEATABLE READ READ ONLY, проверка владельцев, эффективных
  прав столбцов/таблиц/последовательностей, отсутствия grant option/членств,
  свойств функции/триггеров и закрытых прав новых объектов.
- `rollback`: адресное восстановление владельцев, определения функции и
  исходных ACL, включая grantor и grant option. Права столбцов восстанавливаются
  после прав таблицы, чтобы REVOKE таблицы не удалил уже восстановленные права.

Manifest привязан к system_identifier кластера, OID БД и роли, OID таблиц/функции
и составу столбцов. Неподходящая версия, чужая pg16_owner, неизвестные объекты,
изменённые исходные ACL или свойства роли останавливают операцию. Существующая
база с дополнительными служебными таблицами, включая tasks, намеренно не проходит
проверку production-состава: этот runner не применяется к общей локальной БД.

Каталог состояния должен быть отдельным, 0700 и принадлежать запускающему
пользователю; файлы state.json и before.dump — 0600, без симлинков. `prepare`
не перезаписывает существующие копии: для новой подготовки нужен новый каталог.
После apply исходный state.json не заменяется текущими ACL.

Сценарий запускается root из git-копии проекта. `--service` загружает окружение
работающей службы через /proc и передаёт его штатному loader: прямого чтения
или вывода .env нет. Административный сокет
открывается с временным effective UID/GID ОС-пользователя postgres для peer-auth,
затем восстанавливается root для доступа к закрытой резервной копии. Пароль
администратора и изменения pg_hba.conf не нужны; при запросе пароля соединение
завершается отказом. Сам pg_dump работает с UID/GID postgres, пишет в заранее
открытый root дескриптор; его окружение не содержит секретов приложения.
Механизм смены effective UID/GID подтверждён на appuse отдельным READ ONLY
подключением: peer-auth дал административный доступ к PostgreSQL 16.14, затем
UID/GID были восстановлены. Эта проверка не выполняла DDL, GRANT или запись данных.
Локально полный сценарий проверен под текущим пользователем macOS на приватном сокете.

Пример будущего запуска на appuse после отдельно разрешённых коммита/выпуска,
проверки соседних сайтов и резервирования остальных изменяемых настроек:

```bash
node scripts/db-role-separation.js prepare --service pg16-cert-prep \
  --state-dir /root/ssh-backups/pg16-role-separation-235 \
  --pg-bin /usr/lib/postgresql/16/bin
node scripts/db-role-separation.js apply --service pg16-cert-prep \
  --state-dir /root/ssh-backups/pg16-role-separation-235 \
  --pg-bin /usr/lib/postgresql/16/bin
node scripts/db-role-separation.js apply --service pg16-cert-prep \
  --state-dir /root/ssh-backups/pg16-role-separation-235 \
  --pg-bin /usr/lib/postgresql/16/bin
node scripts/db-role-separation.js verify --service pg16-cert-prep \
  --state-dir /root/ssh-backups/pg16-role-separation-235 \
  --pg-bin /usr/lib/postgresql/16/bin
```

Здесь `node` — согласованный поддерживаемый Node.js, например абсолютный путь
runtime службы. Для согласованного отката используется тот же вызов с `rollback`
вместо `verify`. Runner не перезапускает службу, не меняет .env и не отправляет
письма/запросы модели. После перехода новые SQL-миграции запускаются отдельным
административным соединением с SET ROLE pg16_owner. 146 напрямую не запускается:
один DO-блок содержит и проверку, и создание функции, поэтому отсутствие
ON_ERROR_STOP в ручном psql не позволяет обойти защиту продолжением файла.

## Проверки реализованного этапа

PostgreSQL 16.14 собран из официального исходного архива с проверкой SHA-256 в
отдельном /private/tmp каталоге. Системные PostgreSQL и пакеты не заменялись.
Для повторения нужен полный PG16 с pgcrypto и доступ к текущей схеме проекта:

```bash
PG16_TEST_BIN=/absolute/path/to/postgresql16/bin npm run test:db-roles
```

Этот отдельный набор не запускается обычным npm test и не пропускает проверки
молча: без PG16 он завершается ошибкой. Он читает только схему исходной БД через
штатный loader, исключает локальную tasks, создаёт свой кластер без TCP в закрытом
каталоге, приводит fixture к состоянию 145 и останавливает сервер после проверки.
Прошли 14/14 результатов TAP (13 сценариев и родительский тест); один из сценариев
включает 33 функциональные проверки с реальным LOGIN runtime и контроллерами.
Дополнительно проверены аварийный откат транзакции после передачи владения,
ошибочная роль-владелец, изменение схемы/column grant option, права файла manifest,
