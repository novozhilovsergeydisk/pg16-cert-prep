# Планировщик и EXPLAIN: материал для изучения

Этот материал к разделу «20. Планировщик и EXPLAIN». Он объясняет, как PostgreSQL решает, каким способом выполнить запрос, и как прочитать это решение в выводе команды `EXPLAIN`. Тема относится скорее к курсу «Оптимизация запросов» (QPT), чем к DBA1, поэтому раздел вне экзамена. Но читать простые планы нужно любому администратору: с этого начинается разбор любого медленного запроса.

Ориентир — PostgreSQL 16. Примеры выполнены на учебных кластерах PostgreSQL 16 (Linux) и 17 (macOS). Для тем этого материала между ними нет разницы; цифры времени и стоимости у вас будут другими, важны названия узлов и то, как они меняются.

## Как пользоваться материалом

- Каждая глава состоит из трёх частей. «Коротко» — суть простыми словами. «Подробнее» — как это устроено. «Проверьте сами» — запросы с объяснением, что смотреть в результате.
- Опыты ставьте на учебном кластере, а не на рабочем сервере. Как его создать, описано в главе 1.
- `EXPLAIN ANALYZE` действительно выполняет запрос. Для `INSERT`, `UPDATE` и `DELETE` оборачивайте его в транзакцию с откатом: `BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;`.
- Параметры `enable_seqscan`, `enable_indexscan` и подобные меняйте только в своём сеансе и только для опытов.
- Все опыты используют одну таблицу `t` на 100 тысяч строк. Как её создать, описано в главе 1.
- В конце есть практикум по шагам и словарь терминов.

## 1. Учебный кластер и таблица для опытов

### Коротко

Опыты с планами удобнее всего ставить на отдельном кластере: его не жалко, можно менять настройки и перезапускать. На рабочем сервере опыты с `ALTER SYSTEM`, перезапуском и большими сортировками мешают приложениям.

### Подробнее

Учебный кластер создаётся одной командой `initdb` в отдельном каталоге и запускается на своём порту. Пример для PostgreSQL из Homebrew на macOS (в Debian путь к программам — `/usr/lib/postgresql/16/bin`):

```
/usr/local/opt/postgresql@17/bin/initdb -D ~/pg-lab/data -U postgres
/usr/local/opt/postgresql@17/bin/pg_ctl -D ~/pg-lab/data -o "-p 5440" -l ~/pg-lab/server.log start
/usr/local/opt/postgresql@17/bin/psql -p 5440 -U postgres
```

Проверить, что вы подключились именно к нему: `SHOW port;` и `SELECT current_setting('data_directory');`. Функция `inet_server_port()` при подключении через Unix-сокет возвращает пустое значение — это нормально.

Если учебного кластера нет, но есть учебный сервер без рабочей нагрузки, можно создать на нём отдельную базу: `CREATE DATABASE lab;`, затем подключиться к ней командой `\c lab` и проверить, куда подключились: `SELECT current_database(), current_setting('port');`. После опытов базу удаляют: `\c postgres` и `DROP DATABASE lab;`. Внутри рабочего кластера так делать не стоит: отдельная база не изолирует нагрузку, общие настройки и перезапуски.

### Проверьте сами

Таблица для всех опытов:

```
CREATE TABLE t (id int PRIMARY KEY, val text);
INSERT INTO t SELECT g, 'строка ' || g FROM generate_series(1, 100000) AS g;
ANALYZE t;
\timing on
```

- `generate_series(1, 100000)` выдаёт числа от 1 до 100 000, из каждого получается строка `(id, 'строка id')`.
- `PRIMARY KEY` сам создаёт уникальный индекс `t_pkey`.
- `ANALYZE` собирает статистику для планировщика (глава 5).
- `\timing on` показывает время каждой команды.

## 2. Путь запроса

### Коротко

Сервер обрабатывает запрос в четыре этапа:

- разбор — проверка синтаксиса и поиск таблиц и столбцов в системном каталоге;
- переписывание — применение правил, прежде всего подстановка запроса вместо имени представления;
- планирование — выбор способа выполнения: по индексу или полным просмотром, каким способом соединять таблицы;
- выполнение — работа по выбранному плану.

`EXPLAIN` показывает результат третьего этапа — план.

### Подробнее

Ошибки разных этапов выглядят по-разному. `SELEC * FROM t` даёт «syntax error»: текст не удалось разобрать. `SELECT * FROM nosuch` даёт «relation does not exist»: синтаксис верен, но таблица не найдена в каталоге. Обе ошибки возникают до планирования.

Переписывание идёт раньше планирования, потому что планировщику нужно знать, какие таблицы стоят за представлением. Поэтому в плане запроса к представлению видны таблицы, а не само представление.

Подготовленный оператор (`PREPARE`) обычно выполняет разбор и переписывание один раз и хранит результат в сеансе; при каждом `EXECUTE` остаются планирование и выполнение. Если изменились таблицы, от которых зависит запрос, `search_path` или статистика, сервер разберёт или спланирует запрос заново. После нескольких выполнений сервер может перейти на общий план, не зависящий от значений параметров, и не планировать заново.

### Проверьте сами

```
CREATE VIEW small AS SELECT * FROM t WHERE id <= 1000;
CREATE VIEW tiny AS SELECT * FROM small WHERE id <= 10;
EXPLAIN SELECT * FROM tiny;
```

В плане не будет ни `tiny`, ни `small` — только таблица `t` с объединённым условием. Оба представления раскрыты до планирования.

Заглянуть в дерево запроса после переписывания (вывод длинный, служебный):

```
SET client_min_messages = log;
SET debug_print_rewritten = on;
SELECT * FROM tiny;
RESET debug_print_rewritten;
RESET client_min_messages;
DROP VIEW tiny, small;
```

## 3. Как читать план

### Коротко

План — дерево узлов. Каждый узел получает строки от узлов под ним, что-то с ними делает и передаёт выше. Читают план изнутри наружу: сначала самые глубокие узлы (чтение таблиц), потом то, что над ними (соединение, сортировка).

### Подробнее

```
EXPLAIN SELECT * FROM t WHERE id = 5;

Index Scan using t_pkey on t  (cost=0.29..8.31 rows=1 width=22)
  Index Cond: (id = 5)
```

- `Index Scan using t_pkey on t` — узел: как и откуда читаются строки;
- `cost=0.29..8.31` — оценка стоимости в условных единицах, а не в миллисекундах. Первое число — стоимость до получения первой строки, второе — всех строк;
- `rows=1` — сколько строк узел, по оценке, вернёт;
- `width=22` — средний размер строки в байтах (русская буква в UTF-8 занимает два байта);
- `Index Cond` — условие, проверяемое по индексу. `Filter` — условие, проверяемое на уже прочитанных строках.

Дочерние узлы сдвинуты вправо и отмечены стрелкой `->`.

Стоимость складывается из параметров:

- `seq_page_cost` = 1 — прочитать страницу при последовательном чтении (это и есть единица стоимости);
- `random_page_cost` = 4 — прочитать страницу в произвольном месте;
- `cpu_tuple_cost` = 0.01 — обработать одну строку;
- `cpu_index_tuple_cost` = 0.005 — обработать одну запись индекса;
- `cpu_operator_cost` = 0.0025 — вычислить одно условие или функцию.

Стоимость полного просмотра можно посчитать вручную. У таблицы `t` 637 страниц и 100 000 строк, условие одно:

```
EXPLAIN SELECT * FROM t WHERE id > 10;

Seq Scan on t  (cost=0.00..1887.00 rows=99990 width=22)
  Filter: (id > 10)
```

637 × 1 (страницы) + 100 000 × 0.01 (строки) + 100 000 × 0.0025 (условие) = 637 + 1000 + 250 = 1887. Без условия было бы 1637.

Планировщик перебирает возможные планы и выбирает самый дешёвый. Если нужны все строки, сравнивается полная стоимость; если только часть, например при `LIMIT`, важнее стоимость получения первых строк (глава 11). Стоимость — модель, а не измерение: она не знает, например, что сортировка по русским правилам сравнения строк в опыте главы 10 шла почти в восемь раз дольше побайтовой.

### Проверьте сами

```
SELECT relpages, reltuples FROM pg_class WHERE relname = 't';
SHOW seq_page_cost;
SHOW random_page_cost;
EXPLAIN SELECT * FROM t;
EXPLAIN SELECT * FROM t WHERE id > 10;
```

Пересчитайте стоимость `Seq Scan` по формуле и сравните с планом.

## 4. EXPLAIN ANALYZE

### Коротко

Обычный `EXPLAIN` только показывает план, запрос не выполняется. `EXPLAIN ANALYZE` выполняет запрос и добавляет к каждому узлу фактические цифры: время, число строк, число выполнений. Сравнение оценок с фактом — главный способ понять, где планировщик ошибся.

### Подробнее

```
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM t WHERE id < 1000;

Index Scan using t_pkey on t  (cost=0.29..39.60 rows=989 width=22) (actual time=0.017..0.221 rows=999 loops=1)
  Index Cond: (id < 1000)
  Buffers: shared hit=11
Planning:
  Buffers: shared hit=6
Planning Time: 1.466 ms
Execution Time: 0.301 ms
```

- `actual time=0.017..0.221` — миллисекунды до первой строки и до последней;
- `rows=999` — сколько строк получено на самом деле. Сравнивайте с оценкой `rows=989` слева: здесь статистика точная. Расхождение в десятки и сотни раз — повод разбираться (глава 12);
- `loops=1` — сколько раз выполнялся узел. Время и строки указаны в среднем на одно выполнение: при `loops=1000` общее время в тысячу раз больше. Среднее число строк округляется до целого;
- `Buffers: shared hit=11` — 11 обращений к страницам, найденным в буферном кеше (повторное обращение к той же странице считается снова); `read` — страницы, загруженные в буферный кеш из кеша ОС или с диска, по плану этого не различить; `dirtied` и `written` — изменено и записано. В цифры узла входят и обращения его дочерних узлов, поэтому по дереву их не складывают;
- `Planning` и `Planning Time` — работа планировщика. Первое планирование в сеансе дольше: сервер читает описание таблицы из системного каталога;
- `Execution Time` — выполнение.

В PostgreSQL 16 и 17 счётчики буферов нужно просить явно, параметром `BUFFERS`. С 18-й версии они выводятся при `ANALYZE` по умолчанию.

Сам замер добавляет накладные расходы, иногда заметные: время засекается в каждом узле. Если нужны только строки и буферы, используйте `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)`. Сравнивать `Execution Time` с временем обычного `SELECT` напрямую нельзя: `EXPLAIN ANALYZE` не передаёт строки клиенту.

### Проверьте сами

```
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM t WHERE id < 1000;
```

Если `read` нет, а есть только `hit`, все страницы, которые понадобились этому запросу, уже лежали в буферном кеше. О всей таблице это ничего не говорит. Увидеть `read` можно после перезапуска учебного кластера: буферный кеш при этом очищается (кеш ОС — нет).

Изменение данных — только с откатом:

```
BEGIN;
EXPLAIN ANALYZE DELETE FROM t WHERE id <= 10;
ROLLBACK;
SELECT count(*) FROM t;
```

## 5. Статистика

### Коротко

Чтобы оценить, сколько строк вернёт условие, планировщик пользуется статистикой: сколько в таблице строк и страниц, сколько разных значений в столбце, какие значения встречаются чаще, как они распределены. Статистику собирает команда `ANALYZE` или автоочистка. Без статистики или с устаревшей статистикой оценки строятся почти наугад, и план может оказаться плохим.

### Подробнее

`ANALYZE` строит случайную выборку строк размером около 300 × `default_statistics_target` (по умолчанию около 30 000 строк; чтобы её получить, сервер может просмотреть и больше строк, а маленькую таблицу — целиком) и сохраняет:

- в `pg_class` — `reltuples` (строки) и `relpages` (страницы);
- в `pg_statistic`, удобно смотреть через представление `pg_stats`, — для каждого столбца:
- `null_frac` — доля NULL;
- `n_distinct` — число разных значений. Отрицательное число — доля от числа строк: `-1` означает, что все значения разные;
- `most_common_vals` и `most_common_freqs` — самые частые значения и их доли;
- `histogram_bounds` — границы корзин гистограммы для остальных значений: в каждой корзине примерно одинаковое число строк;
- `avg_width` — средний размер значения;
- `correlation` — насколько порядок строк в файле таблицы совпадает с порядком значений (от −1 до 1, глава 8).

Все эти значения — оценки на момент последнего анализа: после изменений данных их обновляет следующий `ANALYZE`.

Автоочистка запускает анализ сама, когда число изменённых с последнего анализа строк превышает `autovacuum_analyze_threshold` + `autovacuum_analyze_scale_factor` × оценка числа строк `reltuples` (по умолчанию 50 + 10 %). Таблица становится кандидатом, а сам анализ выполнится при ближайшем обходе автоочистки. После массовой загрузки она может не успеть, поэтому `ANALYZE` запускают вручную.

`ANALYZE t` и `EXPLAIN ANALYZE запрос` — разные вещи с одним словом: первое собирает статистику, второе выполняет запрос и показывает план.

### Проверьте сами

```
SELECT reltuples, relpages FROM pg_class WHERE relname = 't';
SELECT attname, null_frac, n_distinct, avg_width, correlation FROM pg_stats WHERE tablename = 't';
SELECT last_analyze, last_autoanalyze FROM pg_stat_user_tables WHERE relname = 't';
```

У `id` будет `n_distinct = -1` (все значения разные) и `correlation = 1` (строки лежат по порядку `id`).

## 6. Способы доступа к таблице

### Коротко

Прочитать нужные строки можно по-разному:

- Seq Scan — прочитать таблицу целиком подряд;
- Index Scan — найти строки по индексу и за каждой сходить в таблицу;
- Bitmap Heap Scan — сначала собрать по индексу список нужных страниц, потом прочитать их подряд;
- Index Only Scan — взять данные прямо из индекса, не заходя в таблицу.

Индекс выгоден, когда нужна небольшая доля строк. Если нужна почти вся таблица, дешевле прочитать её подряд.

### Подробнее

Index Scan идёт по индексу в порядке значений и для каждой найденной записи сразу читает строку из таблицы. Строки выходят в порядке индекса, поэтому индекс B-tree с подходящим порядком может избавить запрос от отдельной сортировки. Плохо, если строк много и лежат они вразброс: сервер прыгает по файлу и может читать одну страницу много раз.

Bitmap Heap Scan работает в два этапа. Узел `Bitmap Index Scan` проходит индекс и отмечает в битовой карте нужные страницы, узел `Bitmap Heap Scan` читает отмеченные страницы в порядке файла, каждую один раз. Строки выходят в порядке страниц, а не индекса. Карты нескольких условий можно объединять узлами `BitmapAnd` и `BitmapOr`. Если карта не помещается в `work_mem`, часть её страниц становится неточной: для них помнится только страница без конкретных строк, и условие перепроверяется на каждой её строке. Сколько страниц точных и сколько неточных, показывает строка `Heap Blocks: exact=... lossy=...` при `ANALYZE`. Строка `Recheck Cond` — условие перепроверки; она есть в плане и тогда, когда неточных страниц нет.

Index Only Scan возможен, когда все нужные запросу столбцы есть в индексе. Но в индексе нет сведений о видимости строк (номера транзакций `xmin` и `xmax` хранятся только в версиях строк таблицы). Поэтому сервер смотрит в карту видимости: если страница отмечена «все строки видны всем», в таблицу ходить не нужно. Иначе он идёт в таблицу проверить, и это считает строка `Heap Fetches`. Отметки в карте видимости ставит `VACUUM`, а изменения строк их снимают.

Параметрами `enable_seqscan`, `enable_indexscan`, `enable_bitmapscan`, `enable_indexonlyscan` и подобными смотрят, какой план планировщик выбрал бы без данного способа. Действуют они по-разному: выключение одних делает способ очень дорогим в оценке (если другого пути нет, он всё равно будет выбран), выключение `enable_indexonlyscan` исключает этот способ совсем. Меняют их только в учебном сеансе, на рабочем сервере их не выключают.

### Проверьте сами

Один запрос, разные доли строк:

```
EXPLAIN SELECT * FROM t WHERE id = 5;
EXPLAIN SELECT * FROM t WHERE id < 20000;
EXPLAIN SELECT * FROM t WHERE id > 10;
```

Для одной строки — `Index Scan`, для почти всей таблицы — `Seq Scan`. Для 20 % строк на таблице `t` тоже получится `Index Scan`, а не битовая карта: строки лежат по порядку `id`, и обычный индексный доступ читает страницы подряд (глава 8).

Битовая карта, если запретить обычный индексный доступ:

```
SET enable_indexscan = off;
EXPLAIN (ANALYZE) SELECT * FROM t WHERE id < 20000;
RESET enable_indexscan;
EXPLAIN SELECT * FROM t WHERE id < 100 OR id > 99900;
```

Index Only Scan и карта видимости — на копии `v`. Изменение строк переносит их новые версии на другие страницы, и таблица `t` перестала бы лежать по порядку `id`, а на этом построены главы 8 и 10.

```
CREATE TABLE v AS SELECT * FROM t;
ALTER TABLE v ADD PRIMARY KEY (id);
VACUUM ANALYZE v;
EXPLAIN (ANALYZE) SELECT id FROM v WHERE id < 1000;
UPDATE v SET val = val WHERE id < 1000;
EXPLAIN (ANALYZE) SELECT id FROM v WHERE id < 1000;
SELECT relpages, relallvisible FROM pg_class WHERE relname = 'v';
VACUUM v;
EXPLAIN (ANALYZE) SELECT id FROM v WHERE id < 1000;
DROP TABLE v;
```

После изменения строк `Heap Fetches` станет больше нуля; точное число зависит от того, поместились ли новые версии строк на те же страницы. После `VACUUM` счётчик обычно возвращается к нулю. Если нет — в базе есть старые открытые транзакции, которые мешают очистке.

## 7. Что лежит в индексе

### Коротко

В индексе B-tree для каждой строки хранится значение индексируемых столбцов и адрес строки в таблице — номер страницы и позиция на ней. Остальных столбцов в индексе нет. Поэтому для `SELECT *` сервер находит адрес в индексе и идёт за строкой в таблицу.

### Подробнее

Адрес версии строки в PostgreSQL называется `ctid`, например `(0,5)` — страница 0, позиция 5 в списке указателей этой страницы. Это физический адрес, а не постоянный номер: при изменении строки её новая версия получает новый `ctid`. Именно пары «значение → ctid» хранит индекс `t_pkey`.

Чтобы обходиться без таблицы чаще, в индекс можно положить и другие столбцы, не участвующие в поиске, — покрывающий индекс с предложением `INCLUDE` (опыт — ниже, в «Проверьте сами»). Цена — индекс больше и медленнее обновляется.

Индекс `t_pkey` создан первичным ключом: имя таблицы плюс `_pkey`. Ограничение `UNIQUE` создаёт индекс с окончанием `_key`, команда `CREATE INDEX` без имени — с окончанием `_idx`. Индекс первичного ключа нельзя удалить через `DROP INDEX`: сначала снимают ограничение (`ALTER TABLE ... DROP CONSTRAINT`).

Тип индекса в PostgreSQL называется методом доступа:

- btree — по умолчанию: равенство, сравнения, диапазоны, сортировка, уникальность;
- hash — только равенство;
- gin — значения из многих частей: массивы, `jsonb`, полнотекстовый поиск;
- gist и spgist — геометрия, диапазоны, поиск ближайших;
- brin — очень маленький индекс для огромных таблиц, где значения лежат по порядку.

Индексы принадлежат базе данных: запрос видит индексы только той базы, к которой подключён.

### Проверьте сами

```
SELECT ctid, id, val FROM t WHERE id <= 3;
EXPLAIN SELECT id FROM t WHERE id < 1000;
EXPLAIN SELECT val FROM t WHERE id < 1000;
\d t_pkey
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 't';
\di+
```

Первый план — `Index Only Scan` (нужен только `id`), второй — `Index Scan` (за `val` нужно идти в таблицу). В `\d t_pkey` и `indexdef` виден тип: `btree`.

Покрывающий индекс: после его создания второй запрос тоже может выполняться `Index Only Scan`.

```
CREATE INDEX t_id_val ON t (id) INCLUDE (val);
EXPLAIN SELECT val FROM t WHERE id < 1000;
DROP INDEX t_id_val;
```

## 8. Корреляция и выбор способа доступа

### Коротко

`correlation` показывает, насколько порядок строк в файле таблицы совпадает с порядком значений столбца. Если совпадает, соседние значения лежат на соседних страницах, и чтение по индексу идёт почти подряд — индекс выгоден даже для большой доли строк. Если строки разбросаны, чтение по индексу превращается в прыжки по файлу, и планировщик выбирает битовую карту или полный просмотр.

### Подробнее

Значения `correlation`:

- 1 — строки лежат по возрастанию значения;
- −1 — по убыванию;
- около 0 — порядка нет.

Планировщик учитывает корреляцию при оценке Index Scan: при высокой корреляции он считает чтение страниц почти последовательным (`seq_page_cost`), при низкой — произвольным (`random_page_cost`, в четыре раза дороже).

### Проверьте сами

```
CREATE TABLE r AS SELECT * FROM t ORDER BY random();
CREATE INDEX ON r (id);
ANALYZE r;
SELECT tablename, correlation FROM pg_stats WHERE tablename IN ('t', 'r') AND attname = 'id';
EXPLAIN SELECT * FROM t WHERE id < 5000;
EXPLAIN SELECT * FROM r WHERE id < 5000;
```

У `t` корреляция 1 и план `Index Scan`, у `r` — около 0 и, скорее всего, `Bitmap Heap Scan`. Данные одинаковые, условие одно, разница только в порядке строк в файле.

## 9. Соединения таблиц

### Коротко

Соединить две таблицы можно тремя способами:

- Nested Loop — для каждой строки одной таблицы искать пары в другой. Хорош, когда строк с одной стороны мало, а с другой есть индекс;
- Hash Join — по одной таблице построить в памяти хеш-таблицу, вторую просмотреть и искать пары. Хорош для больших наборов и условий равенства;
- Merge Join — обе стороны упорядочены по ключу соединения и сливаются, как две отсортированные колоды. Хорош, когда данные уже упорядочены, например по индексу.

### Подробнее

В Nested Loop внешний набор — верхний дочерний узел, внутренний — нижний. Внутренний выполняется столько раз, сколько строк во внешнем: это видно в `loops` при `EXPLAIN ANALYZE`.

Hash Join строит хеш-таблицу по меньшему набору (узел `Hash`). Она должна поместиться в `work_mem` × `hash_mem_multiplier` (по умолчанию 2). Если не помещается, данные делятся на порции, и в плане при `ANALYZE` видно `Batches` больше 1.

Hash Join и Merge Join ищут пары по условию равенства: в условии соединения должно быть хотя бы одно равенство, а остальные условия проверяются отдельно (строка `Join Filter`). Если соединение задано только неравенством, остаётся Nested Loop.

### Проверьте сами

```
CREATE TABLE u (id int PRIMARY KEY, t_id int);
INSERT INTO u SELECT g, g % 100000 + 1 FROM generate_series(1, 50000) AS g;
ANALYZE u;
EXPLAIN SELECT * FROM t JOIN u ON u.t_id = t.id;
EXPLAIN SELECT * FROM t JOIN u ON u.t_id = t.id WHERE u.id = 7;
EXPLAIN (ANALYZE) SELECT * FROM t JOIN u ON u.t_id = t.id WHERE u.id < 100;
```

Для всех строк обычно будет `Hash Join`, для одной строки `u` — `Nested Loop`. В последнем плане посмотрите на `loops` у внутреннего узла.

## 10. Сортировка и work_mem

### Коротко

Если порядок строк нельзя взять из индекса, сервер сортирует их сам. Пока данные помещаются в `work_mem`, сортировка идёт в памяти (`quicksort`). Если не помещаются, данные сортируются порциями, порции записываются во временные файлы и затем сливаются (`external merge`). Обычно в памяти быстрее, но не всегда: время сортировки сильно зависит от цены сравнения и от исходного порядка данных.

### Подробнее

Строка `Sort Method` в `EXPLAIN ANALYZE` показывает способ:

- `quicksort  Memory: ...kB` — в памяти;
- `external merge  Disk: ...kB` — через временные файлы;
- `top-N heapsort` — для `ORDER BY ... LIMIT N`: сервер держит только N лучших строк.

В памяти сортировка занимает больше места, чем на диске: у каждой строки в памяти есть служебные заголовки и указатели.

`work_mem` ограничивает каждую операцию сортировки или хеширования, а не запрос и не сеанс. В сложном плане таких операций несколько, а подключений много, поэтому большое значение для всего сервера опасно. Обычно его повышают точечно: `SET work_mem` в сеансе или `SET LOCAL` в транзакции для тяжёлого отчёта.

Подробности сортировки показывает служебный параметр `trace_sort`: число порций, проходы слияния, время этапов.

### Опыт: когда через диск оказалось быстрее

Сортировка 100 000 строк `t` по `val` с разными правилами сравнения строк (сервер PostgreSQL 16 на Linux, время выполнения):

- `COLLATE "C"`, побайтовое сравнение: в памяти 264 мс, через диск 271 мс;
- `COLLATE "ru_RU.utf8"`, правила glibc: в памяти 2049 мс, через диск 874 мс;
- `COLLATE "ru-RU-x-icu"`, правила ICU: в памяти 1031 мс, через диск 418 мс;
- числа, `ORDER BY id % 1000`: в памяти 139 мс, через диск 264 мс;
- `ru_RU.utf8` на перемешанной копии `r`: в памяти 1954 мс, через диск 2310 мс.

Что из этого следует:

- Цена сравнения решает почти всё. С правилами `ru_RU.utf8` запрос в памяти шёл почти в восемь раз дольше, чем с `C`: сравнение по языковым правилам многоуровневое и намного дороже побайтового. Это отношение времени запросов; цену одного сравнения отдельно не измеряли. Планировщик разницы не учитывает: оценка стоимости у всех трёх вариантов одинаковая.
- На таблице `t` строки вставлены по порядку `id`. Сортировка через диск режет данные на порции примерно по 850 подряд идущих строк, например «строка 42500» … «строка 43350». У чисел одной длины алфавитный порядок совпадает с числовым, поэтому порция уже почти упорядочена. Быстрая сортировка PostgreSQL сначала проверяет, не упорядочены ли данные, и если упорядочены полностью, обходится одним проходом. Большинство порций не пересекает границу разрядности чисел (как между 9 и 10) и уже упорядочено. `trace_sort` показал: все 118 порций были отсортированы и записаны через 0,22 с от начала сортировки, а одна сортировка всех строк в памяти длилась 1,93 с.
- На перемешанных данных порции не упорядочены, преимущество исчезает, и всё становится как в теории: в памяти быстрее.
- Правила ICU здесь оказались вдвое быстрее glibc. Возможная причина: для ICU PostgreSQL умеет сравнивать сокращённые ключи, а для правил glibc это ускорение обычно отключено. Использовалось ли оно в этом опыте и насколько помогло, отдельно не проверяли.

Вывод для работы: «больше work_mem — всегда быстрее» и «C и ru_RU стоят одинаково» — неверно. Проверяют замером.

### Проверьте сами

```
SET work_mem = '64MB';
EXPLAIN (ANALYZE) SELECT * FROM t ORDER BY val;
SET work_mem = '64kB';
EXPLAIN (ANALYZE) SELECT * FROM t ORDER BY val;
EXPLAIN (ANALYZE) SELECT * FROM t ORDER BY val COLLATE "C";
EXPLAIN (ANALYZE) SELECT * FROM t ORDER BY val LIMIT 10;
RESET work_mem;
```

Подробности сортировки — на том же запросе, с тем же правилом сравнения и `work_mem`:

```
SET work_mem = '64kB';
SET client_min_messages = log;
SET trace_sort = on;
EXPLAIN (ANALYZE) SELECT * FROM t ORDER BY val COLLATE "ru_RU.utf8";
RESET trace_sort;
RESET client_min_messages;
RESET work_mem;
```

Время в сообщениях `trace_sort` накопительное, от начала сортировки: длительность этапа — разность соседних отметок. Повторите с `work_mem = '64MB'` и сравните. Если правила `ru_RU.utf8` на сервере нет, возьмите имя из запроса ниже.

Какие правила сравнения есть на сервере и какие у базы по умолчанию:

```
SELECT collname FROM pg_collation WHERE collname ILIKE 'ru%';
SELECT datlocprovider, datcollate, daticulocale FROM pg_database WHERE datname = current_database();
```

`datlocprovider` = `c` — правила библиотеки ОС, смотрите `datcollate`; `i` — правила ICU, смотрите `daticulocale`. В сравнительных опытах правило лучше указывать явно, через `COLLATE`.

## 11. Агрегация и LIMIT

### Коротко

Для `GROUP BY` и агрегатных функций сервер либо строит хеш-таблицу групп (HashAggregate), либо сортирует строки и считает группы подряд (GroupAggregate). Для `LIMIT` узел Limit забирает нужное число строк и останавливает выполнение, поэтому важна стоимость получения первых строк.

### Подробнее

- HashAggregate хорош, когда групп немного и хеш-таблица помещается в память (`work_mem` × `hash_mem_multiplier`). Если не помещается, начиная с PostgreSQL 13 данные сбрасываются во временные файлы: в плане видны `Batches` и `Disk Usage`.
- GroupAggregate нужен отсортированный вход: от индекса или от узла Sort.
- Для `LIMIT` планировщик выбирает план с малой стоимостью первых строк. Поэтому `ORDER BY id LIMIT 10` пойдёт по индексу, даже если для всей таблицы выгоднее полный просмотр.

### Проверьте сами

```
EXPLAIN (ANALYZE) SELECT id % 10 AS g, count(*) FROM t GROUP BY 1;
EXPLAIN SELECT * FROM t ORDER BY id LIMIT 10;
EXPLAIN SELECT * FROM t ORDER BY val LIMIT 10;
```

## 12. Что смотреть в плохом плане

- Оценка `rows` расходится с фактическими `rows` в десятки раз. Частая причина — устаревшая или неполная статистика: начните с `ANALYZE` и посмотрите `pg_stats`.
- `Seq Scan` на большой таблице, хотя нужна малая доля строк. Нет подходящего индекса, условие не может его использовать (например, функция над столбцом), или оценка доли строк неверна.
- `Sort Method: external merge` или `Batches` больше 1 у Hash и HashAggregate. Операции не хватает `work_mem`. Перед повышением сравните время замером: внешняя сортировка не всегда медленнее (глава 10).
- `Nested Loop` с большим `loops` у внутреннего узла без индекса. Внутренний узел выполняется много раз, и каждое выполнение дорогое.
- Большой `Heap Fetches` у Index Only Scan. Многие страницы не отмечены в карте видимости: после изменений таблице нужна очистка, а если отметок нет и после `VACUUM`, мешают старые открытые транзакции.
- `Buffers: read` намного больше `hit`. Данные читаются с диска или из кеша ОС, а не из буферного кеша.

## 14. Словарь терминов

- Планировщик (оптимизатор) — часть сервера, которая выбирает способ выполнения запроса.
- План — дерево узлов, по которому выполняется запрос; его показывает `EXPLAIN`.
- Узел плана — одна операция: чтение таблицы, соединение, сортировка, агрегация.
- Стоимость (`cost`) — оценка затрат в условных единицах; за единицу принято последовательное чтение одной страницы.
- Стоимость запуска — первое число `cost`: затраты до получения первой строки.
- `rows` — оценка числа строк; при `ANALYZE` рядом стоит фактическое число.
- `loops` — сколько раз выполнялся узел.
- Статистика — сведения о данных таблицы для оценок планировщика; собирается `ANALYZE`.
- `pg_stats` — представление со статистикой столбцов.
- `n_distinct` — оценка числа разных значений столбца.
- Гистограмма — границы корзин с примерно одинаковым числом строк.
- `correlation` — согласованность порядка строк в файле и порядка значений столбца.
- Seq Scan — последовательное чтение всей таблицы.
- Index Scan — поиск по индексу с чтением строк из таблицы.
- Bitmap Heap Scan — чтение страниц таблицы по битовой карте, собранной по индексу.
- Index Only Scan — получение данных только из индекса с проверкой карты видимости.
- `Heap Fetches` — сколько раз Index Only Scan всё же обратился к таблице.
- `ctid` — физический адрес версии строки: номер страницы и позиция на ней.
- Покрывающий индекс — индекс с дополнительными столбцами (`INCLUDE`) для Index Only Scan.
- Метод доступа — тип индекса: btree, hash, gin, gist, spgist, brin.
- Nested Loop, Hash Join, Merge Join — способы соединения таблиц.
- `work_mem` — лимит памяти на одну операцию сортировки или хеширования.
- `external merge` — сортировка порциями через временные файлы.
- Правило сравнения (`COLLATE`) — правила упорядочения строк; `C` сравнивает байты, языковые правила — по алфавиту языка.
- `trace_sort` — служебный параметр, выводящий подробности сортировки.
