# Практикум. Мониторинг

Примеры повторяют практику курса к теме: статистика обращений к таблице, взаимоблокировка и сообщения о ней в журнале сервера, расширение pg_stat_statements. Выполняйте на учебном кластере, не на рабочем сервере. Первому и третьему примерам хватит одного окна psql под суперпользователем postgres, для второго нужны три окна psql и окно командной строки (в третьем окне только смотрим, кто кого ждёт).

Номера процессов и транзакций, время и размеры в выводе у вас будут другими.

Подготовка, в любом окне psql:

```sql
CREATE DATABASE practice;
```

Затем в каждом окне:

```sql
\c practice
```

## Пример 1. Накопительная статистика таблицы

Цель: сопоставить счётчики статистики с тем, что вы делали с таблицей, и увидеть, что меняет очистка.

Автоочистку для таблицы примера отключаем параметром хранения, чтобы счётчики не менялись сами:

```sql
CREATE TABLE t (id int, val text) WITH (autovacuum_enabled = off);
INSERT INTO t SELECT g, 'строка ' || g FROM generate_series(1, 1000) g;
SELECT pg_sleep(1.5);
SELECT relname, n_tup_ins, n_tup_upd, n_tup_del, n_live_tup, n_dead_tup, last_vacuum
FROM pg_stat_user_tables WHERE relname = 't';
```

Накопительная статистика обновляется не чаще раза в секунду, поэтому перед запросом к ней нужна короткая пауза.

```
 relname | n_tup_ins | n_tup_upd | n_tup_del | n_live_tup | n_dead_tup | last_vacuum
---------+-----------+-----------+-----------+------------+------------+-------------
 t       |      1000 |         0 |         0 |       1000 |          0 |
(1 строка)
```

Вставлено 1000 строк, все живые, мёртвых нет. Теперь удалим все строки:

```sql
DELETE FROM t;
SELECT pg_sleep(1.5);
SELECT relname, n_tup_ins, n_tup_del, n_live_tup, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 't';
```

```
 relname | n_tup_ins | n_tup_del | n_live_tup | n_dead_tup
---------+-----------+-----------+------------+------------
 t       |      1000 |      1000 |          0 |       1000
(1 строка)
```

Счётчик вставок остался прежним, потому что он накопительный и только растёт. Живых строк нет, а 1000 удалённых версий лежат в таблице мёртвыми: место они занимают, пока их не уберёт очистка.

```sql
VACUUM t;
SELECT pg_sleep(1.5);
SELECT relname, n_tup_ins, n_tup_del, n_live_tup, n_dead_tup, last_vacuum IS NOT NULL AS vacuumed
FROM pg_stat_user_tables WHERE relname = 't';
```

```
 relname | n_tup_ins | n_tup_del | n_live_tup | n_dead_tup | vacuumed
---------+-----------+-----------+------------+------------+----------
 t       |      1000 |      1000 |          0 |          0 | t
(1 строка)
```

После очистки мёртвых версий нет, а накопительные счётчики вставок и удалений не сбросились: очистка их не меняет. В последнем столбце видно, что очистка отмечена: заполнено поле last_vacuum.

К вопросам: какой столбец pg_stat_user_tables показывает примерное число мёртвых версий строк; какие параметры сбора статистики включены по умолчанию; какое представление показывает текущую активность процессов.

## Пример 2. Взаимоблокировка и журнал сервера

Цель: создать взаимоблокировку двух транзакций и посмотреть, что о ней сообщают клиенту и что записывается в журнал.

Окно 1 (psql), подготовка таблицы:

```sql
CREATE TABLE t (id int PRIMARY KEY, val text);
INSERT INTO t VALUES (1, 'первая'), (2, 'вторая');
```

Каждая транзакция сначала блокирует свою строку. Окно 1:

```sql
BEGIN;
UPDATE t SET val = 'A' WHERE id = 1;
```

Окно 2:

```sql
BEGIN;
UPDATE t SET val = 'B' WHERE id = 2;
```

Теперь транзакции пытаются изменить строку друг друга. Окно 1:

```sql
UPDATE t SET val = 'A' WHERE id = 2;
```

Окно 1 зависло: строка 2 заблокирована транзакцией из окна 2. Это обычное ожидание, не взаимоблокировка. Пока оно длится, в окне 3 (psql) посмотрим, кто кого ждёт:

```sql
SELECT pid, wait_event_type, wait_event, pg_blocking_pids(pid) AS blocked_by
FROM pg_stat_activity
WHERE datname = 'practice' AND wait_event_type = 'Lock';
```

```
 pid  | wait_event_type |  wait_event   | blocked_by
------+-----------------+---------------+------------
 3173 | Lock            | transactionid | {3174}
(1 строка)
```

Процесс 3173 ждёт завершения транзакции процесса 3174. Теперь замкнём цикл. Окно 2:

```sql
UPDATE t SET val = 'B' WHERE id = 1;
```

Через секунду сервер обнаруживает, что транзакции ждут друг друга. Одна из них прерывается, и вторая продолжает работу. В этом опыте ошибку получило окно 1:

```
ОШИБКА:  обнаружена взаимоблокировка
ПОДРОБНОСТИ:  Процесс 3173 ожидает в режиме ShareLock блокировку "транзакция 1092"; заблокирован процессом 3174.
Процесс 3174 ожидает в режиме ShareLock блокировку "транзакция 1091"; заблокирован процессом 3173.
ПОДСКАЗКА:  Подробности запроса смотрите в протоколе сервера.
КОНТЕКСТ:  при изменении кортежа (0,2) в отношении "t"
```

А окно 2 получило ответ UPDATE 1: транзакция из окна 1 прервана, её блокировки сняты. Какая из двух транзакций станет жертвой, заранее сказать нельзя, поэтому приложение должно уметь повторить прерванную транзакцию.

Задержка в секунду — это параметр deadlock_timeout. Сервер проверяет, нет ли цикла ожидания, только когда ожидание длится дольше него.

Завершите транзакции, в обоих окнах:

```sql
ROLLBACK;
```

Теперь посмотрим журнал сервера. В командной строке (путь к журналу у вас свой, на Debian и Ubuntu это обычно файл в /var/log/postgresql):

```bash
tail -n 12 /var/log/postgresql/postgresql-16-main.log
```

```
ОШИБКА:  обнаружена взаимоблокировка
ПОДРОБНОСТИ:  Процесс 3173 ожидает в режиме ShareLock блокировку "транзакция 1092"; заблокирован процессом 3174.
	Процесс 3174 ожидает в режиме ShareLock блокировку "транзакция 1091"; заблокирован процессом 3173.
	Процесс 3173: UPDATE t SET val = 'A' WHERE id = 2
	Процесс 3174: UPDATE t SET val = 'B' WHERE id = 1
ПОДСКАЗКА:  Подробности запроса смотрите в протоколе сервера.
КОНТЕКСТ:  при изменении кортежа (0,2) в отношении "t"
ОПЕРАТОР:  UPDATE t SET val = 'A' WHERE id = 2
```

В начале каждой строки журнала стоят время и номер процесса, здесь они опущены. Клиент получает только описание цикла, а журнал дополнительно хранит тексты команд обоих процессов: по ним видно, какие запросы столкнулись.

К вопросам: что показывают поля state, wait_event и query в pg_stat_activity; какой параметр записывает в журнал долгие ожидания блокировок.

## Пример 3. Расширение pg_stat_statements

Цель: подключить расширение, накапливающее статистику по запросам, и посмотреть, как оно объединяет похожие запросы.

Расширение должно загружаться при старте сервера. Список библиотек в примере пуст; если в вашем списке уже есть библиотеки, перечислите их через запятую вместе с новой. В psql под суперпользователем:

```sql
ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';
```

Параметр меняется только при перезапуске сервера. В командной строке, на Debian и Ubuntu:

```bash
sudo pg_ctlcluster 16 main restart
```

После перезапуска, в psql:

```sql
\c practice
CREATE EXTENSION pg_stat_statements;
SELECT pg_stat_statements_reset();
CREATE TABLE t (id int PRIMARY KEY, val text);
INSERT INTO t SELECT g, 'строка ' || g FROM generate_series(1, 10000) g;
SELECT count(*) FROM t WHERE id < 100;
SELECT count(*) FROM t WHERE id < 5000;
SELECT * FROM t WHERE id = 1;
SELECT * FROM t WHERE id = 2;
SELECT * FROM t WHERE id = 3;
```

Смотрим накопленное:

```sql
SELECT query, calls, rows, round(total_exec_time::numeric, 2) AS total_ms, round(mean_exec_time::numeric, 3) AS mean_ms
FROM pg_stat_statements
WHERE dbid = (SELECT oid FROM pg_database WHERE datname = 'practice')
  AND query NOT LIKE '%pg_stat_statements%'
ORDER BY total_exec_time DESC;
```

```
                             query                              | calls | rows  | total_ms | mean_ms
----------------------------------------------------------------+-------+-------+----------+---------
 INSERT INTO t SELECT g, $1 || g FROM generate_series($2, $3) g |     1 | 10000 |    21.69 |  21.689
 CREATE TABLE t (id int PRIMARY KEY, val text)                  |     1 |     0 |     2.87 |   2.875
 SELECT count(*) FROM t WHERE id < $1                           |     2 |     2 |     1.19 |   0.597
 SELECT * FROM t WHERE id = $1                                  |     3 |     3 |     0.02 |   0.008
(4 строки)
```

Запросы с разными константами сложились в одну строку: константы заменены параметрами $1, $2, поэтому три выборки по id дали одну запись с calls = 3, а два подсчёта с разными границами — запись с calls = 2. В столбцах видно число выполнений, число строк, суммарное и среднее время.

Верните настройку, чтобы расширение не загружалось дальше. В psql:

```sql
ALTER SYSTEM RESET shared_preload_libraries;
```

И перезапустите сервер:

```bash
sudo pg_ctlcluster 16 main restart
```

К вопросам: какое расширение накапливает число выполнений, время и число строк по нормализованным запросам; что нужно сделать перед CREATE EXTENSION pg_stat_statements.
