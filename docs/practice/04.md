# Практикум. Общее устройство PostgreSQL

В курсе к этой теме практических заданий нет, поэтому примеры составлены по лекции: процесс на каждое подключение и служебные процессы, подготовленные операторы, расширения. Выполняйте на учебном кластере, не на рабочем сервере. Нужны два окна psql под суперпользователем postgres и окно командной строки.

Если нужно подключаться не к стандартному порту, добавляйте к команде psql ключ -p. Номера процессов и размеры в выводе у вас будут другими.

Подготовка, в psql:

```sql
CREATE DATABASE practice;
\c practice
```

## Пример 1. Процесс на каждое подключение

Цель: увидеть, что сервер обслуживает каждого клиента отдельным процессом, а рядом с ними работают служебные процессы.

Окно 1 (psql) подключено к базе practice. Узнаем номер процесса, который его обслуживает, и оставим окно открытым:

```sql
SELECT pg_backend_pid();
```

```
 pg_backend_pid 
----------------
          16035
(1 строка)
```

Окно 2 (psql). Посмотрим на все процессы сервера через pg_stat_activity:

```sql
SELECT pid, backend_type, state, left(query, 30) AS query
FROM pg_stat_activity
WHERE datname = 'practice' OR backend_type <> 'client backend'
ORDER BY (backend_type = 'client backend') DESC, pid;
```

```
  pid  |         backend_type         | state  |             query              
-------+------------------------------+--------+--------------------------------
 16035 | client backend               | idle   | SELECT pg_backend_pid();
 16042 | client backend               | active | SELECT pid, backend_type, stat
 15424 | checkpointer                 |        | 
 15425 | background writer            |        | 
 15427 | walwriter                    |        | 
 15428 | autovacuum launcher          |        | 
 15429 | logical replication launcher |        | 
(7 строк)
```

Двух клиентов обслуживают два процесса типа client backend. Номер первого совпадает с тем, что вернул pg_backend_pid в окне 1. Остальные пять процессов служебные, они не принадлежат клиентам. Состояние idle у первого означает, что он ждёт следующую команду, а запись в столбце query это его последняя команда.

Теперь посмотрим на те же процессы глазами операционной системы. В командной строке возьмём номер главного процесса из postmaster.pid и выберем сам этот процесс и всех его потомков:

```bash
PM=$(head -n 1 $PGDATA/postmaster.pid)
ps -ax -o pid,ppid,args | awk -v p=$PM '$1==p || $2==p'
```

```
15423     1 /usr/lib/postgresql/16/bin/postgres -D /var/lib/postgresql/16/main -c config_file=/etc/postgresql/16/main/postgresql.conf
15424 15423 postgres: 16/main: checkpointer
15425 15423 postgres: 16/main: background writer
15427 15423 postgres: 16/main: walwriter
15428 15423 postgres: 16/main: autovacuum launcher
15429 15423 postgres: 16/main: logical replication launcher
16035 15423 postgres: 16/main: postgres practice [local] idle
16042 15423 postgres: 16/main: postgres practice [local] idle
```

Все процессы сервера порождены главным, у них одинаковый родитель 15423. Процесс 16035 назван по пользователю, базе, способу подключения и состоянию. На Debian и Ubuntu после postgres: стоит имя кластера 16/main, в других установках его может не быть. Служебные процессы работают и без клиентов, а клиентский процесс появился вместе с подключением. Закройте окно 1 командой \q и повторите запрос из окна 2: процесс 16035 исчез, потому что с отключением клиента завершается и его процесс.

К вопросам: сколько процессов обслуживает одно подключение; как называется главный процесс сервера; какие служебные процессы работают всегда.

## Пример 2. Подготовленные операторы

Цель: увидеть, что подготовленный оператор живёт в памяти одного сеанса, и проследить, как планировщик переходит от планов под конкретное значение к общему плану.

Подготовим таблицу, в psql:

```sql
\c practice
CREATE TABLE t (id int PRIMARY KEY, val text);
INSERT INTO t SELECT g, 'строка ' || g FROM generate_series(1, 10000) g;
ANALYZE t;
```

Подготовим запрос с параметром. Запрос разбирается один раз, а значение подставляется при каждом выполнении:

```sql
PREPARE q (int) AS SELECT * FROM t WHERE id = $1;
SELECT name, parameter_types, generic_plans, custom_plans FROM pg_prepared_statements;
```

```
 name | parameter_types | generic_plans | custom_plans 
------+-----------------+---------------+--------------
 q    | {integer}       |             0 |            0
(1 строка)
```

Подготовленный оператор виден в представлении pg_prepared_statements, пока ни разу не выполнялся. Посмотрим, какой план получается для значения 42:

```sql
EXPLAIN EXECUTE q(42);
```

```
                           QUERY PLAN                            
-----------------------------------------------------------------
 Index Scan using t_pkey on t  (cost=0.29..8.30 rows=1 width=21)
   Index Cond: (id = 42)
(2 строки)
```

В условии стоит конкретное значение: план построен под него. Выполним запрос ещё пять раз с разными значениями, вывод строк при этом отправим в никуда:

```sql
\o /dev/null
EXECUTE q(1);
EXECUTE q(2);
EXECUTE q(3);
EXECUTE q(4);
EXECUTE q(5);
\o
SELECT name, generic_plans, custom_plans FROM pg_prepared_statements;
EXPLAIN EXECUTE q(42);
```

```
 name | generic_plans | custom_plans 
------+---------------+--------------
 q    |             1 |            5
(1 строка)

                           QUERY PLAN                            
-----------------------------------------------------------------
 Index Scan using t_pkey on t  (cost=0.29..8.30 rows=1 width=21)
   Index Cond: (id = $1)
(2 строки)
```

Первые пять выполнений планировщик строил под конкретное значение, считая и EXPLAIN. На шестом он сравнил стоимость с общим планом, увидел, что общий не дороже, и дальше пользуется им: в условии теперь параметр $1, а не число, и план не нужно строить заново при каждом выполнении. Выбор делает параметр plan_cache_mode, по умолчанию auto.

Подготовленные операторы принадлежат сеансу. Откройте второе окно psql, подключитесь к базе practice и проверьте:

```sql
SELECT count(*) FROM pg_prepared_statements;
EXECUTE q(1);
```

```
 count 
-------
     0
(1 строка)

ОШИБКА:  подготовленный оператор "q" не существует
```

Подготовленный оператор виден только сеансу, который его создал, и исчезает вместе с ним. Команда DEALLOCATE q удаляет его раньше.

К вопросам: что делает команда PREPARE; где хранится подготовленный оператор; чем общий план отличается от плана под конкретное значение.

## Пример 3. Расширения подключаются без перезапуска

Цель: установить расширение «на лету» и убедиться, что сервер при этом не перезапускался.

Расширения, доступные в вашей установке, показывает представление pg_available_extensions. Проверим три из них:

```sql
SELECT name, installed_version IS NOT NULL AS installed
FROM pg_available_extensions
WHERE name IN ('hstore', 'pg_stat_statements', 'pg_trgm')
ORDER BY name;
```

```
        name        | installed 
--------------------+-----------
 hstore             | f
 pg_stat_statements | f
 pg_trgm            | f
(3 строки)
```

Расширения входят в пакет postgresql-contrib или в основной пакет, зависит от дистрибутива. Они доступны, но не установлены в базу. Попробуем воспользоваться функцией из расширения pg_trgm:

```sql
SELECT similarity('postgres', 'postgress');
```

```
ОШИБКА:  функция similarity(unknown, unknown) не существует
СТРОКА 1: SELECT similarity('postgres', 'postgress')
                 ^
ПОДСКАЗКА:  Функция с данными именем и типами аргументов не найдена. Возможно, вам следует добавить явные приведения типов.
```

Запомним время запуска сервера, установим расширение и повторим запрос:

```sql
SELECT pg_postmaster_start_time() AS started \gset
CREATE EXTENSION pg_trgm;
SELECT similarity('postgres', 'postgress');
```

```
CREATE EXTENSION
 similarity 
------------
 0.72727275
(1 строка)
```

Функция заработала сразу, без перезапуска. Проверим, что сервер действительно не перезапускался, и посмотрим, что расширение добавило:

```sql
SELECT pg_postmaster_start_time() = :'started' AS same_start;
\dx
```

```
 same_start 
------------
 t
(1 строка)

                                  Список установленных расширений
   Имя   | Версия |   Схема    |                             Описание                              
---------+--------+------------+-------------------------------------------------------------------
 pg_trgm | 1.6    | public     | text similarity measurement and index searching based on trigrams
 plpgsql | 1.0    | pg_catalog | PL/pgSQL procedural language
(2 строки)
```

Время запуска главного процесса не изменилось. Версия расширения у вас может быть другой. Расширение pg_trgm добавило функции, оператор сходства строк и классы операторов для индексов, а plpgsql это язык программирования, который тоже поставляется как расширение. Не все расширения подключаются так просто: те, которым нужна своя общая память или фоновые процессы, например pg_stat_statements, загружаются при старте сервера и требуют перезапуска. Об этом пример 3 практикума по мониторингу.

К вопросам: какой командой подключают расширение к базе; какие возможности могут добавлять расширения; всегда ли для подключения расширения нужен перезапуск сервера.
