# Практикум. Логическая репликация

Примеры повторяют практику курса к теме: логическая репликация таблицы в другую таблицу на том же сервере и двунаправленная репликация одной таблицы между двумя серверами. Между ними вставлен пример про ограничения, о которых говорит лекция. Выполняйте на учебных кластерах, не на рабочем сервере, в psql под суперпользователем postgres. Нужны окно psql и окно командной строки.

В строках подключения ниже порт 5432 это порт основного учебного кластера. Если у вас другой порт или нужен ещё и пользователь, добавьте port=... и user=... в строку подключения. Второй сервер в третьем примере запускаем на порту 5472. Номера позиций журнала и тексты сообщений в выводе у вас могут отличаться.

## Подготовка

Для логической репликации уровень журнала должен быть logical, а смена уровня требует перезапуска сервера. В psql:

```sql
SHOW wal_level;
ALTER SYSTEM SET wal_level = logical;
```

```
 wal_level 
-----------
 replica
(1 строка)
```

Перезапустите кластер так, как вы это обычно делаете (на Debian и Ubuntu это pg_ctlcluster 16 main restart) и проверьте:

```sql
SHOW wal_level;
```

```
 wal_level 
-----------
 logical
(1 строка)
```

## Пример 1. Репликация таблицы в другую базу того же сервера

Цель: настроить публикацию и подписку между двумя базами одного сервера и обойти зависание CREATE SUBSCRIPTION.

Источник и приёмник это две базы одного кластера. В источнике создадим таблицу с данными и публикацию, а в приёмнике пустую таблицу той же структуры. Структура не копируется репликацией, её нужно создать заранее:

```sql
CREATE DATABASE pub;
CREATE DATABASE sub;
\c pub
CREATE TABLE t (id int PRIMARY KEY, val text);
INSERT INTO t VALUES (1, 'раз'), (2, 'два');
CREATE PUBLICATION p FOR TABLE t;
\c sub
CREATE TABLE t (id int PRIMARY KEY, val text);
```

Создадим подписку обычной командой:

```sql
CREATE SUBSCRIPTION s CONNECTION 'port=5432 dbname=pub' PUBLICATION p;
```

Команда не возвращает управление. Откройте второе окно psql и посмотрите, на чём она стоит:

```sql
SELECT wait_event_type, wait_event, left(query, 40) AS query
FROM pg_stat_activity
WHERE query ILIKE 'CREATE SUBSCRIPTION%' OR query ILIKE 'CREATE_REPLICATION_SLOT%';
```

```
 wait_event_type |       wait_event        |                  query                   
-----------------+-------------------------+------------------------------------------
 Client          | LibpqwalreceiverReceive | CREATE SUBSCRIPTION s CONNECTION 'port=5
 Lock            | transactionid           | CREATE_REPLICATION_SLOT "s" LOGICAL pgou
(2 строки)
```

Подписка создаёт на сервере публикации слот репликации. Здесь сервер тот же, и создание слота ждёт завершения всех текущих транзакций, включая транзакцию самой команды CREATE SUBSCRIPTION. Получился замкнутый круг. Отмените команду в первом окне сочетанием Ctrl+C, она завершится сообщением «ОШИБКА:  выполнение оператора отменено по запросу пользователя». Слот при этом не создаётся, подписка тоже.

Обойти зависание можно, создав слот заранее отдельной командой и запретив подписке создавать его:

```sql
\c pub
SELECT pg_create_logical_replication_slot('s', 'pgoutput');
\c sub
CREATE SUBSCRIPTION s CONNECTION 'port=5432 dbname=pub' PUBLICATION p
  WITH (create_slot = false, slot_name = 's');
```

```
 pg_create_logical_replication_slot 
------------------------------------
 (s,0/1DA1248)
(1 строка)

CREATE SUBSCRIPTION
```

Подписка создана сразу. По умолчанию при создании подписка копирует имеющиеся данные, поэтому в приёмнике уже две строки:

```sql
SELECT * FROM t;
```

```
 id | val 
----+-----
  1 | раз
  2 | два
(2 строки)
```

Изменения тоже доезжают. Добавим строку в источнике и посмотрим на приёмник:

```sql
\c pub
INSERT INTO t VALUES (3, 'три');
\c sub
SELECT * FROM t ORDER BY id;
```

```
 id | val 
----+-----
  1 | раз
  2 | два
  3 | три
(3 строки)
```

Состояние видно с двух сторон. В источнике слот логический и активный, а в приёмнике подписка включена:

```sql
\c pub
SELECT slot_name, plugin, slot_type, active FROM pg_replication_slots;
```

```
 slot_name |  plugin  | slot_type | active 
-----------+----------+-----------+--------
 s         | pgoutput | logical   | t
(1 строка)
```

К вопросам: какой уровень wal_level нужен для логической репликации; что такое публикация и подписка; почему CREATE SUBSCRIPTION зависает на том же сервере и как этого избежать.

## Пример 2. Ограничения логической репликации

Цель: убедиться, что структура таблиц не реплицируется, а для изменения и удаления строк нужен идентификатор реплики.

Добавим столбец в таблицу в источнике и вставим в него строку:

```sql
\c pub
ALTER TABLE t ADD COLUMN note text;
INSERT INTO t VALUES (4, 'четыре', 'заметка');
```

Подождите несколько секунд и посмотрите приёмник:

```sql
\c sub
SELECT * FROM t ORDER BY id;
```

```
 id | val 
----+-----
  1 | раз
  2 | два
  3 | три
(3 строки)
```

Новая строка не доехала. Причина в журнале сервера, где она повторяется, потому что подписка раз за разом пробует применить изменение:

```
ОШИБКА:  в целевом отношении логической репликации ("public.t") отсутствуют реплицируемые столбцы: "note"
```

Команда ALTER TABLE не реплицируется, структуру приёмника меняют вручную. Добавим столбец в приёмнике:

```sql
ALTER TABLE t ADD COLUMN note text;
```

Через несколько секунд подписка применит застрявшее изменение:

```sql
SELECT * FROM t ORDER BY id;
```

```
 id |  val   |  note   
----+--------+---------
  1 | раз    | 
  2 | два    | 
  3 | три    | 
  4 | четыре | заметка
(4 строки)
```

Теперь второе ограничение. Создадим таблицу без первичного ключа в обеих базах, добавим её в публикацию и обновим подписку:

```sql
\c pub
CREATE TABLE n (id int, val text);
ALTER PUBLICATION p ADD TABLE n;
\c sub
CREATE TABLE n (id int, val text);
ALTER SUBSCRIPTION s REFRESH PUBLICATION;
\c pub
INSERT INTO n VALUES (1, 'a');
```

Вставка проходит и реплицируется. Попробуем изменить и удалить строку:

```sql
UPDATE n SET val = 'b' WHERE id = 1;
DELETE FROM n WHERE id = 1;
```

```
ОШИБКА:  изменение в таблице "n" невозможно, так как в ней отсутствует идентификатор реплики, но она публикует изменения
ПОДСКАЗКА:  Чтобы эта таблица поддерживала изменение, установите REPLICA IDENTITY, выполнив ALTER TABLE.
ОШИБКА:  удаление из таблицы "n" невозможно, так как в ней отсутствует идентификатор реплики, но она публикует удаления
ПОДСКАЗКА:  Чтобы эта таблица поддерживала удаление, установите REPLICA IDENTITY, выполнив ALTER TABLE.
```

Чтобы приёмник нашёл нужную строку, источник должен передать её идентификатор: обычно это первичный ключ. Таблицы без ключа публикуют только на вставку либо задают идентификатор командой ALTER TABLE ... REPLICA IDENTITY.

Уберём подписку и базы, они больше не нужны. В psql:

```sql
\c sub
DROP SUBSCRIPTION s;
\c postgres
DROP DATABASE pub;
DROP DATABASE sub;
```

```
ЗАМЕЧАНИЕ:  слот репликации "s" удалён на сервере репликации
DROP SUBSCRIPTION
```

К вопросам: реплицируется ли изменение структуры таблицы; что делать, если подписка не может применить изменение; зачем нужен идентификатор реплики.

## Пример 3. Двунаправленная репликация между двумя серверами

Цель: настроить репликацию одной и той же таблицы в обе стороны между двумя серверами так, чтобы изменения не ходили по кругу.

На первом сервере (основной учебный кластер) создадим базу и таблицу:

```sql
CREATE DATABASE practice;
\c practice
CREATE TABLE t (id int PRIMARY KEY, val text);
INSERT INTO t VALUES (1, 'исходная');
```

Второй сервер получим клонированием из физической копии первого. Ключ -R не нужен: это не реплика, а самостоятельный кластер. В командной строке:

```bash
mkdir -p ~/practice
pg_basebackup -D ~/practice/server2
pg_ctl -D ~/practice/server2 -o "-p 5472" -l ~/practice/server2.log -w start
psql -p 5472 -d practice -c "SELECT * FROM t"
```

```
 id |   val    
----+----------
  1 | исходная
(1 строка)
```

Таблица со строкой уже есть и на втором сервере. Создадим публикации на обоих серверах. Первый сервер:

```sql
CREATE PUBLICATION p FOR TABLE t;
```

Второй сервер (psql -p 5472 -d practice):

```sql
CREATE PUBLICATION p FOR TABLE t;
```

Теперь подписки навстречу друг другу. Данные на обоих серверах уже одинаковые, поэтому копировать их повторно не нужно: copy_data = false. А origin = none говорит подписке принимать только изменения, сделанные на сервере публикации самим, а не полученные им по репликации от другого сервера. Без этого каждое изменение ходило бы по кругу. Первый сервер:

```sql
CREATE SUBSCRIPTION s_from_b CONNECTION 'port=5472 dbname=practice' PUBLICATION p
  WITH (copy_data = false, origin = none);
```

Второй сервер:

```sql
CREATE SUBSCRIPTION s_from_a CONNECTION 'port=5432 dbname=practice' PUBLICATION p
  WITH (copy_data = false, origin = none);
```

```
ЗАМЕЧАНИЕ:  на сервере публикации создан слот репликации "s_from_b"
CREATE SUBSCRIPTION
```

Сервер, на котором вы выполняете команду, создаёт слот на другом сервере, поэтому зависания, как в первом примере, здесь нет. Теперь добавим по строке на каждом сервере. Идентификаторы выбираем разные, чтобы строки не конфликтовали по первичному ключу. Первый сервер:

```sql
INSERT INTO t VALUES (2, 'с первого');
```

Второй сервер:

```sql
INSERT INTO t VALUES (3, 'со второго');
```

Через пару секунд на любом из серверов:

```sql
SELECT * FROM t ORDER BY id;
```

```
 id |    val     
----+------------
  1 | исходная
  2 | с первого
  3 | со второго
(3 строки)
```

Оба сервера содержат все три строки, причём каждая появилась ровно один раз. Изменение тоже доезжает в любую сторону. На первом сервере:

```sql
UPDATE t SET val = 'изменена на первом' WHERE id = 3;
```

На втором сервере через пару секунд:

```sql
SELECT val FROM t WHERE id = 3;
```

```
        val         
--------------------
 изменена на первом
(1 строка)
```

Двунаправленная репликация не разрешает конфликты: если одну и ту же строку одновременно изменить на обоих серверах или вставить строки с одним ключом, подписка остановится с ошибкой и будет повторять попытки, пока вы не поправите данные. Поэтому каждый сервер должен писать в свой набор строк.

К вопросам: зачем нужны copy_data = false и origin = none; чем двунаправленная репликация отличается от физической; что происходит при конфликте.

## Уборка

Удалите подписки на обоих серверах. Первый сервер:

```sql
DROP SUBSCRIPTION s_from_b;
```

Второй сервер:

```sql
DROP SUBSCRIPTION s_from_a;
```

Остановите второй сервер и удалите его, в командной строке:

```bash
pg_ctl -D ~/practice/server2 stop
rm -r ~/practice
```

На первом сервере удалите базу и верните уровень журнала, перезапустите кластер:

```sql
\c postgres
DROP DATABASE practice;
ALTER SYSTEM RESET wal_level;
```
