# Практикум. Низкоуровневое хранение

Примеры повторяют практику курса к теме: расположение файлов таблицы, индекса и последовательности, утилита oid2name, слой init нежурналируемой таблицы, стратегии хранения и TOAST, размер базы данных и сжатие длинных значений. Выполняйте на учебном кластере, не на рабочем сервере. Понадобятся окно psql под суперпользователем postgres и окно командной строки.

Подготовка, в psql:

```sql
CREATE DATABASE practice;
\c practice
```

Для примера 1 нужен пустой каталог для табличного пространства, как в практикуме темы 10. На Debian и Ubuntu, в командной строке:

```bash
sudo mkdir /var/lib/postgresql/ts
sudo chown postgres: /var/lib/postgresql/ts
```

Номера oid, размеры и время у вас будут другими.

## Расположение файлов таблицы, индекса и последовательности

Создадим таблицу с первичным ключом и identity-столбцом, загрузим данные и выполним очистку. VACUUM запускайте вне блока BEGIN/COMMIT.

```sql
CREATE TABLE t (
    id integer PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    n numeric
);
INSERT INTO t(n) SELECT id FROM generate_series(1, 10_000) AS id;
VACUUM t;
SHOW data_directory;
SELECT pg_relation_filepath('public.t');
SELECT oid FROM pg_database WHERE datname = current_database();
SELECT oid, relfilenode FROM pg_class WHERE oid = 'public.t'::regclass;
```

Например, путь base/16390/16392 отсчитывается от PGDATA: base соответствует табличному пространству pg_default, 16390 — OID базы, 16392 — filenode таблицы. OID таблицы и filenode — разные идентификаторы: после VACUUM FULL filenode меняется, а OID сохраняется. Схемы отдельными каталогами не представлены.

Посмотрим основной слой, карту свободного пространства и карту видимости. В командной строке подставьте свой PGDATA из SHOW data_directory и свой путь из pg_relation_filepath:

```bash
sudo -u postgres sh -c 'ls -l /var/lib/postgresql/16/main/base/16390/16392*'
```

В этом примере после загрузки и VACUUM у таблицы будут файлы 16392, 16392_fsm и 16392_vm. Размеры могут отличаться; слой init у обычной журналируемой таблицы отсутствует.

Индекс первичного ключа и последовательность identity — отдельные отношения со своими файлами. В psql:

```sql
\d public.t
SELECT pg_relation_filepath('public.t_pkey');
SELECT pg_get_serial_sequence('public.t', 'id');
SELECT pg_relation_filepath(pg_get_serial_sequence('public.t', 'id'));
```

Функция pg_get_serial_sequence работает и для SERIAL, и для IDENTITY. Она возвращает имя связанной со столбцом последовательности, а pg_relation_filepath получает путь к её основному файлу. Для просмотра файлов индекса и последовательности повторите ls с полученными путями. У индекса нет карты видимости. У небольшого B-tree в этом опыте файл _fsm может отсутствовать; индексы поддерживают карту свободного пространства в зависимости от метода доступа.

## Поиск объектов утилитой oid2name

oid2name — утилита командной строки из contrib, а не SQL-расширение, устанавливаемое через CREATE EXTENSION. Она подключается к серверу и сопоставляет объекты с OID и filenode. На Debian/Ubuntu команда может находиться в /usr/lib/postgresql/16/bin/oid2name. Укажите свои параметры подключения, если они отличаются от стандартных.

В командной строке:

```bash
sudo -u postgres /usr/lib/postgresql/16/bin/oid2name
sudo -u postgres /usr/lib/postgresql/16/bin/oid2name -d practice
sudo -u postgres /usr/lib/postgresql/16/bin/oid2name -d practice -i
sudo -u postgres /usr/lib/postgresql/16/bin/oid2name -d practice -t t
```

Без -d выводятся базы и их OID. С -d practice — таблицы этой базы. Ключ -i добавляет индексы и последовательности, а -S — системные объекты. Поэтому вывод команды без этих ключей нельзя называть списком всех объектов базы.

Ключ -t ищет по имени таблицы (шаблон LIKE), -o — по OID объекта, -f — по filenode. Например, для файла с номером 16392, полученным выше:

```bash
sudo -u postgres /usr/lib/postgresql/16/bin/oid2name -d practice -f 16392
```

Подставьте свой filenode. Суффиксы слоя и сегмента (_fsm, _vm, .1) в значение -f не входят. Поиск ограничен выбранной базой; при пользовательских табличных пространствах учитывайте также табличное пространство файла.

Завершив опыт, в psql удалите таблицу: зависимые индекс и identity-последовательность удалятся вместе с ней.

```sql
DROP TABLE t;
```

К вопросам: как устроен путь pg_relation_filepath; чем OID отличается от filenode; как получить файл identity-последовательности; как включить индексы и последовательности в oid2name.

## Пример 1. Слой init нежурналируемой таблицы

Цель: увидеть файл слоя init у нежурналируемой таблицы в пользовательском табличном пространстве.

```sql
CREATE TABLESPACE ts LOCATION '/var/lib/postgresql/ts';
CREATE UNLOGGED TABLE u (id int) TABLESPACE ts;
SELECT pg_relation_filepath('u');
```

```
            pg_relation_filepath
---------------------------------------------
 pg_tblspc/16634/PG_16_202307071/16633/16635
(1 строка)
```

Путь указан относительно PGDATA. В командной строке посмотрим файлы таблицы:

```bash
sudo ls -l /var/lib/postgresql/ts/PG_16_202307071/16633/
```

```
-rw------- 1 postgres postgres 0 ... 16635
-rw------- 1 postgres postgres 0 ... 16635_init
```

Рядом с основным слоем лежит слой init с суффиксом _init. После сбоя сервер заменяет им основной слой: нежурналируемая таблица становится пустой.

Удаляем табличное пространство:

```sql
DROP TABLESPACE ts;
```

```
ОШИБКА:  табличное пространство "ts" не пусто
```

Сначала нужно удалить или перенести таблицу:

```sql
DROP TABLE u;
DROP TABLESPACE ts;
```

К вопросам: для каких объектов существует слой инициализации; что происходит с нежурналируемой таблицей после сбоя.

## Пример 2. Стратегия хранения и TOAST

Цель: увидеть, какие значения уходят в toast-таблицу при стратегии external.

```sql
CREATE TABLE s (val text);
\d+ s
```

```
                                                      Таблица "public.s"
 Столбец | Тип  | Правило сортировки | Допустимость NULL | По умолчанию | Хранилище | Сжатие | Цель для статистики | Описание
---------+------+--------------------+-------------------+--------------+-----------+--------+---------------------+----------
 val     | text |                    |                   |              | extended  |        |                     |
Метод доступа: heap
```

Для text по умолчанию действует стратегия extended: длинное значение сначала сжимается, а если и сжатое не помещается, уходит в toast-таблицу. Стратегия external отправляет длинное значение в toast-таблицу без сжатия.

```sql
SELECT reltoastrelid::regclass FROM pg_class WHERE relname = 's';
ALTER TABLE s ALTER COLUMN val SET STORAGE external;
INSERT INTO s VALUES ('короткая строка'), (repeat('длинная строка ', 1000));
SELECT length(val), pg_column_size(val) FROM s;
```

```
      reltoastrelid
-------------------------
 pg_toast.pg_toast_16638
(1 строка)

 length | pg_column_size
--------+----------------
     15 |             30
  15000 |          28000
(2 строки)
```

Строки в UTF-8: русская буква занимает два байта, поэтому байтов почти вдвое больше, чем символов. Подставьте имя своей toast-таблицы и посмотрите, что в ней лежит:

```sql
SELECT chunk_id, chunk_seq, length(chunk_data)
FROM pg_toast.pg_toast_16638
ORDER BY chunk_id, chunk_seq;
```

```
 chunk_id | chunk_seq | length
----------+-----------+--------
    16643 |         0 |   1996
    16643 |         1 |   1996
...
    16643 |        13 |   1996
    16643 |        14 |     56
(15 строк)
```

В toast-таблице одно значение — длинная строка, нарезанная на 15 фрагментов примерно по 2 КБ. Короткая строка осталась в самой таблице: TOAST включается, только когда версия строки больше порога около 2 КБ.

К вопросам: что такое TOAST; что верно для TOAST.

## Пример 3. Размер базы данных и сумма размеров таблиц

Цель: сравнить размер базы данных с суммой размеров её таблиц и объяснить разницу.

```sql
DROP TABLE s;
SELECT pg_database_size('practice') AS db_size,
       sum(pg_total_relation_size(oid)) AS tables_size
FROM pg_class WHERE relkind IN ('r', 'm');
```

```
 db_size | tables_size
---------+-------------
 7886515 |     8306688
(1 строка)
```

Своих таблиц в базе нет, а таблицы системного каталога занимают даже больше, чем вся база. Дело в общих для кластера таблицах каталога:

```sql
SELECT relisshared, count(*), sum(pg_total_relation_size(oid)) AS size
FROM pg_class WHERE relkind IN ('r', 'm')
GROUP BY relisshared;
```

```
 relisshared | count |  size
-------------+-------+---------
 f           |    57 | 7725056
 t           |    11 |  581632
(2 строки)
```

Одиннадцать таблиц, например pg_database, pg_authid и pg_tablespace, общие для всего кластера. Они видны из любой базы, но хранятся в табличном пространстве pg_global, а не в каталоге базы, поэтому в pg_database_size не входят. Без них таблицы занимают 7725056 байт, примерно на 158 КБ меньше размера базы. Разница — служебные файлы в каталоге базы, прежде всего pg_internal.init, кеш описаний системных таблиц.

Итог: даже пустая база занимает несколько мегабайт из-за собственного системного каталога.

Проверим, с какими методами сжатия собран сервер. Строка параметров configure длинная, поэтому разбиваем её на части:

```sql
SELECT opt
FROM pg_config, string_to_table(setting, ' ') AS opt
WHERE name = 'CONFIGURE' AND opt LIKE '%lz4%';
SHOW default_toast_compression;
```

```
     opt
--------------
 '--with-lz4'
...
 default_toast_compression
---------------------------
 pglz
(1 строка)
```

Ключ --with-lz4 означает, что сервер поддерживает lz4. pglz встроен всегда, он и используется по умолчанию.

К вопросам: почему pg_database_size возвращает больше, чем сумма размеров пользовательских таблиц.

## Пример 4. Сжатие pglz и lz4

Цель: сравнить размер таблицы и время загрузки одного и того же длинного значения без сжатия и с каждым из методов.

Текст для опыта получим из исполняемого файла postgres, переведя его в Base32. Ключ -w0 отменяет переносы строк, получается одна строка. В командной строке:

```bash
base32 -w0 /usr/lib/postgresql/16/bin/postgres > /tmp/postgres.txt
ls -l /tmp/postgres.txt
```

Файл больше 10 МБ. В psql создадим три таблицы: без сжатия (стратегия external), со сжатием pglz и со сжатием lz4:

```sql
CREATE TABLE t_none (data text);
ALTER TABLE t_none ALTER COLUMN data SET STORAGE external;
CREATE TABLE t_pglz (data text COMPRESSION pglz);
CREATE TABLE t_lz4 (data text COMPRESSION lz4);
\timing on
\copy t_none FROM '/tmp/postgres.txt'
\copy t_pglz FROM '/tmp/postgres.txt'
\copy t_lz4 FROM '/tmp/postgres.txt'
\timing off
```

```
COPY 1
Время: 385,151 мс
COPY 1
Время: 738,515 мс
COPY 1
Время: 211,291 мс
```

Каждая команда загружает весь файл как одно значение: в нём одна строка без табуляций.

```sql
SELECT relname, pg_size_pretty(pg_total_relation_size(oid))
FROM pg_class WHERE relname LIKE 't\_%' ORDER BY relname;
```

```
 relname | pg_size_pretty
---------+----------------
 t_lz4   | 8856 kB
 t_none  | 14 MB
 t_pglz  | 8656 kB
(3 строки)
```

```sql
SELECT 'none' AS method, pg_column_size(data), pg_column_compression(data) FROM t_none
UNION ALL
SELECT 'pglz', pg_column_size(data), pg_column_compression(data) FROM t_pglz
UNION ALL
SELECT 'lz4', pg_column_size(data), pg_column_compression(data) FROM t_lz4;
```

```
 method | pg_column_size | pg_column_compression
--------+----------------+-----------------------
 none   |       14042744 |
 pglz   |        8491607 | pglz
 lz4    |        8694399 | lz4
(3 строки)
```

Оба метода сжали значение примерно до 60 % исходного размера, pglz чуть сильнее. Зато lz4 загрузил данные в три с лишним раза быстрее pglz и даже быстрее, чем загрузка без сжатия: записывать на диск пришлось меньше. Время на вашей машине будет другим, но соотношение обычно такое же: lz4 быстрее, сжатие у методов близкое.

Сжатие задаётся для столбца предложением COMPRESSION или для всех новых значений параметром default_toast_compression.

К вопросам: методы сжатия TOAST; параметр default_toast_compression; проверка поддержки lz4 через SQL. Приведённые размеры и время иллюстрируют один опыт: степень сжатия зависит от данных, скорость — также от кеша, процессора и диска.

\c postgres
