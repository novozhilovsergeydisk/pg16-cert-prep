# Практикум. Планировщик и EXPLAIN

Примеры собраны из раздела «Практикум» материала к теме: как читать план и откуда берётся стоимость, как доля строк меняет способ доступа, как work_mem меняет сортировку. Выполняйте на учебном кластере или в отдельной базе учебного сервера, не на рабочем, в psql под суперпользователем postgres. Хватит одного окна psql.

Вывод получен на PostgreSQL 16 в Linux. Время выполнения у вас будет другим, а стоимости совпадут, если таблица и настройки те же.

Подготовка, таблица из главы 1 материала:

```sql
CREATE DATABASE lab;
\c lab
CREATE TABLE t (id int PRIMARY KEY, val text);
INSERT INTO t SELECT g, 'строка ' || g FROM generate_series(1, 100000) AS g;
ANALYZE t;
```

## Пример 1. Как читать план и откуда стоимость

Цель: найти в плане узел, стоимость, число строк и ширину, пересчитать стоимость полного чтения по формуле и сравнить оценку с фактом.

Сначала размер таблицы по статистике и цены, которыми пользуется планировщик:

```sql
SELECT relpages, reltuples FROM pg_class WHERE relname = 't';
SHOW seq_page_cost;
SHOW cpu_tuple_cost;
SHOW cpu_operator_cost;
```

```
 relpages | reltuples 
----------+-----------
      637 |    100000
(1 строка)

 seq_page_cost 
---------------
 1
(1 строка)

 cpu_tuple_cost 
----------------
 0.01
(1 строка)

 cpu_operator_cost 
-------------------
 0.0025
(1 строка)
```

Теперь план полного чтения таблицы:

```sql
EXPLAIN SELECT * FROM t;
```

```
                        QUERY PLAN                        
----------------------------------------------------------
 Seq Scan on t  (cost=0.00..1637.00 rows=100000 width=22)
(1 строка)
```

Узел Seq Scan: последовательное чтение. В скобках стоимость до первой строки и до последней, ожидаемое число строк и их средняя ширина в байтах. Полная стоимость складывается из чтения страниц и обработки строк: 637 страниц по 1 плюс 100 000 строк по 0,01, итого 637 + 1000 = 1637. Ровно столько и в плане.

Добавим условие:

```sql
EXPLAIN SELECT * FROM t WHERE id > 10;
```

```
                       QUERY PLAN                        
---------------------------------------------------------
 Seq Scan on t  (cost=0.00..1887.00 rows=99990 width=22)
   Filter: (id > 10)
(2 строки)
```

Каждую строку теперь надо проверить условием: 100 000 сравнений по 0,0025 добавляют 250, получается 1887. Строк планировщик ждёт на 10 меньше.

Чтобы увидеть факт, нужен EXPLAIN ANALYZE: он выполняет запрос. Параметр BUFFERS добавляет число прочитанных страниц:

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM t WHERE id < 1000;
```

```
                                                   QUERY PLAN                                                    
-----------------------------------------------------------------------------------------------------------------
 Index Scan using t_pkey on t  (cost=0.29..40.04 rows=1014 width=22) (actual time=0.030..0.454 rows=999 loops=1)
   Index Cond: (id < 1000)
   Buffers: shared hit=11
 Planning Time: 0.100 ms
 Execution Time: 0.586 ms
(5 строк)
```

Оценка 1014 строк, факт 999: статистика точна. Время в actual указано в миллисекундах и тоже в виде «до первой строки..до последней». Строка Buffers говорит, что все 11 нужных страниц нашлись в буферном кеше (hit), с диска ничего не читалось. Изменяющие запросы под EXPLAIN ANALYZE выполняют только внутри транзакции с ROLLBACK, иначе изменение останется.

К вопросам: что означают числа в cost; чем EXPLAIN отличается от EXPLAIN ANALYZE; что показывает Buffers.

## Пример 2. Доля строк и способ доступа

Цель: увидеть, как планировщик выбирает между индексным и последовательным доступом в зависимости от того, сколько строк нужно.

Один запрос, разные доли строк:

```sql
EXPLAIN SELECT * FROM t WHERE id = 5;
EXPLAIN SELECT * FROM t WHERE id < 20000;
EXPLAIN SELECT * FROM t WHERE id > 10;
```

```
                           QUERY PLAN                            
-----------------------------------------------------------------
 Index Scan using t_pkey on t  (cost=0.29..8.31 rows=1 width=22)
   Index Cond: (id = 5)
(2 строки)

                              QUERY PLAN                               
-----------------------------------------------------------------------
 Index Scan using t_pkey on t  (cost=0.29..705.94 rows=20037 width=22)
   Index Cond: (id < 20000)
(2 строки)

                       QUERY PLAN                        
---------------------------------------------------------
 Seq Scan on t  (cost=0.00..1887.00 rows=99990 width=22)
   Filter: (id > 10)
(2 строки)
```

Для одной строки индекс очевидно выгоден. Для почти всей таблицы выгоднее прочитать её подряд. Для 20 % строк здесь тоже индекс, потому что строки лежат в таблице по порядку id, и индексный доступ читает страницы подряд. На перемешанной таблице на той же доле был бы другой план, об этом глава 8 материала.

Запретим обычный индексный доступ и посмотрим, что выберет планировщик:

```sql
SET enable_indexscan = off;
EXPLAIN (ANALYZE) SELECT * FROM t WHERE id < 20000;
RESET enable_indexscan;
```

```
                                                       QUERY PLAN                                                        
-------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on t  (cost=379.58..1267.04 rows=20037 width=22) (actual time=2.469..7.252 rows=19999 loops=1)
   Recheck Cond: (id < 20000)
   Heap Blocks: exact=128
   ->  Bitmap Index Scan on t_pkey  (cost=0.00..374.57 rows=20037 width=0) (actual time=2.422..2.423 rows=19999 loops=1)
         Index Cond: (id < 20000)
 Planning Time: 0.088 ms
 Execution Time: 9.169 ms
(7 строк)
```

Сканирование по битовой карте идёт в два шага: сначала Bitmap Index Scan собирает из индекса карту нужных страниц, затем Bitmap Heap Scan читает эти страницы таблицы по порядку, 128 страниц. Его стоимость 1267 выше, чем 706 у обычного индексного доступа, поэтому без запрета его не выбрали.

Битовая карта нужна и без запретов, когда условий несколько и их надо объединить:

```sql
EXPLAIN SELECT * FROM t WHERE id < 100 OR id > 99900;
```

```
                                 QUERY PLAN                                  
-----------------------------------------------------------------------------
 Bitmap Heap Scan on t  (cost=10.16..429.63 rows=196 width=22)
   Recheck Cond: ((id < 100) OR (id > 99900))
   ->  BitmapOr  (cost=10.16..10.16 rows=196 width=0)
         ->  Bitmap Index Scan on t_pkey  (cost=0.00..5.05 rows=101 width=0)
               Index Cond: (id < 100)
         ->  Bitmap Index Scan on t_pkey  (cost=0.00..5.01 rows=96 width=0)
               Index Cond: (id > 99900)
(7 строк)
```

Две карты из двух проходов по индексу объединяются узлом BitmapOr, а таблица читается один раз.

К вопросам: когда планировщик выбирает Seq Scan, Index Scan и Bitmap Heap Scan; что делает BitmapOr; зачем нужны параметры enable_*.

## Пример 3. Сортировка и work_mem

Цель: увидеть, как work_mem определяет, где идёт сортировка, в памяти или через временные файлы, и проверить, что больше памяти не всегда значит быстрее.

Сортировка всей таблицы с большим work_mem:

```sql
SET work_mem = '64MB';
EXPLAIN (ANALYZE) SELECT * FROM t ORDER BY val;
```

```
                                                   QUERY PLAN                                                   
----------------------------------------------------------------------------------------------------------------
 Sort  (cost=9941.82..10191.82 rows=100000 width=22) (actual time=1977.035..1990.085 rows=100000 loops=1)
   Sort Key: val
   Sort Method: quicksort  Memory: 7760kB
   ->  Seq Scan on t  (cost=0.00..1637.00 rows=100000 width=22) (actual time=0.013..20.328 rows=100000 loops=1)
 Planning Time: 0.926 ms
 Execution Time: 2000.513 ms
(6 строк)
```

Все строки поместились в память, способ quicksort, заняли 7760 КБ. Теперь урежем память до минимума:

```sql
SET work_mem = '64kB';
EXPLAIN (ANALYZE) SELECT * FROM t ORDER BY val;
```

```
                                                   QUERY PLAN                                                   
----------------------------------------------------------------------------------------------------------------
 Sort  (cost=16094.82..16344.82 rows=100000 width=22) (actual time=566.169..793.291 rows=100000 loops=1)
   Sort Key: val
   Sort Method: external merge  Disk: 3272kB
   ->  Seq Scan on t  (cost=0.00..1637.00 rows=100000 width=22) (actual time=0.014..18.547 rows=100000 loops=1)
 Planning Time: 0.091 ms
 Execution Time: 804.512 ms
(6 строк)
```

Способ external merge: строки сортируются порциями, порции пишутся во временные файлы, потом сливаются. Планировщик считает такой вариант дороже, стоимость выросла с 10 192 до 16 345. А на деле он оказался в два с половиной раза быстрее. Причина в правилах сравнения строк. В этой базе правило en_US.UTF-8, сравнение по языковым правилам дорогое. Строки вставлены по порядку id, поэтому каждая порция уже почти упорядочена по val, и её сортировка почти не требует сравнений. Подробно этот опыт разобран в главе 10 материала, в части «Опыт: когда через диск оказалось быстрее».

Проверим влияние правил сравнения: то же с побайтовым правилом C:

```sql
EXPLAIN (ANALYZE) SELECT * FROM t ORDER BY val COLLATE "C";
```

```
                                                   QUERY PLAN                                                   
----------------------------------------------------------------------------------------------------------------
 Sort  (cost=20200.32..20450.32 rows=100000 width=54) (actual time=202.909..250.272 rows=100000 loops=1)
   Sort Key: val COLLATE "C"
   Sort Method: external merge  Disk: 5104kB
   ->  Seq Scan on t  (cost=0.00..1637.00 rows=100000 width=54) (actual time=0.014..34.530 rows=100000 loops=1)
 Planning Time: 0.099 ms
 Execution Time: 271.954 ms
(6 строк)
```

Тоже через диск, но втрое быстрее: побайтовое сравнение намного дешевле языкового. Наконец, если нужны только первые строки:

```sql
EXPLAIN (ANALYZE) SELECT * FROM t ORDER BY val LIMIT 10;
RESET work_mem;
```

```
                                                      QUERY PLAN                                                      
----------------------------------------------------------------------------------------------------------------------
 Limit  (cost=3797.96..3797.99 rows=10 width=22) (actual time=144.184..144.189 rows=10 loops=1)
   ->  Sort  (cost=3797.96..4047.96 rows=100000 width=22) (actual time=144.182..144.184 rows=10 loops=1)
         Sort Key: val
         Sort Method: top-N heapsort  Memory: 26kB
         ->  Seq Scan on t  (cost=0.00..1637.00 rows=100000 width=22) (actual time=0.012..20.425 rows=100000 loops=1)
 Planning Time: 0.098 ms
 Execution Time: 144.217 ms
(7 строк)
```

Способ top-N heapsort держит в памяти только десять лучших строк, 26 КБ, и укладывается даже в 64 КБ. Вывод для работы: способ сортировки виден в плане в строке Sort Method, а решает, быстрее ли станет с большим work_mem, только замер.

К вопросам: что означают quicksort, external merge и top-N heapsort; на что действует work_mem; почему правило сравнения строк влияет на скорость сортировки.
