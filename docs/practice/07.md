# Практикум. Буферный кеш и журнал

Примеры повторяют практику курса к теме: сколько журнала порождают изменения, что делает контрольная точка, чем отличаются остановка сервера в режимах fast и immediate. Выполняйте на учебном кластере, не на рабочем сервере. Понадобятся окно psql под суперпользователем postgres и окно командной строки для управления сервером.

Подготовка, в psql:

```sql
CREATE DATABASE practice;
\c practice
```

Позиции в журнале, номера процессов и время у вас будут другими.

## Пример 1. Сколько журнала порождают изменения

Цель: увидеть, что каждое изменение данных записывается в журнал, и сравнить объём журнала с размером таблицы.

Позиция записи в журнал растёт по мере работы. Запомним её в переменную psql, выполним вставку и посчитаем разницу:

```sql
CREATE TABLE t (id int, val text);
SELECT pg_current_wal_insert_lsn() AS lsn_before \gset
INSERT INTO t SELECT g, 'строка ' || g FROM generate_series(1, 100000) g;
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_insert_lsn(), :'lsn_before')) AS wal_size,
       pg_size_pretty(pg_table_size('t')) AS table_size;
```

```
 wal_size | table_size
----------+------------
 7836 kB  | 5128 kB
(1 строка)
```

Журнала записано больше, чем занимает сама таблица: в каждой журнальной записи кроме новой строки есть заголовок и сведения о том, к какой странице она относится.

Теперь удаление:

```sql
SELECT pg_current_wal_insert_lsn() AS lsn_before \gset
DELETE FROM t;
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_insert_lsn(), :'lsn_before')) AS wal_size;
```

```
 wal_size
----------
 5485 kB
(1 строка)
```

Удаление тоже порождает журнал: в каждой версии строки меняется поле xmax, и это изменение страницы должно попасть в журнал раньше самой страницы.

К вопросам: в чём главное правило журнала предзаписи; почему запись через журнал эффективнее, чем запись каждой изменённой страницы сразу на диск.

## Пример 2. Контрольная точка

Цель: увидеть процессы, которые сбрасывают данные на диск, и что меняет контрольная точка в управляющем файле.

```sql
SELECT pid, backend_type
FROM pg_stat_activity
WHERE backend_type IN ('checkpointer', 'background writer', 'walwriter');
```

```
  pid  |   backend_type
-------+-------------------
 58588 | checkpointer
 58589 | background writer
 58591 | walwriter
(3 строки)
```

checkpointer выполняет контрольные точки, background writer понемногу сбрасывает грязные буферы между ними, walwriter записывает журнал из буферов на диск.

Сведения о последней контрольной точке хранятся в управляющем файле pg_control:

```sql
SELECT checkpoint_lsn, redo_lsn, checkpoint_time FROM pg_control_checkpoint();
SELECT pg_current_wal_lsn();
```

```
 checkpoint_lsn |  redo_lsn  |    checkpoint_time
----------------+------------+------------------------
 0/1BC0F2D8     | 0/1BC0F2D8 | 2026-10-28 23:31:54+03

 pg_current_wal_lsn
--------------------
 0/1C939DB0
```

Текущая позиция журнала ушла далеко вперёд от последней контрольной точки: при сбое восстанавливать пришлось бы всё, что записано после redo_lsn. Выполним контрольную точку вручную:

```sql
CHECKPOINT;
SELECT checkpoint_lsn, redo_lsn, checkpoint_time FROM pg_control_checkpoint();
SELECT pg_walfile_name(redo_lsn) FROM pg_control_checkpoint();
```

```
 checkpoint_lsn |  redo_lsn  |    checkpoint_time
----------------+------------+------------------------
 0/1C939E08     | 0/1C939DB0 | 2026-10-28 23:32:20+03

     pg_walfile_name
--------------------------
 00000001000000000000001C
```

redo_lsn — позиция начала контрольной точки, с неё начнётся восстановление после сбоя. checkpoint_lsn — запись о завершении контрольной точки, она чуть дальше: к этому моменту все грязные буферы, изменённые до redo_lsn, уже сброшены на диск. pg_walfile_name показывает, в каком файле журнала лежит эта позиция. Файлы до него для восстановления после сбоя больше не нужны.

К вопросам: что делает контрольная точка; когда контрольная точка считается выполненной; чем процесс bgwriter отличается от checkpointer.

## Пример 3. Остановка в режимах fast и immediate

Цель: сравнить по журналу сервера, что происходит при остановке в двух режимах.

Для примера нужен каталог данных учебного кластера и его журнал сообщений. Ниже каталог данных — $PGDATA, журнал — server.log. На Debian и Ubuntu вместо pg_ctl используют pg_ctlcluster 16 main stop -m fast, а журнал лежит в /var/log/postgresql.

В psql добавим строки:

```sql
CREATE TABLE w (id int);
INSERT INTO w SELECT generate_series(1, 1000);
```

В командной строке остановим сервер в режиме fast:

```bash
pg_ctl -D $PGDATA stop -m fast
pg_controldata -D $PGDATA | grep 'Состояние кластера'
```

```
ожидание завершения работы сервера.... готово
сервер остановлен
Состояние кластера БД:                выключен
```

В журнале сервера:

```
СООБЩЕНИЕ:  получен запрос на быстрое выключение
СООБЩЕНИЕ:  прерывание всех активных транзакций
ВАЖНО:  закрытие подключения по команде администратора
СООБЩЕНИЕ:  выключение
СООБЩЕНИЕ:  начата контрольная точка: shutdown immediate
СООБЩЕНИЕ:  контрольная точка завершена: записано буферов: 951 (5.8%); ...
СООБЩЕНИЕ:  система БД выключена
```

Сервер прервал транзакции, закрыл подключения, выполнил контрольную точку и только потом остановился. Все грязные буферы на диске, управляющий файл говорит «выключен».

Запускаем:

```bash
pg_ctl -D $PGDATA -l server.log start
```

```
СООБЩЕНИЕ:  система БД была выключена: 2026-10-28 23:31:47 MSK
СООБЩЕНИЕ:  система БД готова принимать подключения
```

Восстановление не нужно: сервер сразу готов к работе.

Теперь в psql (он переподключится сам) добавим ещё строки:

```sql
INSERT INTO w SELECT generate_series(1001, 2000);
```

И остановим сервер в режиме immediate:

```bash
pg_ctl -D $PGDATA stop -m immediate
pg_controldata -D $PGDATA | grep 'Состояние кластера'
```

```
ожидание завершения работы сервера.... готово
сервер остановлен
Состояние кластера БД:                в работе
```

```
СООБЩЕНИЕ:  получен запрос на немедленное выключение
СООБЩЕНИЕ:  система БД выключена
```

Контрольной точки не было, процессы просто завершены. Управляющий файл говорит «в работе», как после сбоя. Запускаем:

```bash
pg_ctl -D $PGDATA -l server.log start
```

```
СООБЩЕНИЕ:  работа системы БД была прервана; последний момент работы: 2026-10-28 23:31:47 MSK
СООБЩЕНИЕ:  система БД была остановлена нештатно; производится автоматическое восстановление
СООБЩЕНИЕ:  запись REDO начинается со смещения 0/1BBFEA38
СООБЩЕНИЕ:  неверная длина записи в позиции 0/1BC0F2D8: ожидалось минимум 24, получено 0
СООБЩЕНИЕ:  записи REDO обработаны до смещения 0/1BC0F2B0, ...
СООБЩЕНИЕ:  начата контрольная точка: end-of-recovery immediate wait
СООБЩЕНИЕ:  контрольная точка завершена: ...
СООБЩЕНИЕ:  система БД готова принимать подключения
```

Сервер прочитал журнал с позиции последней контрольной точки и повторил записанные изменения. Строка «неверная длина записи» — не ошибка: так сервер находит конец журнала. После восстановления выполнена контрольная точка.

```sql
SELECT count(*) FROM w;
```

```
 count
-------
  2000
(1 строка)
```

Зафиксированные строки на месте: они были в журнале, хотя страницы таблицы на диск не попали.

К вопросам: что делает сервер при остановке в режиме fast; какие транзакции после восстановления считаются оборванными.
