# Практикум. Блокировки строк

Практика по остальным вопросам раздела — резервные копии, PITR, мониторинг, репликация, ACID, место на диске, планы — есть в «Материале для изучения». Здесь примеры к вопросам о режимах блокировок строк.

Выполняйте на учебном кластере, не на рабочем сервере. Понадобятся четыре окна терминала с psql, во всех — одна и та же база.

Подготовка, в любом окне:

```sql
CREATE DATABASE practice;
```

Затем в каждом окне:

```sql
\c practice
```

Номера процессов в выводе у вас будут другими. Узнать номер процесса своего окна можно запросом SELECT pg_backend_pid();

## Пример 1. Очередь писателей и блокировка версии строки

Цель: увидеть, как PostgreSQL выстраивает в очередь несколько транзакций, которые хотят изменить одну строку.

Терминал 1:

```sql
CREATE TABLE t (id int PRIMARY KEY, val text);
INSERT INTO t VALUES (100, 'исходное');
BEGIN;
UPDATE t SET val = 'первый' WHERE id = 100;
```

Терминал 2:

```sql
BEGIN;
UPDATE t SET val = 'второй' WHERE id = 100;
```

Терминал 2 завис. Он увидел в xmax строки номер незавершённой транзакции Терминала 1, взял блокировку самой версии строки и ждёт завершения этой транзакции.

Терминал 3:

```sql
BEGIN;
UPDATE t SET val = 'третий' WHERE id = 100;
```

Терминал 3 тоже завис. Ждать транзакцию Терминала 1 вместе с Терминалом 2 он не может: тогда было бы неясно, кто получит строку следующим. Поэтому он встаёт в очередь за блокировкой версии строки, которую держит Терминал 2.

Терминал 4, блокировки версии строки:

```sql
SELECT pid, locktype, relation::regclass, mode, granted
FROM pg_locks
WHERE relation = 't'::regclass AND locktype = 'tuple';
```

```
  pid  | locktype | relation |     mode      | granted
-------+----------+----------+---------------+---------
 53646 | tuple    | t        | ExclusiveLock | t
 53647 | tuple    | t        | ExclusiveLock | f
(2 строки)
```

Строк две. Терминал 2 блокировку версии строки получил (granted = t), Терминал 3 её ждёт (granted = f). А кого ждёт сам Терминал 2:

```sql
SELECT pid, locktype, mode, granted
FROM pg_locks
WHERE locktype = 'transactionid' AND NOT granted;
```

```
  pid  |   locktype    |   mode    | granted
-------+---------------+-----------+---------
 53646 | transactionid | ShareLock | f
(1 строка)
```

Терминал 2 ждёт завершения транзакции Терминала 1. Блокировка версии строки живёт в памяти, в pg_locks, лишь пока строится очередь; сама блокировка строки записана в её версии, в поле xmax.

Терминал 1:

```sql
COMMIT;
```

Терминал 2 отвис и выполнил свой UPDATE. Терминал 4, тот же запрос к pg_locks с locktype = 'tuple':

```
 pid | locktype | relation | mode | granted
-----+----------+----------+------+---------
(0 строк)
```

Очередь за версией строки опустела: Терминал 3 теперь просто ждёт транзакцию Терминала 2, это видно запросом с locktype = 'transactionid'.

Терминал 2:

```sql
COMMIT;
```

Терминал 3 отвис. Терминал 3:

```sql
COMMIT;
SELECT * FROM t;
```

```
 id  |  val
-----+--------
 100 | третий
(1 строка)
```

Изменения применились по очереди: первый, второй, третий.

К вопросам: какую блокировку строки берёт UPDATE и DELETE; что видно в pg_locks при ожидании.

## Пример 2. Проверка внешнего ключа берёт FOR KEY SHARE

Цель: увидеть, что незавершённая вставка в дочернюю таблицу не мешает менять обычные столбцы родительской строки, но не даёт её удалить или поменять ключ.

Терминал 1:

```sql
CREATE TABLE parent (id int PRIMARY KEY, name text);
CREATE TABLE child (id int PRIMARY KEY, parent_id int REFERENCES parent);
INSERT INTO parent VALUES (1, 'один'), (2, 'два');
BEGIN;
INSERT INTO child VALUES (10, 1);
```

Проверка внешнего ключа заблокировала родительскую строку с id = 1 в режиме FOR KEY SHARE.

Терминал 2:

```sql
UPDATE parent SET name = 'первый' WHERE id = 1;
```

```
UPDATE 1
```

Не ждёт: обычный UPDATE берёт FOR NO KEY UPDATE, а он совместим с FOR KEY SHARE.

```sql
DELETE FROM parent WHERE id = 1;
```

Терминал 2 завис: удаление берёт FOR UPDATE, а с ним FOR KEY SHARE несовместим.

Терминал 3:

```sql
SELECT pid, pg_blocking_pids(pid), wait_event, query
FROM pg_stat_activity
WHERE datname = 'practice' AND wait_event_type = 'Lock';
```

```
  pid  | pg_blocking_pids |  wait_event   |              query
-------+------------------+---------------+----------------------------------
 55852 | {55851}          | transactionid | DELETE FROM parent WHERE id = 1;
(1 строка)
```

Блокировки строк хранятся в самих версиях строк, поэтому в pg_locks их не видно: видно, что Терминал 2 ждёт транзакцию Терминала 1.

Терминал 1:

```sql
ROLLBACK;
```

Терминал 2 отвис: DELETE 1. Вставка отменена, ссылки на строку не осталось, удаление прошло.

Теперь изменение ключа. Терминал 1:

```sql
BEGIN;
INSERT INTO child VALUES (20, 2);
```

Терминал 2:

```sql
UPDATE parent SET id = 3 WHERE id = 2;
```

Терминал 2 завис: изменение ключа тоже берёт FOR UPDATE.

Терминал 1:

```sql
COMMIT;
```

Терминал 2:

```
ОШИБКА:  UPDATE или DELETE в таблице "parent" нарушает ограничение внешнего ключа "child_parent_id_fkey" таблицы "child"
ПОДРОБНОСТИ:  На ключ (id)=(2) всё ещё есть ссылки в таблице "child".
```

Дождавшись, UPDATE увидел зафиксированную ссылку на ключ 2 и завершился ошибкой.

К вопросам: в каком режиме проверка внешнего ключа блокирует родительскую строку; какие действия не ждут FOR KEY SHARE.

## Пример 3. FOR SHARE и FOR KEY SHARE

Цель: сравнить два разделяемых режима на одной строке.

Терминал 1:

```sql
CREATE TABLE s (id int PRIMARY KEY, val text);
INSERT INTO s VALUES (1, 'исходное');
BEGIN;
SELECT * FROM s WHERE id = 1 FOR KEY SHARE;
```

Терминал 2:

```sql
BEGIN;
SELECT * FROM s WHERE id = 1 FOR SHARE;
COMMIT;
UPDATE s SET val = 'обычный UPDATE' WHERE id = 1;
```

Ни одна команда не ждёт: FOR SHARE совместим с FOR KEY SHARE, обычный UPDATE — тоже.

Терминал 1:

```sql
COMMIT;
BEGIN;
SELECT * FROM s WHERE id = 1 FOR SHARE;
```

Терминал 2:

```sql
UPDATE s SET val = 'после FOR SHARE' WHERE id = 1;
```

Терминал 2 завис: FOR SHARE не пропускает и обычный UPDATE.

Терминал 1:

```sql
COMMIT;
```

Терминал 2 отвис: UPDATE 1.

Терминал 1:

```sql
BEGIN;
SELECT * FROM s WHERE id = 1 FOR KEY SHARE;
```

Терминал 2:

```sql
DELETE FROM s WHERE id = 1;
```

Терминал 2 завис: удаление FOR KEY SHARE тоже не пропускает.

Терминал 1:

```sql
COMMIT;
```

Терминал 2 отвис: DELETE 1.

Итог: оба режима защищают строку от удаления и изменения ключа; FOR SHARE вдобавок запрещает обычный UPDATE.

Кто кого ждёт:

- FOR KEY SHARE ждёт только FOR UPDATE;
- FOR SHARE ждёт FOR NO KEY UPDATE и FOR UPDATE;
- FOR NO KEY UPDATE (обычный UPDATE) ждёт FOR SHARE, FOR NO KEY UPDATE и FOR UPDATE;
- FOR UPDATE (DELETE, изменение ключа) ждёт все четыре режима.

К вопросам: чем FOR SHARE отличается от FOR KEY SHARE; какую блокировку берёт DELETE.
