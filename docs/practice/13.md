# Практикум. Разграничение доступа

Примеры повторяют практику курса к теме: роли, привилегии на схему, привилегии по умолчанию, наследование прав. Выполняйте на учебном кластере, не на рабочем сервере, в psql под суперпользователем postgres. Хватит одного окна терминала.

Подготовка:

```sql
CREATE DATABASE practice;
\c practice
```

Роли создаются на весь кластер, поэтому в конце их нужно удалить отдельно (см. «Уборку»).

## Пример 1. Роли и привилегии на схему

Цель: настроить две группы пользователей — writer с полным доступом и reader только для чтения.

```sql
CREATE ROLE writer;
CREATE ROLE reader;
REVOKE ALL ON SCHEMA public FROM public;
GRANT CREATE, USAGE ON SCHEMA public TO writer;
GRANT USAGE ON SCHEMA public TO reader;
```

Псевдороль public включает все роли, поэтому сначала у неё отзывают права на схему. Затем writer получает обе привилегии схемы, а reader — только USAGE: обращаться к объектам схемы можно, создавать новые нельзя.

Пользователи, которые входят в эти группы:

```sql
CREATE ROLE w1 LOGIN IN ROLE writer;
CREATE ROLE r1 LOGIN IN ROLE reader;
```

К вопросам: что разрешает привилегия USAGE на схему; что такое public в контексте ролей.

## Пример 2. Привилегии по умолчанию и проверка доступа

Цель: сделать так, чтобы reader автоматически получал чтение новых таблиц writer, и проверить права под w1 и r1.

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE writer IN SCHEMA public GRANT SELECT ON TABLES TO reader;
```

Таблицу создаём от имени writer:

```sql
SET ROLE writer;
CREATE TABLE t (id int, val text);
INSERT INTO t VALUES (1, 'от writer');
RESET ROLE;
\dp t
```

```
                                  Права доступа
 Схема  | Имя |   Тип   |     Права доступа      | Права для столбцов | Политики
--------+-----+---------+------------------------+--------------------+----------
 public | t   | таблица | writer=arwdDxtm/writer+|                    |
        |     |         | reader=r/writer        |                    |
(1 строка)
```

Владелец writer имеет все привилегии, reader получил чтение (r) сразу при создании таблицы — это сработали привилегии по умолчанию.

Проверка под r1:

```sql
SET ROLE r1;
SELECT * FROM t;
```

```
 id |    val
----+-----------
  1 | от writer
(1 строка)
```

```sql
INSERT INTO t VALUES (2, 'от r1');
```

```
ОШИБКА:  нет доступа к таблице t
```

```sql
CREATE TABLE r1_table (id int);
```

```
ОШИБКА:  нет доступа к схеме public
```

r1 читает таблицу, но не может её менять и создавать свои таблицы в схеме.

Проверка под w1:

```sql
RESET ROLE;
SET ROLE w1;
INSERT INTO t VALUES (2, 'от w1');
DELETE FROM t WHERE id = 1;
SELECT * FROM t;
```

```
 id |  val
----+-------
  2 | от w1
(1 строка)
```

```sql
DROP TABLE t;
RESET ROLE;
```

w1 через роль writer меняет и удаляет строки и может удалить саму таблицу: её владелец — writer, а w1 в него входит.

К вопросам: почему недостаточно один раз отозвать привилегию у public; что верно для владельца объекта.

## Пример 3. NOINHERIT: права есть только после SET ROLE

Цель: увидеть, что роль с атрибутом NOINHERIT не пользуется правами включающей роли автоматически.

```sql
CREATE TABLE secret (x int);
INSERT INTO secret VALUES (42);
CREATE ROLE dba;
CREATE ROLE other;
GRANT SELECT ON secret TO dba;
CREATE ROLE bob LOGIN NOINHERIT;
GRANT USAGE ON SCHEMA public TO dba, bob;
GRANT dba TO bob;
```

USAGE на схему нужен потому, что в примере 1 права на схему у public отозваны.

Смотрим, как создалось членство:

```sql
SELECT r.rolname AS role, m.rolname AS member, am.inherit_option, am.set_option
FROM pg_auth_members am
JOIN pg_roles r ON r.oid = am.roleid
JOIN pg_roles m ON m.oid = am.member
WHERE m.rolname = 'bob';
```

```
 role | member | inherit_option | set_option
------+--------+----------------+------------
 dba  | bob    | f              | t
(1 строка)
```

Наследования нет (из-за NOINHERIT), переключаться на роль можно.

Становимся bob. SET SESSION AUTHORIZATION доступна суперпользователю и проверяет дальнейшие SET ROLE уже от имени bob:

```sql
SET SESSION AUTHORIZATION bob;
SELECT * FROM secret;
```

```
ОШИБКА:  нет доступа к таблице secret
```

```sql
SET ROLE other;
```

```
ОШИБКА:  нет прав установить роль "other"
```

```sql
SET ROLE dba;
SELECT * FROM secret;
SELECT current_user, session_user;
```

```
 x
----
 42
(1 строка)

 current_user | session_user
--------------+--------------
 dba          | bob
(1 строка)
```

Права dba у bob появились только после явного переключения, а на роль, в которую он не входит, переключиться нельзя.

```sql
RESET SESSION AUTHORIZATION;
```

К вопросам: как bob с атрибутом NOINHERIT может воспользоваться привилегиями dba.

## Уборка

```sql
\c postgres
DROP DATABASE practice;
DROP ROLE w1, r1, writer, reader, bob, dba, other;
```
