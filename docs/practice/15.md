# Практикум. Физическая репликация

Примеры повторяют практику курса к теме: потоковая физическая репликация между двумя серверами, синхронный режим и конфликты запросов на реплике. Выполняйте на учебных кластерах, не на рабочем сервере. Нужно два окна psql (основной кластер и реплика) и окно командной строки. В курсе реплика уже готова в виртуальной машине, здесь мы создаём её сами в первом примере.

Основной кластер ниже называется основным и слушает на стандартном порту. Если у него другой порт, добавляйте к командам ключ -p. Реплику создаём в каталоге ~/practice/replica и запускаем на порту 5462. Номера позиций журнала в выводе у вас будут другими.

Подготовка, в psql на основном кластере:

```sql
CREATE DATABASE practice;
\c practice
CREATE TABLE t (id int PRIMARY KEY, val text);
INSERT INTO t SELECT g, 'строка ' || g FROM generate_series(1, 3) g;
```

## Пример 1. Создание реплики и проверка работы

Цель: создать физическую реплику из копии основного кластера и убедиться, что изменения доезжают, а писать на реплике нельзя.

Реплику создаёт pg_basebackup. Ключ -R записывает в копию файл standby.signal и параметр primary_conninfo, по которому реплика будет подключаться к основному кластеру. Имя application_name нужно, чтобы основной кластер узнавал эту реплику по имени:

```bash
mkdir -p ~/practice
pg_basebackup -D ~/practice/replica -R -d "application_name=replica"
ls ~/practice/replica | grep standby
```

```
standby.signal
```

Если pg_basebackup отказывает в подключении, в pg_hba.conf основного кластера нужна строка для подключений репликации. Запускаем реплику на отдельном порту:

```bash
pg_ctl -D ~/practice/replica -o "-p 5462" -l ~/practice/replica.log -w start
```

Проверим на реплике, что она в режиме восстановления и видит данные:

```bash
psql -p 5462 -d practice -Atc "SELECT pg_is_in_recovery()"
psql -p 5462 -d practice -c "SELECT * FROM t"
```

```
t
 id |   val    
----+----------
  1 | строка 1
  2 | строка 2
  3 | строка 3
(3 строки)
```

Добавим строку на основном кластере и посмотрим на реплике:

```bash
psql -d practice -c "INSERT INTO t VALUES (4, 'четыре')"
psql -p 5462 -d practice -Atc "SELECT count(*) FROM t"
```

```
INSERT 0 1
4
```

Строка доехала. Писать на реплике нельзя:

```bash
psql -p 5462 -d practice -c "INSERT INTO t VALUES (5, 'пять')"
```

```
ОШИБКА:  в транзакции в режиме "только чтение" нельзя выполнить INSERT
```

Состояние репликации видно на основном кластере в представлении pg_stat_replication:

```sql
SELECT application_name, state, sync_state, sent_lsn, replay_lsn FROM pg_stat_replication;
```

```
 application_name |   state   | sync_state | sent_lsn  | replay_lsn 
------------------+-----------+------------+-----------+------------
 replica          | streaming | async      | 0/3000220 | 0/3000220
(1 строка)
```

Состояние streaming значит, что реплика получает журнал потоком. Режим async: основной кластер не ждёт подтверждения от реплики, его положение sent_lsn и положение replay_lsn, до которого реплика применила журнал, могут расходиться.

К вопросам: что записывает в копию ключ -R; чем реплика отличается от основного кластера в pg_is_in_recovery; что показывает pg_stat_replication.

## Пример 2. Синхронный режим

Цель: включить синхронную репликацию и убедиться, что при остановленной реплике фиксация не завершается.

На основном кластере задаём параметры через ALTER SYSTEM и перечитываем конфигурацию. В synchronous_standby_names перечисляем имена application_name синхронных реплик:

```sql
ALTER SYSTEM SET synchronous_commit = on;
ALTER SYSTEM SET synchronous_standby_names = 'replica';
SELECT pg_reload_conf();
SELECT application_name, state, sync_state FROM pg_stat_replication;
```

```
 application_name |   state   | sync_state 
------------------+-----------+------------
 replica          | streaming | sync
(1 строка)
```

Реплика стала синхронной: sync_state изменился с async на sync. Теперь COMMIT на основном кластере вернёт управление, только когда реплика подтвердит получение журнала. Остановим реплику:

```bash
pg_ctl -D ~/practice/replica stop
```

Окно 1, основной кластер:

```sql
INSERT INTO t VALUES (7, 'семь');
```

Команда зависла: фиксация ждёт реплику, которой нет. В окне 2 посмотрим, чего она ждёт:

```sql
SELECT state, wait_event_type, wait_event, left(query, 40) AS query
FROM pg_stat_activity WHERE query LIKE 'INSERT%' AND pid <> pg_backend_pid();
SELECT count(*) FROM t WHERE id = 7;
```

```
 state  | wait_event_type | wait_event |              query              
--------+-----------------+------------+---------------------------------
 active | IPC             | SyncRep    | INSERT INTO t VALUES (7, 'семь')
(1 строка)

 count 
-------
     0
(1 строка)
```

Событие ожидания SyncRep это ожидание подтверждения от синхронной реплики. Строка с номером 7 другим сеансам пока не видна: транзакция ещё не зафиксирована для них. Запустим реплику снова:

```bash
pg_ctl -D ~/practice/replica -o "-p 5462" -l ~/practice/replica.log -w start
```

Через секунду в окне 1 появится ответ INSERT 0 1: реплика догнала журнал и подтвердила фиксацию, ожидание закончилось. Строка с номером 7 теперь есть и на реплике.

Синхронная репликация защищает от потери подтверждённых транзакций при потере основного кластера, но платой становится зависимость доступности записи от реплики. Поэтому в боевых конфигурациях синхронных реплик делают несколько.

К вопросам: что произойдёт с фиксацией при остановленной синхронной реплике; какой параметр задаёт синхронные реплики; что означает событие ожидания SyncRep.

## Пример 3. Конфликты запросов на реплике

Цель: увидеть, что долгий запрос на реплике прерывается, когда основной кластер удаляет нужные ему версии строк, и что обратная связь это предотвращает.

Сначала посмотрим текущие значения на реплике:

```sql
SHOW max_standby_streaming_delay;
SHOW hot_standby_feedback;
```

```
 max_standby_streaming_delay 
-----------------------------
 30s
(1 строка)

 hot_standby_feedback 
----------------------
 off
(1 строка)
```

По умолчанию применение журнала, конфликтующего с запросом на реплике, откладывается на 30 секунд. Отключим откладывание и перечитаем конфигурацию на реплике, в psql на реплике:

```sql
ALTER SYSTEM SET max_standby_streaming_delay = 0;
SELECT pg_reload_conf();
```

Добавим на основном кластере несколько строк:

```sql
INSERT INTO t SELECT g, 'строка ' || g FROM generate_series(10, 19) g;
```

Окно реплики. Запускаем долгий запрос: pg_sleep(1) в каждой строке растягивает его на десять секунд:

```sql
SELECT id, pg_sleep(1) FROM t WHERE id >= 10;
```

Пока запрос выполняется, в окне основного кластера удаляем часть строк и запускаем очистку:

```sql
DELETE FROM t WHERE id >= 10 AND id < 15;
VACUUM t;
```

Почти сразу запрос на реплике обрывается:

```
ОШИБКА:  выполнение оператора отменено из-за конфликта с процессом восстановления
ПОДРОБНОСТИ:  Запросу пользователя нужно было видеть версии строк, которые должны быть удалены.
```

Очистка удалила на основном кластере версии строк, которые нужны запросу на реплике. Реплика получила запись об этом, а откладывать применение она не может, и отменила запрос.

Включим обратную связь: реплика будет сообщать основному кластеру, какие версии строк ей ещё нужны. На реплике:

```sql
ALTER SYSTEM SET hot_standby_feedback = on;
SELECT pg_reload_conf();
```

Повторим опыт с новыми строками. Основной кластер:

```sql
INSERT INTO t SELECT g, 'строка ' || g FROM generate_series(30, 39) g;
```

Реплика:

```sql
SELECT id, pg_sleep(1) FROM t WHERE id >= 30;
```

Пока запрос работает, на основном кластере:

```sql
DELETE FROM t WHERE id >= 30 AND id < 35;
VACUUM VERBOSE t;
```

В выводе очистки нас интересует одна строка. Формулировка зависит от версии, смысл тот же:

```
версий строк: удалено: 0, осталось: 21, «мёртвых», но ещё не подлежащих удалению: 5
```

Очистка не удалила пять мёртвых версий, потому что реплика сообщила, что они ещё нужны. Запрос на реплике дошёл до конца, все десять строк выведены без ошибки. Цена обратной связи в том, что долгие запросы на реплике откладывают очистку на основном кластере, и таблицы там могут разрастаться.

К вопросам: какой параметр задаёт, как долго реплика откладывает применение конфликтующих записей; что делает hot_standby_feedback; почему обратная связь может раздувать таблицы на основном кластере.

## Уборка

На основном кластере верните параметры и перечитайте конфигурацию, в psql:

```sql
ALTER SYSTEM RESET synchronous_standby_names;
ALTER SYSTEM RESET synchronous_commit;
SELECT pg_reload_conf();
```

Остановите и удалите реплику, в командной строке:

```bash
pg_ctl -D ~/practice/replica stop
rm -r ~/practice
```

Удалите базу, в psql на основном кластере:

```sql
\c postgres
DROP DATABASE practice;
```
