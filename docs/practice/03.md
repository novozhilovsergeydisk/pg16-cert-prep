# Практикум. Конфигурирование

Примеры повторяют практику курса к теме: параметры, которые меняются только при перезапуске, ошибка в дополнительном файле конфигурации и два способа задать параметр для одного подключения. Выполняйте на учебном кластере, не на рабочем сервере. Нужны окно psql под суперпользователем postgres и окно командной строки.

Каталог данных учебного кластера ниже записан как $PGDATA, каталог дополнительных файлов конфигурации как $CONFD, журнал сервера как server.log. На Debian и Ubuntu вместо pg_ctl используют pg_ctlcluster 16 main restart, конфигурация лежит в /etc/postgresql/16/main, журнал в /var/log/postgresql. Если каталог $CONFD принадлежит другому пользователю, записывайте в него файлы через sudo tee. Тексты сообщений, пути и число параметров в выводе у вас будут другими.

Подготовка, в psql:

```sql
CREATE DATABASE practice;
\c practice
```

## Пример 1. Какие параметры требуют перезапуска

Цель: получить список параметров, которые нельзя изменить без перезапуска сервера, и сравнить их с теми, что применяются сразу.

У каждого параметра в представлении pg_settings есть контекст. Значение postmaster означает, что параметр читается при старте главного процесса и меняется только перезапуском. Посчитаем такие параметры:

```sql
SELECT count(*) FROM pg_settings WHERE context = 'postmaster';
```

```
 count 
-------
    65
(1 строка)
```

Сам список длинный. Посмотрим на несколько параметров из разных контекстов:

```sql
SELECT name, setting, unit, context
FROM pg_settings
WHERE name IN ('listen_addresses', 'max_connections', 'shared_buffers', 'wal_level',
               'work_mem', 'log_min_duration_statement')
ORDER BY context, name;
```

```
            name            |  setting  | unit |  context   
----------------------------+-----------+------+------------
 listen_addresses           | localhost |      | postmaster
 max_connections            | 100       |      | postmaster
 shared_buffers             | 16384     | 8kB  | postmaster
 wal_level                  | replica   |      | postmaster
 log_min_duration_statement | -1        | ms   | superuser
 work_mem                   | 4096      | kB   | user
(6 строк)
```

Четыре первых параметра нужны серверу при старте: число подключений, размер общей памяти, адреса, на которых слушает главный процесс, уровень журнала. Параметр work_mem с контекстом user любой пользователь меняет в своём сеансе командой SET, а log_min_duration_statement с контекстом superuser только суперпользователь. Между ними есть ещё контекст sighup: такие параметры применяются после перечитывания конфигурации без перезапуска.

К вопросам: что означает контекст postmaster в pg_settings; какие параметры нельзя изменить без перезапуска сервера; чем контексты sighup, superuser и user отличаются от postmaster.

## Пример 2. Ошибка в дополнительном файле конфигурации

Цель: сделать ошибку в параметре max_connections, посмотреть, как сервер ведёт себя при запуске и при перечитывании конфигурации, а затем исправить ошибку.

Дополнительные файлы подключаются директивой include_dir в конце postgresql.conf. На Debian и Ubuntu она уже есть и указывает на каталог conf.d рядом с postgresql.conf. Сначала узнаем, где лежит основной файл, в psql:

```sql
SHOW config_file;
```

Затем найдём в этом файле директиву, в командной строке (подставьте путь из ответа):

```bash
grep include_dir /etc/postgresql/16/main/postgresql.conf
```

Если строка с include_dir закомментирована, раскомментируйте её, укажите каталог conf.d и создайте его рядом с postgresql.conf. Дальше этот каталог записан как $CONFD, на Debian и Ubuntu это /etc/postgresql/16/main/conf.d. Создадим файл с ошибкой: значение параметра, которое не число.

```bash
export CONFD=/etc/postgresql/16/main/conf.d
echo "max_connections = сто" | sudo tee $CONFD/max_connections.conf
```

Перезапустим сервер. Он остановится, а запуститься не сможет:

```bash
pg_ctl restart -l server.log -w
pg_ctl status
```

```
ожидание завершения работы сервера.... готово
сервер остановлен
ожидание запуска сервера.... прекращение ожидания
pg_ctl: не удалось запустить сервер
Изучите протокол выполнения.
pg_ctl: сервер не работает
```

Причину надо искать в журнале. В последних строках server.log:

```bash
tail -n 3 server.log
```

```
СООБЩЕНИЕ:  система БД выключена
СООБЩЕНИЕ:  неверное значение для параметра "max_connections": "сто"
ВАЖНО:  файл конфигурации "/etc/postgresql/16/main/conf.d/max_connections.conf" содержит ошибки
```

В начале каждой строки журнала стоят время и номер процесса, здесь они опущены. Точная формулировка и путь у вас могут отличаться. Из журнала видно, какой параметр и какой файл виноваты. Исправим значение и запустим сервер:

```bash
echo "max_connections = 100" | sudo tee $CONFD/max_connections.conf
pg_ctl start -l server.log -w
```

```
ожидание запуска сервера.... готово
сервер запущен
```

```sql
\c practice
SHOW max_connections;
SELECT sourcefile, sourceline, setting FROM pg_settings WHERE name = 'max_connections';
```

```
 max_connections 
-----------------
 100
(1 строка)

                      sourcefile                     | sourceline | setting 
-----------------------------------------------------+------------+---------
 /etc/postgresql/16/main/conf.d/max_connections.conf |          1 | 100
(1 строка)
```

Столбцы sourcefile и sourceline показывают, из какого файла и из какой строки взято действующее значение. Это быстрый способ узнать, кто задал параметр.

Для сравнения вернём ошибочное значение и перечитаем конфигурацию, не перезапуская сервер:

```bash
echo "max_connections = сто" | sudo tee $CONFD/max_connections.conf
pg_ctl reload
tail -n 2 server.log
```

```
сигнал отправлен серверу
СООБЩЕНИЕ:  неверное значение для параметра "max_connections": "сто"
СООБЩЕНИЕ:  файл конфигурации "/etc/postgresql/16/main/conf.d/max_connections.conf" содержит ошибки; были применены не зависимые изменения
```

```sql
SHOW max_connections;
```

```
 max_connections 
-----------------
 100
(1 строка)
```

Работающий сервер не падает от ошибки в файле: он пишет о ней в журнал и оставляет прежнее значение. Остановить запуск ошибка может только при старте сервера. Поэтому после правки конфигурации важно проверять журнал. Верните правильное значение и перечитайте конфигурацию:

```bash
echo "max_connections = 100" | sudo tee $CONFD/max_connections.conf
pg_ctl reload
```

К вопросам: что произойдёт при запуске сервера с ошибкой в файле конфигурации; как узнать, из какого файла взято значение параметра; как перечитать конфигурацию без перезапуска.

## Пример 3. Параметр для одного подключения и поиск postgresql.conf

Цель: задать work_mem для одного сеанса при подключении, а затем выяснить, как сервер нашёл свой файл конфигурации.

Параметр можно передать прямо при подключении двумя способами. Первый: ключ options в строке подключения.

```bash
psql "options='-c work_mem=32MB'" -c "SHOW work_mem"
```

```
 work_mem 
----------
 32MB
(1 строка)
```

Второй: переменная окружения PGOPTIONS.

```bash
PGOPTIONS='-c work_mem=32MB' psql -c "SHOW work_mem"
```

```
 work_mem 
----------
 32MB
(1 строка)
```

Другие подключения значение не получили:

```bash
psql -c "SHOW work_mem"
```

```
 work_mem 
----------
 4MB
(1 строка)
```

Источник значения видно в pg_settings. Для подключения с options там написано client:

```bash
psql "options='-c work_mem=32MB'" -c "SELECT setting, source FROM pg_settings WHERE name = 'work_mem'"
```

```
 setting | source 
---------+--------
 32768   | client
(1 строка)
```

Теперь второй вопрос практики. В пакетной установке для Ubuntu файл postgresql.conf лежит не в каталоге данных. Как сервер его находит? Подсказка в параметре config_file. Сам параметр задан в командной строке главного процесса. Номер главного процесса записан в первой строке postmaster.pid, посмотрим его командную строку:

```bash
ps -o args -p $(sudo head -n 1 $PGDATA/postmaster.pid)
```

```
COMMAND
/usr/lib/postgresql/16/bin/postgres -D /var/lib/postgresql/16/main -c config_file=/etc/postgresql/16/main/postgresql.conf
```

```sql
SHOW config_file;
SHOW data_directory;
```

```
               config_file               
-----------------------------------------
 /etc/postgresql/16/main/postgresql.conf
(1 строка)

        data_directory        
------------------------------
 /var/lib/postgresql/16/main
(1 строка)
```

Главный процесс запускают с ключом -D (каталог данных) и ключом -c config_file=... (расположение файла). Если ключа config_file нет, сервер ищет postgresql.conf в каталоге данных. В пакетах Debian и Ubuntu ключ задаёт служебная обвязка, поэтому файл оказывается в /etc/postgresql.

К вопросам: какими способами задают параметр для одного подключения; где сервер ищет postgresql.conf; какой параметр хранит расположение файла конфигурации.

## Уборка

В командной строке удалите файл с ошибкой и перечитайте конфигурацию:

```bash
sudo rm $CONFD/max_connections.conf
pg_ctl reload
```

В psql:

```sql
\c postgres
DROP DATABASE practice;
```
