# Практикум. Системные вызовы и режимы процессора

Примеры собраны из раздела «Практикум» материала к теме: время в режиме пользователя и в режиме ядра, цена сброса на диск и то, чем занят процесс PostgreSQL. Нужен Linux: команды читают /proc. Выполняйте на учебном сервере с PostgreSQL 16 из пакетов Debian или Ubuntu, не на рабочем. Второй пример пишет на диск, поэтому его запускаем от пользователя nobody во временном каталоге.

Нужно окно командной строки с правами root (через sudo) и окно psql. Время и номера процессов в выводе у вас будут другими.

## Пример 1. Время в программе и в ядре

Цель: увидеть, что много мелких системных вызовов стоят намного дороже одного крупного, даже если переданный объём одинаков.

Утилита dd копирует данные блоками: каждый блок это один вызов read и один вызов write. Скопируем мегабайт из /dev/zero в /dev/null сначала блоками по одному байту, то есть миллионом пар вызовов:

```bash
time dd if=/dev/zero of=/dev/null bs=1 count=1000000
```

```
1000000+0 records in
1000000+0 records out
1000000 bytes (1,0 MB, 977 KiB) copied, 4,78695 s, 209 kB/s

real	0m4,791s
user	0m3,510s
sys	0m1,253s
```

Теперь тот же мегабайт одним блоком:

```bash
time dd if=/dev/zero of=/dev/null bs=1000000 count=1
```

```
1+0 records in
1+0 records out
1000000 bytes (1,0 MB, 977 KiB) copied, 0,00141979 s, 704 MB/s

real	0m0,004s
user	0m0,000s
sys	0m0,004s
```

Строка user это время в режиме пользователя, sys время в режиме ядра. При побайтовом копировании вызовов два миллиона, и оба времени выросли в сотни раз: на каждый байт приходится вход в ядро и выход из него. Одним блоком работа заняла миллисекунды. Поэтому программы читают и пишут буферами, а PostgreSQL работает со страницами по 8 КБ.

К вопросам: что показывают строки user и sys у time; почему мелкие вызовы дороже крупных; зачем программы буферизуют ввод и вывод.

## Пример 2. Цена сброса на диск

Цель: измерить, сколько стоит запись с гарантией попадания на диск по сравнению с обычной записью в кеш страниц.

Утилита pg_test_fsync входит в пакет PostgreSQL и сравнивает способы сброса, из которых выбирают параметр wal_sync_method. Она создаёт временный файл, поэтому запускаем её в отдельном каталоге от пользователя nobody. Ключ -s 1 отводит на каждый тест одну секунду:

```bash
sudo mkdir -p /tmp/c-lab
sudo chown nobody:nogroup /tmp/c-lab
sudo -u nobody /usr/lib/postgresql/16/bin/pg_test_fsync -s 1 -f /tmp/c-lab/fsync.test
```

Вывод длинный. Нам нужны первая и последняя части:

```
на тест отводится 1 сек.
O_DIRECT на этой платформе поддерживается для open_datasync и open_sync.

Сравнение методов синхронизации файлов при однократной записи 8 КБ:
(в порядке предпочтения для wal_sync_method, без учёта наибольшего предпочтения fdatasync в Linux)
        open_datasync                         4,522 оп/с     221131 мкс/оп
        fdatasync                             4,049 оп/с     246986 мкс/оп
        fsync                                 2,093 оп/с     477766 мкс/оп
        fsync_writethrough                            н/д
        open_sync                             2,893 оп/с     345604 мкс/оп

Несинхронизированная запись 8 КБ:
        write                            206429,665 оп/с          5 мкс/оп
```

Запись 8 КБ без сброса заняла 5 микросекунд: данные легли в кеш страниц, и вызов сразу вернулся. Запись со сбросом через fdatasync заняла около четверти секунды: вызов ждёт, пока данные окажутся на диске. Это очень медленный учебный сервер с вращающимися дисками SMR в зеркале; на SSD сброс занимает доли миллисекунды, но разница с обычной записью всё равно в сотни раз.

Именно поэтому фиксация транзакции дорогая: COMMIT ждёт сброса журнала. Посмотрим, как это настроено:

```bash
sudo -u postgres psql -c "SHOW wal_sync_method" -c "SHOW fsync" -c "SHOW synchronous_commit"
```

```
 wal_sync_method 
-----------------
 fdatasync
(1 строка)

 fsync 
-------
 on
(1 строка)

 synchronous_commit 
--------------------
 on
(1 строка)
```

Удалите временный каталог:

```bash
sudo rm -r /tmp/c-lab
```

К вопросам: что делает вызов fsync; почему запись в кеш страниц быстрее записи на диск; какой параметр выбирает способ сброса журнала.

## Пример 3. Чем занят процесс PostgreSQL

Цель: по /proc/PID/syscall и /proc/PID/wchan определить, ждёт ли обслуживающий процесс клиента, спит или считает.

Окно psql, откройте его командой sudo -u postgres psql. Узнаем номер обслуживающего процесса:

```sql
SELECT pg_backend_pid();
```

```
 pg_backend_pid 
----------------
        3525538
(1 строка)
```

Окно командной строки. Подставьте свой номер:

```bash
B=3525538
ps -o pid,stat,cmd -p $B
sudo cat /proc/$B/syscall
sudo cat /proc/$B/wchan; echo
```

```
    PID STAT CMD
3525538 Ss   postgres: 16/main: postgres postgres [local] idle
232 0x5 0x56241e8d9a60 0x1 0xffffffff 0x0 0x0 0x7ffd1abfae28 0x7f06a9f28ee3
do_epoll_wait
```

Первое число в syscall это номер системного вызова, в котором процесс сейчас находится. На x86-64 номер 232 это epoll_wait: процесс ждёт событий на своих дескрипторах, в первую очередь команду от клиента. Четвёртое число это время ожидания в миллисекундах: 0xffffffff означает -1, то есть ждать без ограничения. Файл wchan называет функцию ядра, в которой процесс спит.

Теперь в окне psql запустим ожидание на минуту:

```sql
SELECT pg_sleep(60);
```

Пока оно идёт, повторите в командной строке:

```bash
ps -o pid,stat,cmd -p $B
sudo cat /proc/$B/syscall
```

```
    PID STAT CMD
3525538 Ss   postgres: 16/main: postgres postgres [local] SELECT
232 0xb 0x56241e840e78 0x1 0xea60 0x0 0x56241e971a60 0x7ffd1abfaa68 0x7f06a9f28ee3
```

Вызов тот же, epoll_wait, но время ожидания теперь 0xea60, то есть 60000 миллисекунд. Если ожидание по какой-то причине прерывалось и началось заново, число будет меньше: это остаток времени. Функция pg_sleep не крутится в цикле, а засыпает в ядре на заданное время. Заголовок процесса сменился на SELECT: запрос выполняется, хотя процессор не занят.

Дождитесь конца ожидания и запустите вычисление, которое занимает процессор на несколько секунд:

```sql
SELECT sum(i) FROM generate_series(1, 20000000) i;
```

Пока оно идёт:

```bash
ps -o pid,stat,cmd -p $B
sudo cat /proc/$B/syscall
```

```
    PID STAT CMD
3525538 Rs   postgres: 16/main: postgres postgres [local] SELECT
running
```

Слово running вместо номера значит, что процесс сейчас выполняется в режиме пользователя и ни в каком вызове не стоит, а буква R в STAT значит, что он выполняется или готов к выполнению. Если на сервере не хватает памяти, вы можете увидеть здесь -1 и состояние D: процесс в ядре, но не по системному вызову, а например на чтении страницы из свопа.

К вопросам: что показывает /proc/PID/syscall; чем отличается ожидание клиента от выполнения запроса по состоянию процесса; что означает состояние D.
