# Практикум. Память процесса

Примеры собраны из раздела «Практикум» материала к теме: память обычного процесса, общая память PostgreSQL и память процесса, который обслуживает ваше подключение. Нужен Linux: каталог /proc есть только там, на macOS примеры не работают. Выполняйте на учебном сервере с PostgreSQL 16 из пакетов Debian или Ubuntu, не на рабочем. Команды только читают и ничего не меняют, кроме учебной базы lab в третьем примере.

Нужно окно командной строки с правами root (через sudo) и, для третьего примера, два окна psql. Номера процессов, адреса и размеры в выводе у вас будут другими.

## Пример 1. Память обычного процесса

Цель: найти в /proc размер страницы, виртуальную и физическую память процесса, его кучу и стек.

Начнём с размера страницы памяти и лимита стека:

```bash
getconf PAGESIZE
ulimit -s
```

```
4096
8192
```

Страница 4 КБ, лимит стека 8192 КБ, то есть 8 МБ. Теперь память вашей оболочки. Переменная $$ это номер процесса оболочки:

```bash
echo $$
grep -E 'VmSize|VmRSS|VmSwap|Threads' /proc/$$/status
```

```
3523497
VmSize:	    6944 kB
VmRSS:	    3208 kB
VmSwap:	       0 kB
Threads:	1
```

VmSize это вся выделенная процессу виртуальная память, VmRSS только та её часть, которая сейчас лежит в оперативной памяти. Первое заметно больше второго: память выдаётся по требованию, и страница занимает физическую память только после первого обращения к ней.

Карта памяти процесса лежит в файле maps. Найдём в ней кучу и стек:

```bash
grep -E '\[heap\]|\[stack\]' /proc/$$/maps
```

```
5575ffb64000-5575ffb85000 rw-p 00000000 00:00 0                          [heap]
7ffc7f6b9000-7ffc7f6da000 rw-p 00000000 00:00 0                          [stack]
```

Первый столбец это диапазон адресов. Размер области равен разности конца и начала. Посчитаем его для кучи средствами самой оболочки:

```bash
echo $(( (0x5575ffb85000 - 0x5575ffb64000) / 1024 )) КБ
```

```
132 КБ
```

Куча лежит в нижней части адресов, рядом с кодом программы, а стек в верхней. Код самой программы тоже виден в начале карты:

```bash
head -n 3 /proc/$$/maps
```

```
5575c89d8000-5575c8a07000 r--p 00000000 09:00 80610586                   /usr/bin/bash
5575c8a07000-5575c8ac8000 r-xp 0002f000 09:00 80610586                   /usr/bin/bash
5575c8ac8000-5575c8b00000 r--p 000f0000 09:00 80610586                   /usr/bin/bash
```

Права r-xp у второй строки означают чтение и выполнение: это машинный код bash. Последняя буква p значит, что область частная, s означала бы общую.

К вопросам: чем VmSize отличается от VmRSS; где в /proc/PID/maps найти кучу и стек; что означают права r-xp и rw-s.

## Пример 2. Общая память PostgreSQL

Цель: найти главный процесс PostgreSQL, его общую память и сравнить её размер с shared_buffers.

Номер главного процесса записан в первой строке postmaster.pid. Посмотрим сам процесс и его дочерние процессы:

```bash
P=$(sudo head -n 1 /var/lib/postgresql/16/main/postmaster.pid)
ps -o pid,comm -p $P
ps -o pid,ppid,cmd --ppid $P
```

```
    PID COMMAND
    779 postgres
    PID    PPID CMD
    866     779 postgres: 16/main: checkpointer 
    867     779 postgres: 16/main: background writer 
   1117     779 postgres: 16/main: walwriter 
   1118     779 postgres: 16/main: autovacuum launcher 
   1119     779 postgres: 16/main: logical replication launcher 
```

Здесь показаны только служебные процессы. На сервере с подключениями ниже будут ещё строки обслуживающих процессов с именем пользователя, базы и адресом клиента. Все они дочерние процессы главного.

Общие области в карте памяти отмечены правами rw-s. Посчитаем их размеры:

```bash
sudo grep rw-s /proc/$P/maps | while read range perms offset dev inode path; do
  echo "$(( (0x${range#*-} - 0x${range%-*}) / 1024 )) КБ  $path"
done
```

```
146040 КБ  /dev/zero (deleted)
28 КБ  /dev/shm/PostgreSQL.3451390980
4 КБ  /SYSV019a11a6 (deleted)
```

Самая большая область, около 143 МБ, и есть основная общая память. Сравним с настройками:

```bash
sudo -u postgres psql -c "SHOW shared_buffers" -c "SHOW shared_memory_size"
```

```
 shared_buffers 
----------------
 128MB
(1 строка)

 shared_memory_size 
--------------------
 143MB
(1 строка)
```

Область больше, чем shared_buffers: кроме буферного кеша в ней лежат буферы журнала, таблица блокировок и другие общие структуры. Параметр shared_memory_size показывает итоговый размер, и он совпадает с тем, что мы насчитали по maps. Маленькая область в /dev/shm это динамическая общая память, которую сервер выделяет по ходу работы, например для параллельных запросов.

К вопросам: как найти главный процесс PostgreSQL; почему общая память больше shared_buffers; как в maps отличить общую область от частной.

## Пример 3. Память обслуживающего процесса

Цель: увидеть, что общая память попадает в VmRSS каждого процесса, который к ней обращался, поэтому VmRSS процессов PostgreSQL нельзя складывать.

Создадим учебную базу и таблицу, в командной строке:

```bash
sudo -u postgres psql -c "CREATE DATABASE lab"
sudo -u postgres psql -d lab -c "CREATE TABLE t (id int PRIMARY KEY, val text)" -c "INSERT INTO t SELECT g, 'строка ' || g FROM generate_series(1, 100000) AS g" -c "ANALYZE t"
```

Таблица занимает около 5 МБ. Откройте два окна psql:

```bash
sudo -u postgres psql -d lab
```

Окно 1. Узнаем номер обслуживающего процесса, передадим его оболочке и посмотрим его память. Строка VmRSS это вся физическая память процесса, RssShmem та её часть, которая приходится на общую память:

```sql
SELECT pg_backend_pid() AS pid \gset
\setenv MYPID :pid
\! grep -E 'VmRSS|RssShmem' /proc/$MYPID/status
```

```
VmRSS:	   13980 kB
RssShmem:	    5216 kB
```

Прочитаем всю таблицу и посмотрим снова:

```sql
SELECT count(*) FROM t;
\! grep -E 'VmRSS|RssShmem' /proc/$MYPID/status
```

```
 count  
--------
 100000
(1 строка)

VmRSS:	   26180 kB
RssShmem:	   16496 kB
```

Процесс прочитал страницы таблицы из буферного кеша, и эти страницы общей памяти добавились в его RssShmem. Прибавка больше размера таблицы: ядро отображает процессу и соседние страницы общей памяти, точная величина зависит от ядра. Своя, частная память процесса почти не изменилась.

Окно 2. Повторим то же самое во втором сеансе, а потом посмотрим на процесс первого окна. Его номер покажет команда \echo :pid в окне 1, подставьте его вместо PID1:

```sql
SELECT count(*) FROM t;
SELECT pg_backend_pid() AS pid \gset
\setenv MYPID :pid
\! grep -E 'VmRSS|RssShmem' /proc/$MYPID/status
\! grep -E 'VmRSS|RssShmem' /proc/PID1/status
```

```
 count  
--------
 100000
(1 строка)

VmRSS:	   26056 kB
RssShmem:	   16432 kB
VmRSS:	   26180 kB
RssShmem:	   16496 kB
```

Первые две строки относятся ко второму окну, последние две к первому.

У обоих процессов около 16 МБ общей памяти в VmRSS, но это одни и те же страницы буферного кеша, а не 32 МБ. Если сложить VmRSS всех процессов PostgreSQL, общая память будет посчитана столько раз, сколько процессов к ней обращались. Для оценки расхода памяти на подключения смотрят частную часть, а общую память считают один раз, как в примере 2.

К вопросам: почему нельзя складывать VmRSS процессов PostgreSQL; как найти память процесса, обслуживающего ваше подключение; какая память у обслуживающего процесса своя.

## Уборка

Закройте окна psql и удалите базу, в командной строке:

```bash
sudo -u postgres psql -c "DROP DATABASE lab"
```
