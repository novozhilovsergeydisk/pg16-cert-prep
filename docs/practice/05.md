# Практикум. Изоляция и многоверсионность

Примеры повторяют практику курса к теме и показывают то, о чём спрашивают вопросы темы. Выполняйте на учебном кластере, не на рабочем сервере. Понадобятся три окна терминала с psql, во всех трёх — одна и та же база.

Подготовка, в любом окне:

```sql
CREATE DATABASE practice;
```

Затем в каждом окне:

```sql
\c practice
```

Номера транзакций в выводе у вас будут другими: важно, как они соотносятся, а не сами числа.

## Пример 1. Снимок: Read Committed и Repeatable Read

Цель: увидеть, что уровни изоляции отличаются моментом создания снимка.

Терминал 1:

```sql
CREATE TABLE t (id int PRIMARY KEY, val text);
INSERT INTO t VALUES (1, 'исходное');
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT * FROM t;
```

```
 id |   val
----+----------
  1 | исходное
(1 строка)
```

Терминал 2 (без BEGIN: команда сразу фиксируется):

```sql
DELETE FROM t WHERE id = 1;
```

Терминал 1, тот же запрос ещё раз:

```sql
SELECT * FROM t;
```

```
 id | val
----+-----
(0 строк)
```

На Read Committed каждый оператор строит новый снимок, поэтому второй запрос уже видит удаление.

Терминал 1:

```sql
COMMIT;
INSERT INTO t VALUES (1, 'исходное');
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM t;
```

Терминал 2:

```sql
DELETE FROM t WHERE id = 1;
```

Терминал 1:

```sql
SELECT * FROM t;
```

```
 id |   val
----+----------
  1 | исходное
(1 строка)
```

На Repeatable Read снимок строится первым оператором транзакции и действует до её конца: удаление, зафиксированное позже, транзакция не видит.

Терминал 1:

```sql
COMMIT;
SELECT * FROM t;
INSERT INTO t VALUES (1, 'исходное');
```

После COMMIT новый запрос строки уже не находит. Вставляем её снова для следующего примера.

К вопросам: когда строится снимок на Repeatable Read; что верно для Read Committed.

## Пример 2. Версии строки: xmin и xmax

Цель: увидеть служебные поля версий и понять, почему чтение не ждёт пишущую транзакцию.

Терминал 1:

```sql
SELECT xmin, xmax, * FROM t;
```

```
 xmin | xmax | id |   val
------+------+----+----------
  786 |    0 |  1 | исходное
(1 строка)
```

Терминал 2:

```sql
BEGIN;
UPDATE t SET val = 'новое' WHERE id = 1;
SELECT pg_current_xact_id();
```

```
 pg_current_xact_id
--------------------
                787
(1 строка)
```

Терминал 1:

```sql
SELECT xmin, xmax, * FROM t;
```

```
 xmin | xmax | id |   val
------+------+----+----------
  786 |  787 |  1 | исходное
(1 строка)
```

Запрос не ждёт. Видна старая версия, но в её xmax уже номер транзакции из Терминала 2: она заменила версию, но ещё не зафиксирована.

Терминал 2, та же строка в своей транзакции:

```sql
SELECT xmin, xmax, * FROM t;
```

```
 xmin | xmax | id |  val
------+------+----+-------
  787 |    0 |  1 | новое
(1 строка)
```

Своя транзакция видит новую версию: её xmin — номер этой транзакции.

Терминал 2:

```sql
COMMIT;
```

Терминал 1:

```sql
SELECT xmin, xmax, * FROM t;
```

```
 xmin | xmax | id |  val
------+------+----+-------
  787 |    0 |  1 | новое
(1 строка)
```

Теперь откат. Терминал 2:

```sql
BEGIN;
UPDATE t SET val = 'откатим' WHERE id = 1;
ROLLBACK;
```

Терминал 1:

```sql
SELECT xmin, xmax, * FROM t;
```

```
 xmin | xmax | id |  val
------+------+----+-------
  787 |  788 |  1 | новое
(1 строка)
```

xmax не нулевой, но версия видна: транзакция 788 отменена, а статус отменённой транзакции правила видимости учитывают. Версия, созданная откатившейся транзакцией, осталась в странице, но её никто не увидит; позже её уберёт очистка.

К вопросам: что увидит транзакция, если другая изменила строку и не зафиксировала; какие версии попадут в снимок; что хранится в xmin.

## Пример 3. Два писателя: ожидание, перепроверка и ошибка сериализации

Цель: увидеть, что писатели ждут друг друга, а читатели — нет, и как ведёт себя второй UPDATE на разных уровнях.

### 3а. Read Committed

Терминал 1:

```sql
BEGIN;
UPDATE t SET val = 'от T1' WHERE id = 1;
```

Терминал 2:

```sql
SELECT * FROM t;
```

```
 id |  val
----+-------
  1 | новое
(1 строка)
```

Читатель не ждёт и видит прежнюю версию.

```sql
BEGIN;
UPDATE t SET val = 'от T2' WHERE id = 1;
```

Терминал 2 завис: строку меняет незавершённая транзакция.

Терминал 3, кто кого ждёт:

```sql
SELECT pid, pg_blocking_pids(pid), wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE datname = 'practice' AND wait_event_type = 'Lock';
```

```
  pid  | pg_blocking_pids | wait_event_type |  wait_event   |                  query
-------+------------------+-----------------+---------------+------------------------------------------
 53569 | {53568}          | Lock            | transactionid | UPDATE t SET val = 'от T2' WHERE id = 1;
(1 строка)
```

Терминал 2 ждёт завершения транзакции Терминала 1 (wait_event = transactionid).

Терминал 1:

```sql
COMMIT;
```

Терминал 2 отвис: UPDATE 1. На Read Committed он заново проверил условие на новой версии строки и изменил её.

Терминал 2:

```sql
COMMIT;
```

### 3б. Условие перестало выполняться

Терминал 1:

```sql
UPDATE t SET val = 'старое' WHERE id = 1;
BEGIN;
UPDATE t SET val = 'новое' WHERE id = 1;
```

Терминал 2:

```sql
BEGIN;
UPDATE t SET val = 'от T2' WHERE val = 'старое';
```

Терминал 2 ждёт.

Терминал 1:

```sql
COMMIT;
```

Терминал 2 отвис: UPDATE 0. После ожидания условие проверено на новой версии, а там уже 'новое'.

Терминал 2:

```sql
COMMIT;
```

### 3в. Repeatable Read

Терминал 1:

```sql
BEGIN;
UPDATE t SET val = 'от T1' WHERE id = 1;
```

Терминал 2:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM t;
UPDATE t SET val = 'от T2' WHERE id = 1;
```

SELECT вернул строку сразу, UPDATE завис.

Терминал 1:

```sql
COMMIT;
```

Терминал 2:

```
ОШИБКА:  не удалось сериализовать доступ из-за параллельного изменения
```

```sql
ROLLBACK;
```

Снимок транзакции не видит изменения Терминала 1, а менять версию, которой нет в снимке, нельзя. Транзакцию нужно повторить целиком.

К вопросам: в каком случае транзакция ждёт блокировку строки; что произойдёт при UPDATE строки, изменённой незавершённой транзакцией; что будет со вторым UPDATE после COMMIT первой транзакции.

## Пример 4. Читатель задерживает DROP TABLE

Цель: увидеть, что обычный SELECT тоже берёт блокировку — на таблицу, и она конфликтует с удалением таблицы.

Терминал 1:

```sql
BEGIN;
SELECT count(*) FROM t;
```

Терминал 2:

```sql
DROP TABLE t;
```

Терминал 2 завис.

Терминал 3:

```sql
SELECT pid, mode, granted FROM pg_locks WHERE relation = 't'::regclass;
```

```
  pid  |        mode         | granted
-------+---------------------+---------
 53568 | AccessShareLock     | t
 53569 | AccessExclusiveLock | f
(2 строки)
```

Терминал 1 держит ACCESS SHARE до конца транзакции, DROP TABLE ждёт несовместимую с ней ACCESS EXCLUSIVE.

Терминал 1:

```sql
COMMIT;
```

Терминал 2 отвис: DROP TABLE выполнена.

К вопросам: что произойдёт с DROP TABLE, пока читающая транзакция не завершена.
