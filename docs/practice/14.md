# Практикум. Резервное копирование

Примеры повторяют практику курса к теме: логическая копия утилитой pg_dump, автономная физическая копия утилитой pg_basebackup и, как в Практике+, потоковая архивация WAL утилитой pg_receivewal с восстановлением по архиву. Выполняйте на учебном кластере, не на рабочем сервере, в командной строке. Основной кластер ниже называется основным, новые кластеры, которые вы создаёте из копий, запускаются на порту 5453.

Копии складываем в каталог ~/practice. Если основной кластер слушает не на стандартном порту, добавляйте к командам psql, pg_dump, pg_basebackup и pg_receivewal ключ -p с его портом. Номера позиций журнала и время в выводе у вас будут другими.

Подготовка:

```bash
mkdir -p ~/practice
cd ~/practice
psql -c "CREATE DATABASE practice"
psql -d practice -c "CREATE TABLE t (id int PRIMARY KEY, val text)" -c "INSERT INTO t VALUES (1, 'раз'), (2, 'два'), (3, 'три')"
```

## Пример 1. Логическая копия: pg_dump

Цель: сделать логическую копию базы данных, удалить базу и восстановить её из копии.

Утилита pg_dump выводит команды SQL, которые воссоздают объекты и данные базы. Сохраним вывод в файл:

```bash
pg_dump practice > practice.sql
```

Посмотрим, что получилось. Это обычный текстовый файл с командами:

```bash
grep -E "^(CREATE|COPY|ALTER)" practice.sql
```

```
CREATE TABLE public.t (
ALTER TABLE public.t OWNER TO postgres;
COPY public.t (id, val) FROM stdin;
ALTER TABLE ONLY public.t
```

Копия не содержит самой команды CREATE DATABASE, поэтому базу перед восстановлением нужно создать. Удалим базу и восстановим её:

```bash
psql -c "DROP DATABASE practice"
psql -c "CREATE DATABASE practice"
psql -q -o /dev/null -d practice -f practice.sql
psql -d practice -c "SELECT * FROM t"
```

```
 id | val 
----+-----
  1 | раз
  2 | два
  3 | три
(3 строки)
```

Ключ -q убирает сообщения о каждой выполненной команде, а -o /dev/null отбрасывает вывод запросов: в файле есть вызовы служебных функций, результат которых не нужен. Данные вернулись.

У pg_dump есть и сжатый формат custom, который восстанавливает утилита pg_restore. Он позволяет восстанавливать отдельные объекты и в несколько потоков:

```bash
pg_dump -Fc practice -f practice.dump
psql -c "DROP DATABASE practice"
psql -c "CREATE DATABASE practice"
pg_restore -d practice practice.dump
psql -d practice -c "SELECT count(*) FROM t"
```

```
 count 
-------
     3
(1 строка)
```

Логическая копия переносима между версиями и платформами, но она сохраняет состояние базы на момент начала копирования и не позволяет вернуться к произвольному моменту. Для этого нужна физическая копия с архивом WAL.

К вопросам: что содержит файл, созданный pg_dump; какой утилитой восстанавливают копию в формате custom; что логическая копия не умеет по сравнению с физической.

## Пример 2. Автономная физическая копия: pg_basebackup

Цель: сделать физическую копию всего кластера, изменить данные и убедиться, что кластер, поднятый из копии, содержит состояние на момент копирования.

Утилита pg_basebackup копирует каталог данных работающего кластера. По умолчанию в копию попадает и WAL, который нужен, чтобы она стала согласованной, поэтому такая копия называется автономной:

```bash
pg_basebackup -D ~/practice/backup -v
```

```
pg_basebackup: начинается базовое резервное копирование, ожидается завершение контрольной точки
pg_basebackup: контрольная точка завершена
pg_basebackup: стартовая точка в журнале предзаписи: 0/3000028 на линии времени 1
pg_basebackup: запуск фонового процесса считывания WAL
pg_basebackup: создан временный слот репликации "pg_basebackup_17226"
pg_basebackup: конечная точка в журнале предзаписи: 0/30472F8
pg_basebackup: ожидание завершения потоковой передачи фоновым процессом...
pg_basebackup: сохранение данных на диске...
pg_basebackup: переименование backup_manifest.tmp в backup_manifest
pg_basebackup: базовое резервное копирование завершено
```

Теперь изменим таблицу в основном кластере. Копия уже сделана и этих изменений знать не должна:

```bash
psql -d practice -c "INSERT INTO t VALUES (4, 'четыре')"
psql -d practice -Atc "SELECT count(*) FROM t"
```

```
4
```

Восстановим новый кластер из копии. Каталог копии сам по себе готов к запуску, но чтобы не испортить копию, работаем с её дубликатом. Каталог данных должен быть доступен только владельцу:

```bash
cp -r ~/practice/backup ~/practice/restored
chmod 700 ~/practice/restored
pg_ctl -D ~/practice/restored -o "-p 5453" -l ~/practice/restored.log -w start
```

Порт 5453 нужен, чтобы новый кластер не конфликтовал с основным: настройки в копии те же. Проверим данные:

```bash
psql -p 5453 -d practice -c "SELECT * FROM t"
```

```
 id | val 
----+-----
  1 | раз
  2 | два
  3 | три
(3 строки)
```

Строки с номером 4 нет: новый кластер содержит состояние на момент окончания копирования. В журнале нового кластера видно, что сервер при запуске восстановил согласованное состояние, используя WAL из самой копии:

```bash
grep -E "восстановление копии|согласованное" ~/practice/restored.log
```

```
СООБЩЕНИЕ:  начинается восстановление копии с LSN redo 0/3000028, LSN контрольной точки 0/3047258, на линии времени 1
СООБЩЕНИЕ:  завершено восстановление копии с LSN redo 0/3000028 и конечным LSN 0/30472F8
СООБЩЕНИЕ:  согласованное состояние восстановления достигнуто в позиции 0/30472F8
```

Остановим новый кластер:

```bash
pg_ctl -D ~/practice/restored stop
```

К вопросам: что копирует pg_basebackup; почему такая копия называется автономной; что содержит файл backup_label; почему копию нельзя просто запустить в том же порту.

## Пример 3. Копия без WAL и архив pg_receivewal

Цель: организовать потоковую архивацию, сделать копию без WAL и восстановить кластер из копии и архива, включая недозаписанный сегмент.

Сначала запустим утилиту, которая получает WAL от основного кластера по протоколу репликации и складывает его в каталог. Она работает, пока её не остановят, поэтому запускаем её в отдельном окне командной строки:

```bash
mkdir ~/practice/archive
pg_receivewal -D ~/practice/archive -v
```

```
pg_receivewal: начало передачи журнала с позиции 0/5000000 (линия времени 1)
```

В другом окне сделаем копию без WAL. Ключ -X none отключает включение WAL в копию, его заменит архив:

```bash
pg_basebackup -D ~/practice/base2 -X none
```

```
ЗАМЕЧАНИЕ:  архивация WAL не настроена; вы должны обеспечить копирование всех требуемых сегментов WAL другими средствами для получения резервной копии
```

Замечание не ошибка: утилита предупреждает, что копия без WAL сама по себе не запустится. Создадим в основном кластере базу и таблицу:

```bash
psql -c "CREATE DATABASE shop"
psql -d shop -c "CREATE TABLE orders (id int, item text)" -c "INSERT INTO orders VALUES (1, 'ручка'), (2, 'тетрадь')"
ls ~/practice/archive
```

```
000000010000000000000005
000000010000000000000006
000000010000000000000007.partial
```

Имена сегментов у вас будут другими. Законченные сегменты WAL лежат в архиве под обычными именами. Сегмент, который сейчас пишется, имеет суффикс .partial: утилита переименует его, когда сегмент заполнится. Остановим pg_receivewal сочетанием клавиш Ctrl+C в её окне:

```
pg_receivewal: получен сигнал прерывания, работа завершается
pg_receivewal: файл сегмента "000000010000000000000007.partial" не переименовывается, так как он неполный
```

Все изменения основного кластера, включая базу shop, лежат в файле .partial. Сначала попробуем восстановить кластер только по законченным сегментам. Берём дубликат копии и настраиваем восстановление: команду, которой сервер достаёт сегменты из архива, и файл recovery.signal, который включает режим восстановления:

```bash
cp -r ~/practice/base2 ~/practice/repl
chmod 700 ~/practice/repl
echo "restore_command = 'cp $HOME/practice/archive/%f %p'" >> ~/practice/repl/postgresql.auto.conf
touch ~/practice/repl/recovery.signal
pg_ctl -D ~/practice/repl -o "-p 5453" -l ~/practice/repl.log -w start
psql -p 5453 -Atc "SELECT datname FROM pg_database ORDER BY 1"
```

```
postgres
practice
template0
template1
```

Базы shop нет: сервер восстановил всё, что нашёл в законченных сегментах, и на этом остановился. Недозаписанный сегмент ему не подходит по имени. Остановим кластер, удалим его и повторим, добавив в архив копию последнего сегмента без суффикса:

```bash
pg_ctl -D ~/practice/repl stop
rm -r ~/practice/repl
cp ~/practice/archive/000000010000000000000007.partial ~/practice/archive/000000010000000000000007
cp -r ~/practice/base2 ~/practice/repl
chmod 700 ~/practice/repl
echo "restore_command = 'cp $HOME/practice/archive/%f %p'" >> ~/practice/repl/postgresql.auto.conf
touch ~/practice/repl/recovery.signal
pg_ctl -D ~/practice/repl -o "-p 5453" -l ~/practice/repl2.log -w start
```

Дадим серверу несколько секунд закончить восстановление и проверим:

```bash
psql -p 5453 -Atc "SELECT datname FROM pg_database ORDER BY 1"
psql -p 5453 -d shop -c "SELECT * FROM orders"
psql -p 5453 -Atc "SELECT pg_is_in_recovery()"
```

```
postgres
practice
shop
template0
template1

 id |  item   
----+---------
  1 | ручка
  2 | тетрадь
(2 строки)

f
```

Теперь база и таблица восстановились. Когда архив закончился, сервер завершил восстановление и стал доступен для записи, об этом говорит значение f у pg_is_in_recovery. В журнале видна последовательность:

```bash
grep -E "восстановлен из архива|восстановление архива завершено" ~/practice/repl2.log
```

```
СООБЩЕНИЕ:  файл журнала "000000010000000000000006" восстановлен из архива
СООБЩЕНИЕ:  файл журнала "000000010000000000000007" восстановлен из архива
СООБЩЕНИЕ:  восстановление архива завершено
```

Файл с суффиксом .partial содержит все данные, которые успели прийти, поэтому для восстановления до последнего момента копию такого сегмента переименовывают, как сделано здесь.

К вопросам: зачем нужен архив WAL для копии без WAL; что означает суффикс .partial; что делают restore_command и recovery.signal.

## Уборка

Остановите кластер и удалите копии:

```bash
pg_ctl -D ~/practice/repl stop
rm -r ~/practice
```

В основном кластере удалите учебные базы:

```bash
psql -c "DROP DATABASE practice"
psql -c "DROP DATABASE shop"
```
