# Android PWA: автономная работа и двусторонняя синхронизация

Дата: 16 ноября 2026. Задача в локальной БД: **254**.
Статус: **реализация в работе**. Выполнены: миграция 150 (таблицы синхронизации),
серверный обмен (`src/routes/sync.js`), manifest и service worker (`public/sw.js`),
локальное хранилище на IndexedDB (`public/js/offline.js`, `offline-core.js`),
автономные учебные сценарии, режим синхронизации «Автоматически / Вручную»,
серверные и браузерные автотесты (`tests/offline-sync.test.js`,
`tests/offline-browser.test.js`). Не завершены: полная регрессия и приёмка
установки/авиарежима на физическом Android.
Для каждого этапа ниже рекомендована текущая модель с высоким уровнем рассуждения.
Согласование этого плана не является разрешением на коммит, push или выпуск.

## 1. Требование и предлагаемые границы

Пользователь подтвердил: Android PWA должна работать автономно, а при наличии
связи отправлять данные на сервер и получать изменения с него. Связь может
исчезнуть и восстановиться во время занятия. Прогресс может меняться на нескольких
устройствах. При подготовке офлайн-режима требуется первый вход с интернетом.

Предлагаемый полный объём первого выпуска:

| Возможность | Без связи | При наличии связи |
| --- | --- | --- |
| Запуск установленного приложения | Из сохранённой оболочки | Проверка обновления приложения |
| Темы, вопросы, пояснения | Все заранее загруженные темы | Получение новых редакций |
| Материалы и практикумы | Чтение сохранённых текстов | Обновление текстов |
| Тренировка и работа над ошибками | Создание и прохождение новых порций | Обмен порциями и ответами |
| «Подходит или нет» | Создание и прохождение карточек | Обмен карточками и ответами |
| Экзамен и разбор | Создание, таймер, завершение, оценка | Сохранение и повторная проверка сервером |
| Личная история и статистика | Сохранённая история плюс новые локальные результаты | Объединённый прогресс всех устройств |
| Незавершённые занятия | Восстановление после закрытия | Получение сохранённого состояния с другого устройства |
| Тема оформления и акцент | Локальное изменение | Обмен настройками профиля |
| Вход по письму, ИИ, административные данные | Понятное сообщение о необходимости связи | Нынешние серверные функции |

Практикум офлайн означает чтение инструкций; запуск PostgreSQL на Android
в эту задачу не входит. Установка — через браузер Android, без отдельного
приложения в Google Play. Начальная цель проверки — актуальный Chrome Android;
поведение в других браузерах проверяется отдельно, без обещания одинакового фона.

## 2. Что подтверждено текущим кодом

Пункты ниже описывают состояние на момент планирования; изменённые в ходе
реализации отмечены отдельно.

- Реализовано: добавлены `public/manifest.webmanifest`, service worker
  `public/sw.js` и хранилище IndexedDB (`public/js/offline.js`, `offline-core.js`).
  Основная логика страницы находится в `public/js/app.js`, вызовы API имеют
  тайм-аут 15 секунд.
- Начальная загрузка зависит от `/api/me`; ответ 401 сейчас переводит на вход.
  Серверный сеанс хранится в HttpOnly cookie, срок сеанса — 30 дней.
  Реализовано: без сети или при истёкшей cookie приложение продолжает работать
  с локальным профилем; для синхронизации после истечения сеанса нужен повторный вход.
- Порции тренировок и карточек создавал сервер. Реализовано: офлайн-каталог
  (`/api/offline/catalog`) выдаёт устройству вопросы с правильными ответами и
  пояснениями для автономной проверки; офлайн-порции и экзамены собираются на
  устройстве, серверная проверка по сохранённой версии каталога. Снимки вопросов
  сохраняются в `training_batches` и `option_check_batches`; в браузер онлайн
  до ответа правильные ответы по-прежнему не выдаются.
- Указатели на незавершённые порции и черновик экзамена сохраняются в localStorage.
  Ошибка записи черновика экзамена сейчас не мешает продолжить занятие.
- У ответов тренировки есть уникальность по порции и вопросу; у экзамена есть
  `submission_id`. Эти гарантии полезны, но не заменяют протокол синхронизации.
- Сервер проверяет экзамен по текущей таблице вопросов. Реализовано: версии
  каталога сохраняются в `offline_catalogs`, занятия по старой редакции
  проверяются по своей версии (`catalog_version` события).
- Последние ошибки и адаптивный выбор вопросов опираются на `answered_at, id`.
  Отложенную отправку нельзя выдавать за новое время выполнения ответа.
- История экзаменов ограничена 50 строками, история тренировок имеет пагинацию.
  Для полной локальной копии нужна отдельная постраничная выгрузка.
- Включены квоты снимков: 1000 порций / 50 MiB на пользователя и 500 MiB на проект;
  runtime-роль БД имеет минимальные права. Синхронизация должна учитывать эти условия.
- Запрет отдельных тем для экзамена хранится в `categories.exam_allowed`, включая
  тему сетей. Этот признак должен действовать и при локальной сборке экзамена.

## 3. Единый способ сохранения онлайн и офлайн

Предлагаю сохранять действие сначала в IndexedDB, одной транзакцией:
ответ/черновик, изменение локального прогресса и запись для отправки серверу.
Пользователь видит подтверждение сохранения только после успешного завершения
этой транзакции. Если запись не удалась, интерфейс сохраняет введённый ответ
и сообщает о проблеме, не переходит молча к следующему вопросу.

При доступном сервере обмен начинается сразу. При обрыве связи та же запись
остаётся в очереди. Возврат интернета не переключает пользователя на другой
экран и не перезапускает порцию. Серверная версия остаётся источником общего
подтверждённого состояния, а локальная копия содержит также ещё не отправленные
действия. Полученные серверные данные не затирают эту очередь.

### Хранилища на устройстве

- Cache Storage: только версионная оболочка приложения — HTML, CSS, JS, иконки.
- IndexedDB: профиль выбранного аккаунта, версии каталога и материалы,
  снимки занятий, ответы, черновики, личная история, состояние синхронизации.
- Отдельная очередь исходящих событий с UUID события, UUID занятия,
  идентификатором устройства, последовательностью устройства и версией данных.
- Локальные данные разделяются по стабильному ID пользователя, а не email.
  В очередь не сохраняются cookie, пароли, коды входа или заголовки авторизации.
- Старые черновики из localStorage переносятся после успешной записи и проверки
  IndexedDB. Исходник не удаляется до подтверждённого переноса.

### Первая загрузка

Предлагаю автоматически после входа скачивать весь актуальный учебный каталог,
материалы и личную историю. Выгрузка идёт страницами, с продолжением после обрыва.
Пакет имеет версию и контрольные суммы; новая версия становится активной только
после проверки полного набора. Старый рабочий пакет сохраняется до переключения.

Показывать готовность учебных материалов и истории отдельно: завершённая загрузка
каталога уже позволяет учиться, частичная история явно обозначается как неполная.
При первом входе без ранее загруженных данных сообщать, что сначала нужна сеть.
Объём файлов и истории измерить на этапе реализации перед проверкой устройства.

Запрашивать `navigator.storage.persist()`, проверять фактический результат
и доступное место через `estimate()`. При нехватке места можно удалить старые
неиспользуемые пакеты, но не неотправленные ответы или активные занятия.
Очистка данных приложения пользователем может удалить локальные результаты;
PWA не может гарантировать их сохранение после такой очистки.

## 4. Двусторонний протокол

### Сервер → устройство

Предлагаемые маршруты и параметры для согласования:

- `GET /api/sync/bootstrap?cursor=...`: начальный согласованный снимок личных
  данных по страницам и конечная ревизия для дальнейшего обмена.
- `GET /api/sync/changes?cursor=...`: последующие изменения личных данных,
  отметки удаления и новая ревизия.
- `GET /api/offline/catalog`: описание активного пакета, совместимость протокола,
  список частей с размерами и контрольными суммами.
- `GET /api/offline/catalog/:version/:part`: часть неизменяемого пакета.

Вход обязателен для всех маршрутов. Личные данные отбираются сервером по сеансу;
переданный клиентом ID пользователя не определяет владельца данных.
Административные и чужие данные в пакет не попадают. HTTP-кеширование личных
ответов запрещено; запись в IndexedDB выполняется явно после проверки аккаунта.

Курсор — непрозрачная серверная ревизия. Нельзя использовать время телефона или
простой `max(sequence)` без учёта незавершённых транзакций: это может пропустить
изменения. Предлагается последовательная ревизия на пользователя, обновляемая
под блокировкой строки в той же транзакции, что и изменение/журнал.
Начальный снимок тоже должен быть согласован с ревизией и последующими страницами.

Журнал пополняется при изменениях через все поддерживаемые пути записи,
включая старые онлайн-маршруты во время переходного периода. Изменения вопросов
через миграции публикуются новой версией каталога. Изменения личных данных вне
штатного API должны либо фиксироваться триггером, либо инвалидировать снимок.
Полная повторная загрузка при недействительном курсоре сохраняет локальную очередь.

### Устройство → сервер

Предлагается `POST /api/sync/events` с `protocol_version`, `device_id`, `events`.
Событие содержит `event_id`, `device_sequence`, `attempt_id`, `base_revision`,
`kind`, `occurred_at`, `catalog_version` и строго проверяемую полезную нагрузку.
Действия: создание занятия, обновление черновика, ответ тренировки/карточки,
завершение экзамена, изменение темы/акцента. Сервер возвращает квитанцию каждого
события, канонические ID/результаты и ревизию.

Предлагаемые пределы одной отправки: до 50 событий и до 96 KiB JSON,
в пределах существующего лимита express.json. Большое занятие разбивается
на зависимые события; максимальные существующие размеры экзамена сохраняются.
UUID занятия и регистрации вопросов передаются прежде его ответов.

- Уникальность `(user_id, event_id)` и контроль хэша содержимого: повтор того же
  события возвращает ту же квитанцию, а другое содержимое под тем же ID отклоняется.
- Запись результата, журнала изменений и квитанции атомарна. Если сервер сохранил
  ответ, но сеть оборвалась до получения квитанции, повтор не создаёт новый ответ.
- Исходящая запись удаляется/помечается подтверждённой только после устойчивой
  локальной записи квитанции. Обрыв между отдельными шагами допускает повтор.
- Приём серверных изменений и продвижение курсора тоже выполняются одной
  транзакцией IndexedDB. Подтверждённое событие не должно исчезать с экрана между
  квитанцией отправки и следующим получением серверных данных.
- Итоговую правильность и счёт вычисляет сервер по сохранённой версии вопросов.
  Переданный клиентом процент, роль или признак правильности не принимается на веру.
- Временные ошибки и 429 повторяются с увеличением задержки и учётом Retry-After.
  Ошибки формата, конфликты и исчерпание квот сохраняются для разбора; очередь
  не удаляется и не повторяет без конца заведомо неверный запрос.
- При 401 отправка приостанавливается до входа в тот же аккаунт. Сеть,
  недоступность сервера и истёкший вход показываются как разные состояния.
- Единый исполнитель между вкладками и service worker через короткую аренду
  в IndexedDB; повтор после завершения аренды безопасен благодаря UUID.

### Когда запускать обмен

При открытии, возвращении в приложение, после локального действия, события
`online`, по кнопке пользователя; дополнительно каждые 30 секунд, пока приложение
видимо и сервер доступен. Это позволяет получать изменения с компьютера даже
когда на телефоне ничего не нажимают. `navigator.onLine` — только сигнал к попытке,
доступность подтверждается ответом API. Существующие тайм-ауты сохраняются.

Background Sync используется при поддержке браузером как дополнительная
возможность. При закрытом PWA Android может отложить фоновую работу; основной
проверяемый сценарий — обмен после восстановления связи в открытом приложении
или при следующем его запуске. Постоянный фоновый процесс не обещается.

## 5. Объединение данных и конфликты

| Ситуация | Предлагаемое правило |
| --- | --- |
| Независимые занятия на двух устройствах | Разные UUID занятий; оба результата входят в историю |
| Повторная доставка одного ответа | Одна запись и прежняя квитанция |
| Одно занятие открыли на другом устройстве | Продолжение с последней полученной ревизии и тем же порядком вопросов |
| В одном занятии отвечали на разные вопросы | Объединение непересекающихся ответов |
| На один вопрос одного занятия дали разные ответы | Сохранить оба варианта конфликта; не перезаписывать молча, предложить выбрать учитываемый |
| Один экзамен независимо завершили по-разному | Не создавать дубль результата; сохранить конфликтующий вариант до явного решения |
| Получили черновик, пока пользователь вводит ответ | Не заменять текущий ввод; сравнить ревизии и применить безопасные изменения |
| Изменилась формулировка/правильный ответ | Новые занятия используют новую редакцию, начатые завершаются по своей |
| Удалён вопрос или раздел | Убрать из нового каталога, сохранить версии для старых занятий и истории |
| Одновременно изменили тему оформления | Последнее принятое сервером изменение; после обмена одинаковая тема на устройствах |

Конфликтующие варианты не считаются двумя ответами одного занятия. В интерфейсе
предлагаются «Оставить ответ с этого устройства» и «Оставить ответ с сервера»;
до решения серверный подтверждённый результат остаётся общим, локальный вариант
сохраняется с пометкой конфликта. Решение фиксируется новой ревизией, повторяемо
и не переписывает историю событий. Для экзамена выбирается вариант целиком.

Для порядка независимых ответов хранить время выполнения отдельно от времени
получения. Внутри устройства порядок определяется последовательностью событий;
между устройствами — временем выполнения с поправкой на последнюю известную
разницу часов с сервером и учётом причинной ревизии. Равенства разрешаются
стабильным идентификатором. Если изменение часов нарушает согласованность,
события сохраняются, но неоднозначный «последний ответ» требует разрешения,
а не замены по времени доставки. Абсолютно точную хронологию независимых
устройств без связи установить нельзя.

Статистика, список ошибок и адаптивный подбор пересчитываются из уникальных
событий по одному алгоритму на клиенте и сервере. Старый офлайн-ответ не должен
становиться последним лишь потому, что его синхронизировали позднее.
Статистика режима карточек остаётся отдельной, как в текущем продукте.

## 6. Версии вопросов, экзамен и обновление приложения

Офлайн-каталог должен содержать правильные ответы и пояснения. Интерфейс
скрывает их до ответа/завершения экзамена, но на самом устройстве они доступны.
Это неизбежное условие локальной проверки учебного тренажёра и отдельный пункт
согласования: прежнее свойство «правильных ответов нет в браузере до проверки»
сохранить одновременно с полноценной офлайн-проверкой нельзя.

Сервер хранит неизменяемые версии учебного пакета, выданного устройствам,
и восстанавливает снимок по версии и ключам вопросов. Клиент не может подменить
эталонный ответ собственным снимком. Старые версии, нужные ещё не отправленным
занятиям, не удаляются по произвольному TTL. Планирование очистки требует учёта
выданных пакетов и завершённых занятий, отдельной политики хранения.

Экзамен сохраняет выбор вопросов, порядок вариантов, ответы, старт, срок
завершения и UUID отправки. Закрытие приложения не обнуляет таймер. После
возврата с истёкшим временем он завершается локально и ожидает синхронизации.
Изменение часов устройства нельзя считать достоверным продлением экзамена;
проверить этот случай отдельно. Этот тренажёр не становится системой прокторинга.

Новая оболочка загружается в отдельный кеш. Переключение — после сохранения
состояния, без принудительной перезагрузки посреди ответа. Миграция IndexedDB
сохраняет исходящие события. Сервер поддерживает предыдущий протокол на время
перехода; неподдерживаемая версия приостанавливает обмен с понятным сообщением,
не очищая очередь. Неуспешная загрузка новой версии оставляет старую рабочую.

## 7. Вход, выход и предлагаемый интерфейс

Локальный доступ после первого онлайн-входа позволяет продолжать занятия без
сети, в том числе после истечения серверной cookie. Для отправки затем нужен
повторный вход. Локальный профиль не даёт административных полномочий и не
заменяет серверную авторизацию. При появлении сети проверяется именно ID аккаунта;
действия пользователя A никогда не отправляются от имени пользователя B.

Предлагаемый выход: при связи сначала синхронизировать и завершить серверный
сеанс; если есть неотправленные данные, предложить остаться или явно удалить
их и выйти. Без сети локально заблокировать профиль и сохранить очередь до
повторного входа в тот же аккаунт. Отзыв HttpOnly cookie нельзя подтвердить
без сервера: на следующем подключении сначала выполнить отложенный выход,
не восстанавливая профиль молча. Локальная блокировка не является шифрованием
данных на диске. Очистка личных данных — отдельное явное действие с предупреждением
о потере неотправленных результатов. Текст «Персональные данные» должен отражать
добавленное локальное хранение; незавершённую юридическую задачу 236 не считать решённой.

Предлагаемые элементы без отдельного нового раздела навигации:

- В профиле: «Установить приложение», если браузер поддерживает приглашение.
- Строка состояния: «Подготовка для работы без интернета…», «Доступно без
  интернета», «Нет связи с сервером · ожидают отправки: N», «Синхронизация…»,
  «Синхронизировано: время», «Для синхронизации войдите снова».
- Кнопка «Синхронизировать» и отдельная пометка неполной загрузки истории.
- На несинхронизированных итогах: «Сохранено на устройстве»; после квитанции —
  «Сохранено на сервере». При конфликте — «Нужно выбрать вариант ответа».
- При нехватке памяти — явное сообщение, что ответ пока не удалось сохранить.
- Для ИИ без сети — «Для ответа ИИ требуется интернет»; очередь запросов ИИ
  автоматически не создаётся, чтобы позднее не запускать ненужные генерации.

## 8. Последовательность реализации после согласования

1. **Контракт и данные.** Зафиксировать поля, события, правила конфликтов и тестовые
   примеры. Подготовить миграции версий каталога, UUID занятий, квитанций событий,
   ревизий/изменений и времён выполнения. Номер миграции определить по состоянию
   репозитория на момент реализации. Перед локальным применением — резервная копия.
   Обновить минимальные права runtime и проверить идемпотентность миграций.
2. **Серверный обмен.** Каталог, bootstrap/changes/events, серверная проверка,
   совместимость старых путей, пагинация, квоты и ограничения. Проверить атомарность,
   повторы, конкурентные транзакции и изоляцию пользователей.
3. **Установка и локальное хранение.** Manifest, существующая иконка в нужных
   размерах и maskable-вариант, service worker, IndexedDB, первоначальная загрузка,
   восстановление после перезапуска, перенос существующих черновиков.
4. **Автономные учебные сценарии.** Общая логика нормализации/оценки ответов,
   подбор вопросов, карточки, экзамен, таймер, материалы, история и статистика.
   Каждый сценарий сохраняет данные локально и использует общую очередь.
5. **Синхронизация и интерфейс.** Обмен в обе стороны, конфликты, обновление пакетов,
   несколько вкладок/устройств, истёкший вход, выход, индикация состояния.
6. **Приёмочные проверки.** Полный сценарий офлайн/онлайн, сбои в критических точках,
   регрессия текущих функций, установка и холодный запуск на Android.
7. **Отдельно согласованный выпуск.** Конкретный состав коммита и миграций,
   резервные копии, git fetch/log/pull --ff-only на сервере, проверка соседних сайтов
   и состояния сервиса. При грязной серверной копии остановиться. Схема выпуска
   должна сохранять работоспособность уже установленных старых PWA.

Оболочка без синхронизации — лишь промежуточный этап, а не завершение задачи.
Разделять работу на новые самостоятельные задачи только при отдельном поручении;
этапы и результаты учитывать в существующей задаче 254.

## 9. Проверки и критерии приёмки

1. Установить на Android после входа и полной загрузки; включить авиарежим,
   полностью закрыть приложение, открыть с иконки. Все учебные сценарии доступны.
2. Пройти порцию, карточки и экзамен, читать материал, открыть ошибки и статистику.
   Закрывать приложение после ответов и посреди экзамена: состояние восстанавливается.
3. Включить интернет: результаты появляются на сервере ровно один раз,
   а на телефоне появляются изменения, сделанные с компьютера.
4. Начать занятие на одном устройстве, синхронизировать и продолжить на другом.
   Проверить независимые занятия и конфликт одного общего занятия отдельно.
5. Оборвать сеть до отправки, после COMMIT сервера, до записи квитанции и во время
   получения страницы изменений. Повторы не теряют данные и не увеличивают счётчики.
6. Повторить одинаковый UUID с тем же и другим содержимым; проверить атомарность
   при сбое БД, два параллельных sync и пропуски курсора при позднем COMMIT.
7. Изменить вопрос, пока телефон офлайн: старое занятие проверяется по старой
   версии, новое — по новой; тема сетей не попадает в экзамен.
8. Проверить пустую установку без сети, частичный пакет, нехватку места,
   отказ persist(), переполнение серверной квоты, 429, 503, тайм-аут и неверные часы.
9. Проверить истёкшую cookie, офлайн-выход, повторный вход, смену аккаунта,
   запоздавший ответ API предыдущего аккаунта и удалённого пользователя.
10. Проверить обновление SW/IndexedDB с очередью и активным занятием, старый клиент
    с новым сервером и временную недоступность новой версии приложения.
11. Проверить существующие API/browser/AI тесты по затронутым сценариям, квоты
    и права БД. Тесты разрыва связи должны затрагивать также service worker;
    одного переключателя Offline в DevTools недостаточно для всех случаев.

Автотесты браузера не выдавать за проверку Android. Если физический телефон или
Android-эмулятор недоступен, указать это явно и оставить ручную приёмку установки,
авиарежима и холодного запуска незавершённой до получения результата.

## Источники ограничений платформы

- [Установка PWA](https://web.dev/learn/pwa/installation): manifest и браузерная
  установка; отдельный исполняемый пакет для установки PWA не требуется.
- [Background Sync](https://developer.chrome.com/docs/workbox/modules/workbox-background-sync):
  время повторов контролирует браузер, поддержка различается; HTTP-ошибки требуют
  отдельной обработки. Источник использован для ограничений платформы, выбор
  зависимости Workbox этим планом не предрешён.
- [Квоты и удаление локальных данных](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria):
  IndexedDB/Cache Storage имеют ограничения, устойчивое хранение нужно запрашивать,
  а ошибки записи необходимо обрабатывать.

Проверка плана: сверка с исходниками и документацией платформы. Согласование
требовалось по CLAUDE.md, пункты «План» и «Строго по ТЗ»; план согласован
пользователем, реализация ведётся по нему. Коммит, push, миграции на сервере
и выпуск по-прежнему требуют отдельных разрешений.
