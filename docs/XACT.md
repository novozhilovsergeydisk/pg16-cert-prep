# Статусы транзакций и pg_xact: материал для изучения

Этот материал к теме «05. Изоляция и многоверсионность». Он объясняет, как PostgreSQL помнит, какая транзакция зафиксирована, а какая отменена, где это хранится на диске и как это связано с атомарностью и видимостью строк. Всё можно проверить своими руками: от номера транзакции до двух бит в файле.

Ориентир — PostgreSQL 16. Опыты удобно ставить на учебном кластере; примеры ниже сделаны на учебном кластере PostgreSQL 17, для этой темы разницы почти нет, а где она есть — сказано отдельно.

## Как пользоваться материалом

- Каждая глава состоит из трёх частей. «Коротко» — суть простыми словами. «Подробнее» — как это устроено. «Проверьте сами» — команды с объяснением, что смотреть.
- Все опыты — на отдельном учебном кластере, под суперпользователем. Команды `CHECKPOINT` и `CREATE EXTENSION` в опытах — не просмотр, а административные действия, влияющие на весь кластер: на рабочем сервере их ради опыта не выполняют.
- Перед опытами подготовьте таблицу `acc` — шаг 1 практикума (глава 9).
- Команды оболочки (`ls`, `xxd`) можно запускать прямо из `psql` через `\!`, например `\! ls -l ~/pg-lab/data/pg_xact`. Они выполняются на машине, где запущен `psql`, поэтому так смотрят файлы, только если кластер на той же машине.
- В примерах каталог данных учебного кластера — `~/pg-lab/data`. Узнать свой: `SHOW data_directory;`.
- Слова «номер», «байт», «файл» в командах заменяйте своими значениями.
- Арифметика в главе 3 разобрана по шагам на одном примере — транзакции номер 755.

## 1. Номер транзакции

### Коротко

Каждая транзакция, которая что-то меняет в базе, получает номер — идентификатор транзакции (xid). Номера выдаются по порядку из одного счётчика на весь кластер. По номеру сервер потом узнаёт, чем закончилась транзакция и видны ли её изменения.

### Подробнее

- Постоянный номер выдаётся не при `BEGIN`, а при первой операции, которой он нужен: изменение данных, блокировка строк (`SELECT ... FOR UPDATE`), создание объектов. Обычные `SELECT` без блокировок номера не требуют. До этого у транзакции есть только временный, виртуальный идентификатор. Так счётчик расходуется экономнее.
- Функция `pg_current_xact_id()` возвращает номер текущей транзакции и выдаёт его, если ещё не выдан. Поэтому сам её вызов расходует номер. `pg_current_xact_id_if_assigned()` возвращает номер, только если он уже есть, и ничего не выдаёт.
- Счётчик общий для всех баз кластера. Номера в одном сеансе идут с пропусками: между ними номера получают другие сеансы и фоновые процессы. Номер отражает порядок выдачи, а не порядок фиксации.
- Номер 32-битный: около 4,3 миллиарда значений. Это важно для главы 8.
- Первые номера служебные, сервер обрабатывает их особо и не читает их статус из `pg_xact`: 0 — «нет транзакции», 1 — транзакция начальной загрузки (bootstrap), 2 — «заморожено», то есть видно всем. Обычные номера начинаются с 3.
- Создание кластера (`initdb`) само расходует несколько сотен номеров. Поэтому в только что созданном кластере первые ваши транзакции получают номера около 740.
- `pg_current_xact_id()` возвращает тип `xid8`: 64-битный номер, где к 32-битному xid добавлен счётчик оборотов («эпоха»), чтобы номера не повторялись. Прежняя функция `txid_current()` сохранена для совместимости и возвращает `bigint`.

### Проверьте сами

```sql
BEGIN;
SELECT pg_current_xact_id_if_assigned();
SELECT count(*) FROM pg_class;
SELECT pg_current_xact_id_if_assigned();
SELECT pg_current_xact_id();
COMMIT;
```

Оба вызова `pg_current_xact_id_if_assigned()` вернут NULL — в `psql` это пустое поле: транзакция только читала, номера у неё нет. `count(*)` между ними вернёт число строк и номера не потребует. Последний запрос выдаст номер явно.

Выполните несколько раз `SELECT pg_current_xact_id();` вне транзакции: каждая такая команда — отдельная транзакция, номер каждый раз новый.

## 2. Статусы транзакции

### Коротко

В `pg_xact` для каждого номера записан один из четырёх кодов, и для этого хватает двух бит:

- `00` — в процессе (или статус ещё не записан);
- `01` — зафиксирована (`COMMIT`);
- `10` — прервана (`ROLLBACK` или ошибка);
- `11` — промежуточная отметка подтранзакции при фиксации (глава 7).

### Подробнее

Двух бит хватает, потому что вариантов ровно четыре: 2 × 2 = 4. Значит, в одном байте (8 бит) помещаются статусы четырёх транзакций.

Нули в файле сами по себе не значат, что транзакция работает: это может быть и ещё не записанный статус (глава 5), и служебный номер.

Статус узнаёт функция `pg_xact_status`. Она принимает номер типа `xid8`. Удобнее всего передать номер строкой в кавычках, `'755'`, — PostgreSQL приведёт её к нужному типу сам; можно и явно: `'755'::xid8`. Число без кавычек — это `integer`, и будет ошибка «функция pg_xact_status(integer) не существует».

Функция возвращает одно из трёх текстовых значений:

- `in progress` — транзакция ещё идёт;
- `committed` — зафиксирована;
- `aborted` — прервана.

Если статус слишком старого номера сервер уже не хранит, результат — NULL (глава 8). Номер «из будущего», ещё не выданный, вызывает ошибку.

### Проверьте сами

```sql
BEGIN;
SELECT pg_current_xact_id();
SELECT pg_xact_status(pg_current_xact_id());
ROLLBACK;
SELECT pg_xact_status('номер');
```

Внутри транзакции — `in progress`, после `ROLLBACK` — `aborted` (подставьте номер из второй строки, в кавычках).

## 3. Где статусы лежат на диске

### Коротко

Статусы всех транзакций хранятся в каталоге `pg_xact` внутри каталога данных кластера. Там лежат файлы с именами `0000`, `0001`… В них подряд записаны пары битов: по четыре номера в байте. Зная номер транзакции, можно вычислить, в каком файле, в каком байте и в какой паре битов лежит её статус.

### Подробнее

До PostgreSQL 10 каталог назывался `pg_clog` (commit log, журнал фиксаций). Отсюда сокращение clog в материалах курса и документации.

Формулы. Обозначим N — 32-битный номер транзакции (в новом кластере он совпадает с числом из `pg_current_xact_id()`; в общем случае N — остаток от деления этого числа на 4 294 967 296). Все деления — целочисленные, `%` — остаток от деления:

- номер файла = N / 1 048 576, имя файла — этот номер в шестнадцатеричной записи из четырёх цифр;
- байт внутри файла = (N % 1 048 576) / 4;
- позиция пары битов в байте = N % 4.

Откуда 1 048 576 — глава 4. Пока номера меньше миллиона, файл `0000`, а формула байта упрощается до N / 4.

Всё сразу считает один запрос:

```sql
WITH x AS (SELECT 755::bigint AS n)
SELECT upper(lpad(to_hex(n / 1048576), 4, '0')) AS файл,
       (n % 1048576) / 4 AS байт,
       n % 4 AS позиция
FROM x;
```

Тот же расчёт по шагам для транзакции 755.

Шаг 1. Номер транзакции: N = 755.

Шаг 2. Файл: 755 / 1 048 576 = 0, файл `0000`.

Шаг 3. Номер байта: 755 / 4 = 188,75, целая часть — байт 188.

Шаг 4. Позиция внутри байта — остаток: 188 × 4 = 752, 755 − 752 = 3, позиция 3. Байт 188 хранит транзакции 752, 753, 754 и 755: позиции 0, 1, 2 и 3. Быстрый способ в уме: остаток от деления на 4 зависит только от двух последних цифр, ведь сотни делятся на 4 без остатка: 55 = 4 × 13 + 3.

Шаг 5. Прочитать байт. Команда `xxd -b -s 188 -l 1 файл` пропускает 188 байт от начала файла и показывает следующий байт в виде восьми битов:

```
000000bc: 10100101
```

Слева — смещение в шестнадцатеричном виде: `bc` = 11 × 16 + 12 = 188.

Шаг 6. Разбить восемь битов на пары и пронумеровать пары справа налево. `xxd` печатает биты от старшего к младшему, а позиция 0 — это два самых младших бита, то есть самые правые:

```
10 | 10 | 01 | 01
 3    2    1    0   ← позиция
755  754  753  752  ← транзакция
```

Шаг 7. Взять пару с номером позиции из шага 4 и расшифровать. Позиция 3 — крайняя левая пара, `10`: транзакция 755 прервана. Совпадает с `pg_xact_status('755')`.

Начало файла. В новом учебном кластере байт 0 был `01000000`: в позиции 3 — первая обычная транзакция 3, зафиксирована. Позиции 0–2 принадлежат служебным номерам; их нули ничего не значат — статус служебных номеров сервер определяет без этого файла. Это наблюдение конкретного кластера, а не обязательное значение.

### Проверьте сами

```
\! ls -l ~/pg-lab/data/pg_xact
\! xxd -b -l 4 ~/pg-lab/data/pg_xact/0000
```

Затем найдите байт своей транзакции из главы 2 по шагам 1–7. Перед чтением файла выполните `CHECKPOINT;` — почему, объяснено в главе 5.

## 4. Откуда числа 4, 8192, 32 и 1 048 576

### Коротко

Один файл `pg_xact` состоит из страниц, страница — из байтов, байт — из четырёх статусов:

```
32 страницы × 8192 байта × 4 статуса = 1 048 576 транзакций в файле
```

### Подробнее

- 4 статуса в байте — по 2 бита на статус, в байте 8 бит.
- 8192 байта в странице — стандартный размер страницы PostgreSQL, 8 КБ. Такие же страницы у таблиц и индексов. Задаётся при сборке сервера; при другом размере страницы все числа ниже пересчитываются. Одна страница `pg_xact` хранит статусы 8192 × 4 = 32 768 транзакций.
- 32 страницы в файле — постоянная в исходном коде PostgreSQL (`SLRU_PAGES_PER_SEGMENT`). Командой её не посмотреть; заполненный файл `pg_xact` имеет размер ровно 32 × 8192 = 262 144 байта (256 КБ). Последний, текущий файл обычно неполный.

Все три множителя — степени двойки: 32 = 2⁵, 8192 = 2¹³, 4 = 2². При умножении степени складываются: 5 + 13 + 2 = 20, то есть 1 048 576 = 2²⁰. Серверу так удобно: файл, страница и байт получаются из номера простыми сдвигами битов.

Файл растёт страницами, а не создаётся сразу полным. В новом кластере, где выдано несколько сотен номеров, файл `0000` занимает одну страницу — 8192 байта. Для номеров от 32 768 нужна вторая страница; на 32-й файл заполнится, и начнётся `0001`. Новая страница сначала появляется в памяти, а в файле — когда её запишут (глава 5), поэтому размер файла может отставать.

Номер 32-битный: 2³² номеров, 2³² / 2²⁰ = 2¹² = 4096 возможных имён файлов, от `0000` до `0FFF` (имена шестнадцатеричные). Столько файлов одновременно не бывает — глава 8.

### Проверьте сами

```sql
SHOW block_size;
```

```
\! ls -l ~/pg-lab/data/pg_xact
```

Размер файла кратен 8192.

## 5. Память и диск

### Коротко

Статус транзакции сначала меняется в памяти сервера, а в файл `pg_xact` попадает позже — на контрольной точке или когда страницу вытесняют из памяти. Поэтому сразу после отката в файле можно увидеть `00`, хотя `pg_xact_status` уже говорит `aborted`. Надёжность при этом не страдает: фиксацию защищает журнал предзаписи.

### Подробнее

Последние страницы `pg_xact` сервер держит в общей памяти, в отдельных буферах:

- в PostgreSQL 16 их число — min(128, max(4, `shared_buffers` в блоках / 512)); при стандартных 128 МБ это 32 страницы;
- в PostgreSQL 17 его задаёт параметр `transaction_buffers`; значение 0 (по умолчанию) — автоматический выбор: `shared_buffers` / 512, но не меньше 16 и не больше 1024 страниц.

Все процессы читают и меняют статусы там. На диск страница записывается на контрольной точке или когда её буфер нужен под другую страницу.

Что происходит при обычной синхронной фиксации (`synchronous_commit = on`, `fsync = on`):

- в журнал предзаписи пишется запись о фиксации, и журнал сохраняется на диск — способом, который задаёт `wal_sync_method` (в Linux по умолчанию `fdatasync`);
- статус `01` ставится в буфере `pg_xact` в памяти;
- клиент получает ответ «зафиксировано».

Если сервер упадёт до того, как страница `pg_xact` попадёт на диск, при восстановлении он прочитает запись о фиксации из журнала и поставит `01` заново. Поэтому срочно сбрасывать `pg_xact` при каждом `COMMIT` не нужно.

При асинхронной фиксации (`synchronous_commit = off`) ответ приходит до сохранения журнала, и при сбое ОС последние подтверждённые транзакции могут потеряться. При `fsync = off` гарантий нет вовсе.

С откатом проще. Обычная транзакция, для которой после сбоя в журнале нет записи о фиксации, работающей больше не считается, и её версии строк никому не видны — даже если в `pg_xact` на её месте остались нули. Отдельный случай — подготовленные двухфазные транзакции (`PREPARE TRANSACTION`): они переживают перезапуск и ждут решения `COMMIT PREPARED` или `ROLLBACK PREPARED`.

### Проверьте сами

`CHECKPOINT` — административная команда для всего кластера, только на учебном кластере, под суперпользователем.

```sql
BEGIN;
SELECT pg_current_xact_id();
ROLLBACK;
SELECT номер / 4 AS байт, номер % 4 AS позиция;
\! xxd -b -s байт -l 1 ~/pg-lab/data/pg_xact/0000
CHECKPOINT;
\! xxd -b -s байт -l 1 ~/pg-lab/data/pg_xact/0000
```

До `CHECKPOINT` в паре вашей транзакции, скорее всего, будет `00`, после — `10`. Если `10` есть уже в первый раз, страницу успела записать плановая контрольная точка или её вытеснили из памяти.

## 6. Зачем статусы нужны: видимость строк

### Коротко

Изменение строки в PostgreSQL не переписывает её, а создаёт новую версию. В заголовке каждой версии записано, какая транзакция её создала (`xmin`) и какая отметила её как удалённую или заменённую (`xmax`). Чтобы решить, видна ли версия, сервер смотрит статусы этих транзакций и снимок данных запроса. Поэтому откат такой быстрый: достаточно поставить транзакции статус «прервана», и её версии станут невидимыми — переписывать таблицу не нужно.

### Подробнее

Обычный запрос видит:

- собственные изменения своей транзакции, сделанные предыдущими командами;
- версии, созданные другими транзакциями, которые зафиксировались до снимка данных этого запроса, — если эти версии не удалены для этого снимка.

Когда берётся снимок, определяет уровень изоляции: при Read Committed — для каждой команды, при Repeatable Read — один на всю транзакцию. Поэтому транзакция, зафиксированная после снимка, остаётся невидимой, хотя в `pg_xact` у неё уже `01`.

Версия, созданная прерванной транзакцией, не видна никому; её потом уберёт очистка (`VACUUM`).

Про поле `xmax`. В простых опытах в нём номер транзакции, удалившей или заменившей версию, а 0 — нет такой отметки. В общем случае оно используется и для блокировок строк, и для групп блокировок (MultiXact), поэтому его смысл определяют вместе с флагами заголовка. Ненулевой `xmax` сам по себе не делает строку невидимой: например, если отметившая её транзакция прервана (глава 7).

Смотреть в `pg_xact` при каждом чтении строки было бы дорого. Поэтому, узнав итог транзакции один раз, сервер записывает подсказку прямо в заголовок версии — биты-подсказки: «xmin зафиксирована», «xmin прервана», «xmax зафиксирована», «xmax прервана». Подсказка избавляет от чтения `pg_xact`, но не от проверки снимка: зафиксированная транзакция всё равно может быть невидима старому снимку. Побочный эффект: первое чтение после изменения иногда «пачкает» страницу таблицы, и её приходится записывать на диск, хотя запрос только читал.

### Проверьте сами

```sql
SELECT xmin, xmax, * FROM acc;
SELECT xmin FROM pg_class WHERE oid = 'acc'::regclass;
```

Первый запрос покажет номер транзакции, вставившей строки. Второй — номер транзакции, создавшей текущую версию записи о таблице в системном каталоге: сразу после `CREATE TABLE` это номер её создания, но позже он может смениться (например, при изменении таблицы).

Биты-подсказки видны через расширение `pageinspect` из стандартной поставки. Опыт необязательный, только на учебном кластере, под суперпользователем. Если расширение уже было установлено до опыта, после него не удаляйте.

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT lp, t_xmin, t_xmax,
       (t_infomask & 768) = 256 AS xmin_зафиксирована,
       (t_infomask & 768) = 512 AS xmin_прервана,
       (t_infomask & 768) = 768 AS xmin_заморожена
FROM heap_page_items(get_raw_page('acc', 0))
WHERE lp_flags = 1;
```

Флаги читают вместе: 256 — подсказка «зафиксирована», 512 — «прервана», оба сразу (768) — версия заморожена (глава 8), ни одного — итог ещё не записан в подсказку. Если расширение ставили только для опыта: `DROP EXTENSION pageinspect;`.

## 7. Подтранзакции и SAVEPOINT

### Коротко

`SAVEPOINT` открывает внутри транзакции подтранзакцию. Её можно отменить отдельно (`ROLLBACK TO`), не отменяя всю транзакцию. Подтранзакция, которая что-то изменила, получает свой номер и свой статус в `pg_xact`.

### Подробнее

- При `ROLLBACK TO` подтранзакция сразу получает статус `10`: её изменения пропадают, а родительская транзакция продолжается.
- При фиксации родителя его подтранзакции должны стать зафиксированными одновременно с ним. Подтранзакции на той же странице `pg_xact`, что и родитель, получают `01` вместе с ним. Если часть подтранзакций лежит на других страницах, сервер сначала ставит им промежуточную отметку `11`, затем фиксирует родителя и подтранзакции на его странице, затем ставит `01` остальным. Пока отметка `11`, итог подтранзакции определяют по родителю. `RELEASE SAVEPOINT` сам по себе `11` не записывает.
- Кто чей родитель, сервер помнит в соседнем каталоге `pg_subtrans`: для подтранзакции с номером там хранится номер её непосредственного родителя. Это временные сведения: после сбоя старому содержимому не доверяют и нужные страницы заполняют заново.
- Много подтранзакций в одной транзакции (например, `SAVEPOINT` на каждую строку в цикле) заметно замедляют работу. Особенно когда их больше 64 в одном процессе: столько номеров подтранзакций сервер держит в быстром кеше, а дальше проверке видимости приходится ходить в `pg_subtrans`.

### Проверьте сами

```sql
BEGIN;
SELECT pg_current_xact_id();
SAVEPOINT s;
UPDATE acc SET balance = balance WHERE id = 1;
SELECT xmin FROM acc WHERE id = 1;
ROLLBACK TO s;
COMMIT;
```

После `UPDATE` в `xmin` — номер подтранзакции. В тихом учебном кластере он обычно на единицу больше номера транзакции из второй строки, но это не гарантия: запишите фактическое значение. После `COMMIT` проверьте: `pg_xact_status` для номера транзакции — `committed`, для номера подтранзакции — `aborted`.

Ещё одна деталь:

```sql
SELECT xmin, xmax, * FROM acc WHERE id = 1;
```

У строки в `xmax` останется номер прерванной подтранзакции: она успела пометить старую версию как заменённую. Строка всё равно видна, потому что заменившая её транзакция прервана. Так видимость и работает: смотрится не только номер, но и итог транзакции.

## 8. Переполнение счётчика и заморозка

### Коротко

Номер транзакции 32-битный, и счётчик идёт по кругу. Чтобы старые строки не стали вдруг «из будущего», очистка (`VACUUM`) заранее замораживает их: помечает, что создание версии было давно и видно любому снимку. После этого статусы старых транзакций больше не нужны, и сервер удаляет ненужные файлы `pg_xact` целиком.

### Подробнее

- Номера сравниваются по кругу: для каждого номера примерно 2 миллиарда (2³¹) номеров считаются прошлыми и столько же — будущими. Поэтому возраст незамороженных номеров должен оставаться меньше примерно 2³¹ выдач.
- Заморозка ставит в заголовке версии комбинацию флагов «заморожено» — оба бита-подсказки xmin сразу. Числовое поле `xmin` обычно остаётся, но проверять статус этой транзакции больше не нужно. Удаление или замена такой версии по-прежнему проверяется по `xmax`: замороженную строку можно удалить, как любую другую.
- Для каждой таблицы хранится граница `relfrozenxid`, для каждой базы — `datfrozenxid`: все незамороженные номера в ней не старше этой границы. Это консервативная нижняя граница, а не обязательно реально встречающийся `xmin`.
- Когда очистка продвигает общую границу всех баз, ненужные целиком файлы `pg_xact` удаляются. После оборота счётчика имена файлов используются снова, поэтому по имени файла нельзя судить о его возрасте.
- `pg_xact_status` для номеров старше своей внутренней границы возвращает NULL: их статус сервер больше не использует, даже если байт ещё лежит в файле. Эта граница двигается вместе с удалением файлов `pg_xact`. Например, в новом кластере `pg_xact_status('3')` — NULL.
- Если заморозка отстаёт, сервер сначала предупреждает, а примерно за 3 миллиона номеров до опасной границы перестаёт выдавать новые номера, пока не будет выполнена очистка; чтение без номера при этом возможно. Обычную автоочистку оставляют включённой, хотя защитные запуски против переполнения выполняются даже при `autovacuum = off` (тема 06).

### Проверьте сами

```sql
SELECT datname, datfrozenxid, age(datfrozenxid) FROM pg_database;
```

`age` — сколько номеров выдано после границы `datfrozenxid` базы.

Сохранённые сведения кластера показывает `pg_controldata` той же основной версии, что и кластер; её запускают на машине кластера от пользователя ОС, у которого есть доступ к каталогу данных. Для учебного кластера PostgreSQL 17 из Homebrew:

```
\! /usr/local/opt/postgresql@17/bin/pg_controldata ~/pg-lab/data | grep -i xid
```

`NextXID` — следующий номер, включая эпоху (запись `0:756` — эпоха 0, номер 756), `oldestXID` — самый старый незамороженный номер кластера. Это значения последней контрольной точки, текущие могут быть больше.

## 9. Практикум

Все шаги — в учебном кластере, в одном сеансе `psql`, под суперпользователем. Опыт с ошибкой рассчитан на стандартный режим `psql` (`ON_ERROR_ROLLBACK` выключен): при включённом `psql` откатит только ошибочную команду, и первое изменение зафиксируется.

Шаг 1. Таблица для опытов. Если `acc` осталась от других опытов и больше не нужна, сначала удалите её: `DROP TABLE acc;`. Начальные балансы важны для шага 2.

```sql
CREATE TABLE acc (id int PRIMARY KEY, balance int CHECK (balance >= 0));
INSERT INTO acc VALUES (1, 100), (2, 0);
```

Шаг 2. Неудачный перевод. Номер транзакции запоминаем до ошибки:

```sql
BEGIN;
SELECT pg_current_xact_id();
UPDATE acc SET balance = balance + 50 WHERE id = 2;
UPDATE acc SET balance = balance - 150 WHERE id = 1;
COMMIT;
```

На `COMMIT` сервер ответит `ROLLBACK`. Стандартное приглашение `psql` показывает состояние транзакции: `*` — открыт блок транзакции, `!` — блок прерван ошибкой, команды игнорируются до `COMMIT` или `ROLLBACK`. Последний символ `#` — у суперпользователя, `>` — у обычной роли.

Шаг 3. Статус этой транзакции:

```sql
SELECT pg_xact_status('номер');
```

Будет `aborted`.

Шаг 4. Где статус лежит в файле — шаги главы 3:

```sql
SELECT номер / 4 AS байт, номер % 4 AS позиция;
CHECKPOINT;
\! xxd -b -s байт -l 1 ~/pg-lab/data/pg_xact/0000
```

В паре с номером позиции (справа налево, начиная с 0) будет `10`.

Шаг 5. Кто создал строки и запись о таблице:

```sql
SELECT xmin, xmax, * FROM acc;
SELECT xmin FROM pg_class WHERE oid = 'acc'::regclass;
```

Найдите эти номера в файле `pg_xact` тем же способом: у них будет `01`.

Шаг 6. Подтранзакция — опыт из главы 7.

Шаг 7. Файлы, размер страницы и возраст заморозки:

```sql
SHOW block_size;
\! ls -l ~/pg-lab/data/pg_xact
SELECT datname, age(datfrozenxid) FROM pg_database;
```

## 10. Словарь терминов

- Номер транзакции (xid) — 32-битный идентификатор из общего счётчика кластера; транзакция получает его при первой операции, которой он нужен.
- Виртуальный идентификатор — временный номер транзакции, которой ещё не понадобился постоянный xid.
- `xid8` — 64-битный номер транзакции с учётом оборотов счётчика (эпохи); его возвращает `pg_current_xact_id()`.
- Статус транзакции в `pg_xact` — два бита: в процессе, зафиксирована, прервана или промежуточная отметка подтранзакции.
- `pg_xact` (раньше `pg_clog`, clog) — каталог с файлами статусов транзакций.
- Страница — блок данных размером 8 КБ; в странице `pg_xact` статусы 32 768 транзакций.
- Сегмент `pg_xact` — файл из 32 страниц, 256 КБ, статусы 1 048 576 транзакций.
- `xmin` — номер транзакции, создавшей версию строки.
- `xmax` — номер транзакции, удалившей или заменившей версию; также используется для блокировок строк.
- Снимок данных — сведения о том, какие транзакции считаются завершёнными для запроса; определяет видимость версий.
- Биты-подсказки — отметки в заголовке версии строки об итоге её транзакций, чтобы не читать `pg_xact` повторно.
- Подтранзакция — часть транзакции после `SAVEPOINT`, которую можно отменить отдельно.
- `pg_subtrans` — каталог, где хранится связь подтранзакции с её родителем.
- Заморозка — отметка, что создание версии видно любому снимку независимо от номера её транзакции.
- `datfrozenxid` — граница базы: все её незамороженные номера не старше этого значения.
- Переполнение счётчика (wraparound) — проблема круговых 32-битных номеров, от которой защищает заморозка.
