## Выводы для следующего этапа

Сейчас рекомендую сохранить личный доступ и действующие ограничения:
один активный запрос на пользователя, общие 10 принятых запросов за скользящие

Эти значения описывают текущую реализацию; анализ пустой выборки не подтверждает
их достаточность для общего доступа.

Для первого повторного анализа предлагаю собрать хотя бы 30–50 обычных запросов
в течение нескольких дней при личном доступе: пояснения, общие вопросы и уточнения
с историей разной длины. Это ориентир для предварительного анализа, а не гарантия
статистической точности; p95 на такой выборке особенно неустойчив. Специально
нагружать рабочий шлюз для накопления статистики не требуется.

После появления данных проверить длительности, известные usage-метрики и ошибки,
размеры контекста/истории, интервалы между запросами и число опросов браузера.
Запросы без usage и прерванные вызовы учитывать отдельно. По реальным размерам
оценить прирост таблиц и резервных копий; текущие 256 KiB для такого прогноза
не подходят. Личный доступ не позволит измерить спрос нескольких пользователей:
проверка конкуренции потребует локальной имитации шлюза и затем согласованного пилота.

При согласовании очереди сохранить параллелизм шлюза 1 и определить отдельно
число ожидающих заданий, срок ожидания до отправки, общие и пользовательские квоты.
Новые численные значения по текущим данным рекомендовать преждевременно.

Очередь требует пересмотра ожидания браузера: сейчас SSH ограничен 55 секундами,
шлюз — 45 секундами, HTTP-вызов генерации — 35 секундами, а браузер опрашивает
задание в течение 70 секунд плюс текущий HTTP-запрос. Даже одно задание впереди
может исчерпать этот браузерный бюджет. При выборе чисел учитывать сумму ожидания
в очереди, выполнения и запаса на подготовку/сохранение/опрос. Расчёт пропускной
способности одного исполнителя `60 / среднее время выполнения в секундах`
даёт только теоретическую оценку; ошибки, ограничения провайдера и запас
нагрузки потребуют уменьшить допустимый поток.
