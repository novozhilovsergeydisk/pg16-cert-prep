# Выпуск разделения ролей БД — 12 ноября 2026

Я выпустил код `78e8468` и применил административную миграцию 146 на appuse
по прямому разрешению пользователя. Учёт: задача 235. SEC-08 закрыт на рабочей БД.

## Что действует

- Текущая LOGIN-роль приложения и её реквизиты сохранены. Она больше не владеет
  БД, таблицами и последовательностями, не может создавать схемы, public-объекты
  и временные таблицы. У неё нет членства в роли владельца.
- `pg16_owner` — NOLOGIN и без superuser/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS;
  ей принадлежат только согласованные объекты проекта и его БД.
- Runtime получил [согласованную матрицу](../../DB-ROLE-SEPARATION.md), включая
  ограничение INSERT/UPDATE по столбцам. Изменение users.role, учебных вопросов,
  чтение архива и доступ к счётчикам квот закрыты.
- Функция квот — приватная SECURITY DEFINER с фиксированным search_path,
  public-квалификацией и проверкой исходного триггера. Оба триггера действуют;
  счётчики совпадают с фактическими снимками.
- Новые миграции выполняются административным соединением через SET ROLE
  pg16_owner. Старый запуск SQL от runtime больше не подходит. .env, пароли,
  pg_hba.conf, nginx/systemd, пакеты и ИИ-шлюз этим выпуском не менялись.

## Backup и применение

Сервер до выпуска был чистым на `f9ca989`. Я сохранил закрытый каталог
`/root/ssh-backups/pg16-role-235-20261112T160714Z` с baseline 22 HTTPS-адресов и
41 службы, git bundle, архивом конфигураций и полной копией before.dump.
Проверены pg_restore --list, git bundle verify и tar -tzf.

Исходники доставлены только git push → fetch → просмотр log/diff → pull --ff-only.
Затем штатный runner prepare создал собственные `roles/before.dump` и
`roles/state.json` с исходными владельцами, ACL, правами столбцов/default ACL,
определением функции и идентичностью кластера/БД/роли. Каталоги 0700, файлы 0600.
Реквизиты и manifest не выводились в чат/журнал приложения.

Первый apply завершился applied, второй — already_applied, затем verify прошёл
в REPEATABLE READ READ ONLY. Исходный manifest не перезаписывался. Откат готов
через тот же runner с этим state-dir; на production он не выполнялся.

## Проверки сервера

- Полная проверка эффективных прав, владельцев, членств, default privileges,
  столбцов и свойств функции прошла штатным verify. Прикладная роль владеет
  нулём public-отношений и не является владельцем БД.
- Семь разрешённых DML-планов проверены через EXPLAIN без ANALYZE и без выполнения
  в READ ONLY: создание/обновление пользователя, сеанс, запрос входа, настройки,
  оба режима снимков и журнал ответов.
- Семь запрещённых операций дали SQLSTATE 42501: изменение роли пользователя,
  изменение вопроса, чтение/изменение счётчика, чтение архива, прямое выполнение
  служебной функции и SET ROLE pg16_owner. Для проверки использованы savepoint;
  записи и пользовательские учётные записи не создавались, sequence не вызывались.
- Отчёт ИИ вернул все семь разделов от runtime в READ ONLY.
- Хэш полных строк всех 805 вопросов и количества снимков/запросов/сообщений ИИ
  совпали с исходными. В счётчиках квот ноль расхождений.
- После перехода создан отдельный after.dump от ОС postgres и проверен
  pg_restore --list. Это подтверждает, что административное копирование не
  зависит от урезанной runtime-роли. Штатный cron-скрипт не менялся и не запускался
  вручную. Полное восстановление production-копии в этом выпуске не выполнялось;
  полный restore тестовой копии ранее проверен на изолированном PG16.14.
- Публичные HTTP-проверки: главная 200; /api/me, /api/admin/users, /api/ai/status —
  401; /.env и /.git/config — 404. Во всех шести ответах присутствуют CSP и HSTS.
- Все 22 HTTPS-результата совпали с baseline. Все 41 службы сохранили состояние,
  PID, время старта и NRestarts; приложение active, прежний PID 411638, NRestarts=0.
  Перезапусков приложения, nginx и PostgreSQL не было.
- Серверный git после применения кода чистый. Локальный посторонний 0.167.1
  сохранён вне коммитов.

На production не выполнялись нагрузочные тесты, реальная отправка письма или
запрос модели. Реальные контроллеры с записью проверены до выпуска на отдельном
PG16.14: 14/14 TAP, включая 33 функциональные проверки. Серверная проверка DML
ограничивалась планированием и правами; она не выдаётся за реальную отправку письма
или полный пользовательский сценарий входа.

Разделение ролей ограничивает последствия компрометации приложения, но оставляет
ему необходимые SELECT/DML по данным пользователей. Оно не заменяет авторизацию
и не является гарантией отсутствия всех уязвимостей. Следующее замечание аудита
для отдельного согласования — SEC-09, точное описание хранения и передачи данных.
