## SEC-01. HTTP-парсер: известная уязвимость отказа в обслуживании

**Где:** `server.js:37–39`, установленный `body-parser 2.3.0` через Express 5.2.1. SHA-256 package-lock локальной и серверной копий совпадает; версии установленных серверных пакетов проверены отдельно.

`express.json()` допускает распаковку сжатых запросов по умолчанию и выполняется до `checkOrigin`, входа и большинства ограничителей частоты. Для этой версии опубликована GHSA-27r3-jxmh-p828: после завершённого сжатого фрейма дополнительные байты могут вызвать необработанную ошибку потока и завершение процесса без авторизации. Приложение в production завершает процесс при uncaughtException, а systemd перезапускает его через 3 секунды. Повторение ошибки может мешать работе пользователей.

**Граница доказательства:** я подтвердил уязвимую версию и применимый путь обработки. Три небольших локальных пробы gzip/deflate/br на Node 22 не завершили процесс. Поэтому я не утверждаю, что воспроизвёл crash на данной конфигурации; опубликованное advisory и уязвимая версия остаются основанием для исправления. На production вредоносные сжатые тела я не отправлял.

**Что исправить:** получить совместимую зависимость с `body-parser >=2.4.0` и перепроверить lockfile/фактическую установку. Если приложение не принимает сжатые JSON-тела по продуктовой необходимости, дополнительно отключить распаковку в обоих JSON-middleware. После обновления проверить обычные запросы, пределы размера и отклонение сжатых тел.

[Advisory разработчиков body-parser](https://github.com/expressjs/body-parser/security/advisories/GHSA-27r3-jxmh-p828).

## SEC-02. SMTP не требует TLS

**Где:** `src/services/mailer.js:12–22`. `secure` включается только для 465, `requireTLS` не задан. Production-порт — 587.

Я поднял локальный SMTP, который объявляет AUTH и не объявляет STARTTLS. Настоящий `sendMail` успешно отправил письмо: AUTH и тело поступили в незашифрованном виде. В опыте использованы случайные временные реквизиты и письмо без данных входа; реальные SMTP-реквизиты в нём не участвовали.

Обычный сервер на 587 может успешно использовать STARTTLS. Находка означает отсутствие обязательного шифрования, а не утверждение, что текущие реальные письма всегда идут открытым текстом. При подмене SMTP-пути или удалении объявления STARTTLS атакующий в сетевом пути может получить SMTP-реквизиты и ссылки/коды входа.

**Что исправить:** для 587 требовать STARTTLS с проверкой сертификата; для 465 использовать TLS с начала соединения. Добавить отрицательную проверку: сервер без STARTTLS должен приводить к отказу отправки до AUTH/письма. Отдельно убедиться, что кастомный `getSocket` сохраняет проверку ожидаемого имени сервера.

[Документация Nodemailer о secure и requireTLS](https://nodemailer.com/smtp).

## SEC-03. Неподдерживаемый Node.js

На appuse установлен Node.js `v20.20.2`. Официальная таблица релизов относит ветку 20 к EOL. Обновления отдельных npm-пакетов не заменяют поддержку среды выполнения.

**Что исправить:** проверить приложение на поддерживаемом LTS, например Node.js 24, затем планировать адресный переход службы. На общем сервере нельзя молча менять системный Node для всех сайтов. Нужны явный исполняемый файл службы, тесты, резервная копия конфигурации и откат. Для этой находки я не заявляю о воспроизведённой атаке на сам Node.

[Официальный список релизов Node.js](https://nodejs.org/en/about/previous-releases), [последствия EOL](https://nodejs.org/en/about/eol).

## SEC-04. Административный SSH допускает root-пароль

На appuse и foolish-magenta эффективные настройки содержат `PermitRootLogin yes`, `PasswordAuthentication yes`; у root статус пароля `P`. SSH слушает внешние интерфейсы, административный порт доступен по установленным правилам. Fail2ban работает на обоих серверах, но не исключает вход по скомпрометированному паролю.

Это конфигурационный риск: я не проверял силу пароля и не выполнял подбор. Успешный root-вход даёт контроль над всеми сайтами на appuse и VPN на magenta.

**Что исправить:** после проверки отдельного входа по ключу и аварийного доступа согласовать запрет root-паролей; по возможности использовать отдельную административную учётную запись и адресные ограничения. Новую сессию нужно подтвердить до закрытия старой. Менять sshd в рамках аудита я не стал.

[Справочник OpenSSH](https://man.openbsd.org/sshd_config).

## SEC-06. Ограничения нагрузки покрывают не все маршруты

`src/routes/auth.js:10` не ставит ограничитель на проверку ссылки. Я отправил локально 35 корректных по форме, но несуществующих случайных значений: все запросы дошли до ответа 400, ни один не получил 429. Это не практический способ угадать 256-битный токен; риск состоит в расходовании подключений и запросов БД до авторизации.

В nginx для этого сайта и просмотренной общей конфигурации не найдено rate/connection-limit. У службы `MemoryMax=infinity`, `CPUQuotaPerSecUSec=infinity`, `TasksMax=4635`. Пул ограничен по времени, поэтому часть защиты уже есть. Отдельно отсутствие предела cgroup увеличивает последствия ресурсной атаки для соседних сайтов.

**Что исправить:** согласовать лимиты дешёвых входных запросов, особенно verify, до обращения к БД; ограничения nginx на подходящие маршруты и число соединений; измерить нормальное потребление приложения и выделить бюджет памяти/CPU. Проверить сохранение настоящего IP за nginx. Производительность и предел отказа я нагрузкой не измерял.

## SEC-07. Нет квоты на хранимые снимки тренировок

`src/controllers/trainingController.js:26–67` сохраняет JSON-снимок при создании порции, даже если пользователь ни разу не ответил. Общий `answerLimit` разрешает до 1000 операций в час на аккаунт. Для обычной темы действует максимум 200 вопросов, а ветка `mistakes` не использует LIMIT. Количество сохранённых порций и общий объём на пользователя не ограничены; код удаления старых порций не найден.

На рабочей БД обнаружены 93 порции, средний физический размер JSON около 5 КБ, максимальный около 10 КБ. Это не размер возможного максимального запроса. Сейчас признаков заполнения диска этой функцией я не установил; риск — длительное автоматическое создание снимков с одного или нескольких подтверждённых аккаунтов.

**Что исправить:** отдельно ограничить создание порций, размер снимка и число активных/пустых порций, определить согласованный срок хранения. Для mistakes установить предел порции. Не удалять учебную историю автоматически без продуктового решения и резервной копии.

## SEC-08. Приложение работает от владельца БД

Рабочее подключение использует роль, которая владеет текущей базой и 11 таблицами public, а также является членом `pg_database_owner`. Суперпользователь, создание ролей/баз, replication и bypass RLS выключены; членство в опасных серверных ролях не обнаружено.

При компрометации приложения права владельца позволят менять структуру и уничтожать объекты его базы. Это увеличение последствий взлома, а не обнаруженная SQL-инъекция.

**Что исправить:** отделить роль миграций/владельца от runtime-роли с необходимыми DML/sequence-правами. Дополнительно рассмотреть `idle_in_transaction_session_timeout` — сейчас 0. Изменение прав потребует отдельного плана и проверки всех операций; в аудите права не менялись.

[Рекомендации OWASP о правах БД](https://cheatsheetseries.owasp.org/cheatsheets/Database_Security_Cheat_Sheet.html).

## SEC-09. Описание приватности не соответствует объёму обработки

`public/index.html:81–84` содержит только фразу об использовании email для входа. Реально сохраняются результаты, история тренировок и экзаменов; администратор видит email и статистику. `gateway/ai_gateway.py:130–140` отправляет текст диалога и, в режиме пояснения, учебный контекст в OpenRouter и провайдеру модели. Для общего вопроса содержимое может включать произвольные данные, которые введёт владелец.

В запросе отсутствует явное требование определённой политики хранения/обучения провайдера. Настройки приватности аккаунта OpenRouter я не инспектировал; отсутствие параметра в коде не доказывает, что обучение на данных включено. Пилот доступен только одному владельцу, что существенно ограничивает охват риска.

**Что исправить:** явно описать поток данных и доступ администратора, согласовать сроки хранения/удаление аккаунта и допустимое содержимое запросов ИИ; проверить настройки OpenRouter для бесплатных моделей и при необходимости закрепить требования на запрос. Если выбранная бесплатная модель не соответствует требованиям, предусмотреть понятный отказ. Это техническая оценка прозрачности, не юридическое заключение.

[Политики хранения данных провайдеров OpenRouter](https://openrouter.ai/docs/guides/privacy/provider-logging).

## SEC-10–12. Дополнительное укрепление

**SEC-10 — персональные ответы и кеш.** `/api/me` и обычные маршруты статистики/истории не задают общий `Cache-Control: no-store`; ИИ-маршруты его задают. Я не воспроизвёл утечку между аккаунтами и не обнаружил proxy-cache для этого сайта. Рекомендуется единый запрет хранения персональных ответов и отдельная проверка logout/back на общем компьютере.

**SEC-11 — случайное попадание файлов в репозиторий.** Локальный `token.txt.save` имеет права 0600, не отслеживается и не игнорируется. По имени нельзя утверждать, что в нём есть действующий секрет. Точечный поиск сильных шаблонов ключей/JWT не нашёл совпадений ни в текущих проверенных файлах, ни в 829 достижимых текстовых git-объектах истории. Рекомендуется согласованный ignore для секретных временных файлов, адресная проверка назначения этого файла и сканирование перед коммитом. Удалять или переносить его я не стал. Произвольные пароли, все форматы токенов и недостижимые git-объекты такой поиск не покрывает.

**SEC-12 — защитные барьеры выпуска.** GitHub подтверждает `main.protected=false`; репозиторий закрытый, в отслеживаемом дереве нет GitHub Actions. Просмотр детальных branch-protection-настроек API вернул ограничение тарифа 403. Рекомендуются воспроизводимые обязательные проверки, контроль зависимостей и секретов перед выпуском; защита ветки/PR — в рамках возможностей тарифа и согласованного процесса. Наличие ручного согласования выпуска и обновление серверов через git уже снижают риск.
