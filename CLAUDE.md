# pg16-cert-prep

## Секреты: не светить паролями и токенами

Правило пользователя: «Никогда и нигде не светить паролями и токенами». Без исключений, в том числе для «тестовых» значений.

- Секрет не попадает ни в какой канал вывода: чат, текст исключений и стек-трейсы, логи, сообщения коммитов, документацию, тесты, комментарии в коде, команды для пользователя, скриншоты.
- `.env` не открывать ни через Read, ни через `cat`. Если нужно знать, какие переменные заданы, спросить пользователя.
- Секреты на сервере `appuse`: `/var/www/pg16-cert-prep/.env` (пароль роли БД, пароль почтового ящика `SMTP_PASS` и ключ `AUTH_SECRET`), `/root/.ssh/pg16-cert-prep-deploy` (закрытый deploy key, только чтение репозитория), `/etc/nginx/.htpasswd-pg16` (хеш пароля сайта). Их содержимое не выводить; проверять только наличие, права и владельца.
- SSH-ключи: закрытую часть никогда не выводить; у публичной показывать только отпечаток (`ssh-keygen -lf`). Команды, печатающие ключ целиком (`gh repo deploy-key list`, `gh api …/keys`), запускать с отбором полей без самого ключа.
- Секрет нужен команде: передавать через переменную окружения или файл. На экран выводить только булевы проверки («задан/не задан», «совпадает/не совпадает»), длину или хэш.
- Переменные БД (`DB_USER`, `DB_HOST`, `DB_NAME`, `DB_PASS`, `DB_PORT`) читаются только в `src/config/db.js` из `process.env`.
- В диагностике подключения к БД не выводить `err.message`: он может содержать адрес хоста и имя пользователя. Выводить только класс ошибки или `ok` / `fail`. В ответах API отдавать фиксированный текст ошибки.
- `.env` и `node_modules` должны быть в `.gitignore`.
- Если секрет всё же попал в вывод: сразу сказать пользователю, предложить перевыпуск и не повторять значение.

## Надёжность и наблюдаемость: обязательно для кода сервера и страницы

- **Ограничения по времени на каждом уровне**, каждый следующий дольше предыдущего: соединение из пула — 3 с, запрос к БД — 5 с (`statement_timeout`, дублирует `query_timeout` 6 с), запрос со страницы — 15 с, nginx — 60 с. Новые обращения к сети и БД без ограничения времени не добавлять.
- **Ошибку не глотать молча.** В `catch` перед ответом 500 вызывать `noteError(res, err)`, вне запроса — `logError('место', err)` (`src/middleware/requestLog.js`). В журнал службы пишутся класс и код ошибки, метод, путь, код ответа, номер пользователя, длительность. Текст ошибки, тела запросов, cookie и адреса почты — никогда.
- **Пользователю — понятное сообщение:** что произошло и что делать дальше, а не «Ошибка запроса».
- **Перед коммитом** сверять изменения с этим списком и с правилами о секретах.
- **Почему:** 16.10.2026 сервер подвис из-за нехватки памяти. Ответ на вопрос завис на 60 с до ошибки 504, а в журнале приложения не было ни строки: 18 из 20 мест перехвата ошибок молчали, ограничений по времени не было нигде. Разобрать случай удалось только по журналам nginx и PostgreSQL.

## Порядок работы над задачей

1. **Модель.** До начала задачи и перед каждым разделом плана назвать рекомендованную модель одной строкой. Пользователь переключается вручную.
2. **План.** Перед реализацией показать подробный план и задать вопросы, если они есть. Кода до согласования плана нет.
3. **Строго по ТЗ.** Всё, чего нет в задании дословно (поля, подписи, значения по умолчанию, параметры API, элементы интерфейса), сначала назвать и согласовать. Молча ничего не добавлять.
   Творческий подход в предложениях приветствуется (дизайн, формулировки, решения), но сначала описать идею пользователю и дождаться ответа. Делать что-либо без вопроса нельзя, даже если идея кажется очевидной.
4. **Тесты.** После реализации прогнать тесты по затронутым изменениям.
5. **Анализ изменений.** Выполнить `git status && git diff` и внимательно проанализировать результат:
   - могли ли изменения нарушить существующий код (регрессии, логика, сигнатуры функций, обработка ошибок, зависимости);
   - нет ли в диффе чувствительных данных.
   Итог описать пользователю в виде, пригодном для комментария коммита по Conventional Commits.
6. **Миграции БД.** Если меняется структура БД: подготовить миграцию, применить локально, проверить, что она завершилась успешно, перед этим сделать резервную копию. Затем дать пользователю команду для сервера. На сервере её выполняет сам пользователь, либо Claude — по его явной просьбе, с резервной копией базы и двумя запусками.
7. **Отчёт.** Вывести пользователю на экран результат выполнения задания и результат тестов.
8. **Коммит и деплой.** Только по явному разрешению пользователя.
9. **Учёт в `tasks`.** Каждую завершённую задачу записать одной строкой в таблицу `tasks` локальной базы `pg16_cert_db` (создаётся миграцией 001, на сервере её нет): `status` — `done` или `failed`, время начала и окончания, в `title` — что сделано, номера миграций и коммитов, выложено ли на сервер и применены ли там миграции. Если выкладка была позже, дописать это в ту же строку.
   **Почему:** 24.10.2026 записи о миграциях 058–060 пришлось вносить задним числом: правила не было, и сессия про таблицу не вспомнила.
